# L13 优化空间深挖（2026-09-21）

## 0. 本文的定位

第一篇（`mem-l02l05-2026-09-21.md`）与第二篇（`mem-l06l13-2026-09-21.md`）
给出 L02–L13 的内存全景与排序。本文只做一件事：**把 L13 的剩余优化空间按
"实测可证 / 假设待验 / 不可行"三类摊开**，并记录当日已落地的一项
（§3，unify 工作栈 buffer 复用）。

口径与工具同前两篇：分配计数（确定性）+ 峰值工作集 + 栈抽样归因
（`l06l13mem` 的 `L06L13MEM_TRACE_*` 开关）。所有"已落地"结论都有门禁
背书；"待验"结论明确标注未测部分。

## 1. L13 的静态成本底座（修复后口径）

### 1.1 结构尺寸（`l06l13mem --sizes`）

L13 是全链孪生态最大的章，结构尺寸上能看出代价来源：

| 项 | L13 | 邻章 | 说明 |
|---|---|---|---|
| `Tm` | **56B** | L02–L05 48B | 多 `Tm::Call` 一个变体（`&str` + slice + `&Tm` = 24B） |
| `Val` | 8B | 全链同 | 打包字 |
| `EnvCons` | 16B | 全链同 | |
| `CloCell` | 48B | 全链同 | |
| `PiCell` | 56B | 全链同 | |
| `MetaEntry` | **40B** | L02–L12 24B | 多 `Rc<MetaSnap>`（16B：上下文快照） |
| `DeclEntry` | **56B** | — | L13 新（`Span` + 两个 `&Tm` + `Option<Rc<String>>` + 两个 `V` + `Option<PrimId>`） |
| `Spine::Entry` | 32B | 全链同 | |
| `Cxt` | 208B | L09/L10 168B | 多 `namespace_prefix` / `decls` |
| **`Machine`** | **1,536B** | L12 1,072B | 20+ 张常驻表（见 §1.2） |
| `Tycker` | **2,552B** | — | `Machine` + 常驻 bump + `Resident` 检查点 |

`Tm` 从 48B 涨到 56B 意味着**同一份源码在 L13 的 arena 字节数比 L02–L05
高 17%**——这是 `Tm::Call` 变体的直接代价，不是浪费。`MetaEntry` 多出的
16B 是"孪生侧的 meta 上下文快照"（`no_metas` / `solve_multi_trait_ref`
读），同样不可省。

### 1.2 Machine 的 20+ 张常驻表

`Machine` 1,536B 里绝大部分是哈希表头。按**失效纪律**分三组：

| 组 | 表 | 清空时机 | 常驻桶风险 |
|---|---|---|---|
| 每轮清（per-run） | `trait_metas` / `symbol_table` / `import_map` / `trait_method_cache` / `tm_import` / `val_import` / `mutable` / `tstate` | `clear_round` | 桶数组不清（见 §2.3） |
| 每 kick 清（per-kick） | `decl_suffix_index` / `suffix_indexed_keys` / `suffix_memo` / `binding_name_mk` / `ns_method_cache` / `ctor_hover_memo` / 三张观察表 | `observe_user` 入口 + kick 末回滚 | 同上 |
| 进核前 clear（复用容量） | `spine.stack` / `vals` / `icits` / `conv.*` / `eval_work` / `quote_*` / `unify_work` / `unify_stack` / `ren` / `constraints` | 各入口 | 已有 `reclaim` 归还档（见 §2.3） |

第三组已有 `ReclaimOnClear`（`CACHE_SHRINK_MIN_ENTRIES = 1<<18`、
`SPINE_SHRINK_MIN_ENTRIES = 1<<16`）在容量到阈值的清空点顺带
`shrink_to_fit()`——这是 L13 相对前十二章独有的机制，`typort stats` 的
孪生口径读数就来自这里。**第一、二组的 8+6 张表没有归还档**：清空只
`clear()` 不还桶数组（见 §2.3 的建议）。

## 2. 已落地：unify 工作栈 buffer 复用（−23% struct）

### 2.1 问题与归因

`Machine::unify` 入口为保护"外层尚未弹出的待办对"（unify 重入）**无条件**
`std::mem::take(stack)`。但非重入入口也 take 时：

1. `unify_stack`（Machine 常驻 buffer）被挪进局部量 `saved`；
2. field 里留下一个全新空 `Vec`；
3. `unify_iter` 从 0 开始长（4→8→16…）；
4. 成功路径 `*stack = saved` 把长大的 buffer **整个 drop**。

即每次 unify 调用都重放一遍完整增长序列。

**归因手段**：`l06l13mem` 的栈抽样 + 相位闸（`trace_arm()` 在 parse
结束、engine 段开始时置位）+ skip（越过 parse 段同尺寸噪声）。深层阶段
288–352B 桶的分配 **100%** 来自
`unify_iter <- Machine::unify` 的 `RawVec<UItem>::grow_one`。

为什么这一个桶这么大：`UItem` 是 L13 最大枚举变体格（`MatchStruct` 持
两个 `&[..]` slice 头 + `Rc<Decls>` + 两个 `Env` ≈ 88B），4 条即 352B；
而 `Vec` 按 4→8→16 翻倍，**第一跳（4 条）就正好落在这个桶里**，所以每
次 unify 至少贡献一次该尺寸分配。

### 2.2 修复

入口**只在栈非空时 take**（非空 = 确有外层待办对 = 重入形态）：

- 非重入（99%+ 的调用）：field 里"上次长大的空 buffer"原地留着，
  `unify_iter` 直接续用，零分配；
- 重入：照旧暂存外层项；内层成功后用 `append` 把外层项放回 field 顶部
  （field 里已是本层长大的空 buffer），buffer 同样留下次续用；
- 成功却非空（旧契约外的意外形态）与失败路径**逐分支保持旧行为**
  （整体替换 / `clear()`）——语义对齐，不留"顺手优化"的暗分区。

### 2.3 实测（l06l13mem，k=11）

| 负载 | 修复前 | 修复后 | Δ |
|---|---|---|---|
| struct | 124,021 allocs / 23.66MB | 107,630 / 18.16MB | **−23%** |
| strchain | 86,751 / 27.28MB | 74,466 / 23.15MB | **−15%** |
| prelude-core | 54,290 / 23.50MB | 52,691 / 22.96MB | −3% |
| church | 9,617 / 3.71MB | 9,577 / 3.70MB | −0.4% |
| natadd / gadt / match / enum / moduletree | — | — | 噪声带内 |

struct 的 320B 桶（16,396 allocs / 5.25MB）**整桶消失**。reset 后保留
arena 不变（chunk 链由 skim 顶决定，与全局分配无关）。

时间 A/B（l13bench，fast_ss，rounds 5）：struct 12.08→11.95ms、
strchain 8.22→7.81ms，其余噪声带内——**无回归**。

门禁：`l13_fast_parity` 417 / lib L13 405 / 全仓库 38 套件 0 失败 /
l13bench 八负载「快版==参考版」互检全 ok。

### 2.4 同一形态还可能在别处

这次是"常驻 buffer 被 entry 阶段无条件 take/替换掉"的经典形态。同类
嫌疑点（**未逐一审计**，仅列出读码时看到的相似结构）：

- `quote_memo`：注释明确"容量跨调用复用，内容每次调用 clear"——已是正确
  形态；
- `Machine::update_cxt` / `decl_reg_in` 的 `Rc::make_mut`：COW，独占时
  原地写（已优化过）；
- `state_journal` 帧：`push(Vec::new())`——每 kick 一帧，量极小。

## 3. 剩余优化空间（按收益排序，均为**未实施**）

### 3.1 观察面成本：prelude-core 的 16%（假设，需二次确认）

l13bench 的 `fast(no-obs)` 对照（`L13BENCH_NOBSERVE=1` 关掉
`typ_pretty` / hover / inlay 渲染）：

| 口径 | allocs | bytes |
|---|---|---|
| observe 开 | 113,183 | 28.05MB |
| observe 关 | 54,280 | 23.48MB |

差值 58,903 allocs / 4.57MB。但注意：`print_sizes` 与 churn 口径里
observe 开/关的差只有 ~10 allocs——说明**大头在一次性增长段**，且只影响
bench 口径的"每轮全量重放 prelude"路径。生产 LSP 已常驻 prelude
（`prime_resident` 一次装载），用户段每 kick 只推用户 decl 的观察条目，
所以这 4.57MB **不是 LSP 稳态成本**。判定：优先级低，值得一次
`TYPORT_KICK_PROBE` 确认后归档。

### 3.2 decl 表 + 后缀索引每轮全量重建（结构性，优先级中）

`bench_check_nf_bounded` 每轮 `resident = None` → 走 `prime_round` 全量
重放。L13 `struct` 每轮 124k allocs 里，`decl_reg` 的 `Rc<Decls>` 克隆
（栈抽样显示为 `hashbrown RawTable clone <- Rc::make_mut`）与
`index_decl_key` 的后缀索引维护占可见份额。

- **bench 口径**：这是测试假象，不是生产问题；
- **`typort --file` 一次性 CLI**：峰值本来就 ≤30MB，与 decl 表同量级；
- **LSP 常驻路径**：已回灌（`prime_resident` + journal 回滚），不受影响。

结论同 §3.1：结构清晰但收益面窄。若要动，方向是"suffix 索引延后到首次
fallback"（现在每键即时索引）。

### 3.3 第一/二组哈希表无归还档（长驻 LSP 的稳态 RSS 项）

`clear_round` / `observe_user` 清空的 14 张表只 `clear()` 不
`shrink_to_fit()`。第三组已有 `ReclaimOnClear` 归还档且证明有效
（`CACHE_SHRINK_MIN_ENTRIES` 阈值 + `typort stats` 读数），把这同一机制
推广到第一/二组是机械改动。收益取决于真实 kick 序列中这些表的峰值容量：
`decl_suffix_index` 在 prelude-hdl（900+ decl）装载后桶数组约数百 KB 级，
常驻到进程结束。**值得在 LSP 长会话场景实测**（需构造 5 分钟以上的
kick 序列量 RSS）。

### 3.4 `Tm::Call` 的 8B 变体开销（结构性，不建议动）

`Tm` 48→56B 让 L13 的 arena 字节比 L02–L05 高 17%。`Call` 变体是 inline
match 特性的必需载体（`wrap_match_in_call` + eval 的 Call 帧），且 8B
变体差在 56B 的 enum 布局里还可能被对齐吃掉一部分。除非实测确认影响，
不建议为省 8B 把 Call 换成侧表（会引入间接寻址，反而更慢）。

### 3.5 strchain/global 的堆字符串 O(n²)（跨章项，见 §6.2）

L13 的 `string_concat` prim 仍是堆 `String`。这条与 L06–L08 同源，代价
在 arena 外的 O(n²) 字节（k=13 ~257MB）。L09/L10 已证 arena 化可行且
churn 归零。跨章统一做更划算（一次改 prim 分发，八章受益）。

## 4. 不建议动的部分（避免"优化"成回退）

1. **`fresh_meta` 的全链 close 语义**——L10 刚做过值中性化简
   （`close_tm_reduced`），L13 的 `fresh_meta` 走 `close_tm`（包整条链）
   与参考版 `close_ty` 逐字节同轨。L13 的 telescope 只有当前 def 的局部
   条目（globals 进 `Rc<Decls>` 表、不进 binder 链），所以**不存在** L10
   那个 O(n²)。不要"顺手"把 L11/L12/L13 也改掉。
2. **`force_memo` / `PRIME_COMPACT_BYTES=384MB` / `didClose` 修复**——
   `docs/mem-round-2026-09-20.md` 已记录前两轮的调参与修复，当前档位是
   实测后收敛的结果。
3. **`unify_stack` 的重入保护本身**——它是 `cong` 隐参分叉的修复
   （`examples/theorem_proving`），本次只改"何时 take"，没改保护语义。

```bash
cargo build --release --bin l06l13mem
# struct 前后对比（本次修复的收益格）
./target/release/l06l13mem --chapter L13 --workload struct --k 11 --no-basic --rounds 1
# 归因：只采 engine 段、越过 parse 段的 288B+ 分配，各取 60 个栈
L06L13MEM_TRACE_MIN=288 L06L13MEM_TRACE_SKIP=6000 L06L13MEM_TRACE_MAX=60 \
  RUST_BACKTRACE=full ./target/release/l06l13mem --chapter L13 --workload struct --k 11 --no-basic --rounds 1
# 观察面对照
L13BENCH_NOBSERVE=1 ./target/release/l06l13mem --chapter L13 --workload prelude --rounds 1 --no-basic

# 时间 A/B
./target/release/l13bench --workload struct --max-k 11 --only fast,fast_ss --rounds 5
# 门禁
cargo test --release --test l13_fast_parity
cargo test --release --lib L13_namespace
cargo test --release
./target/release/l13bench --workload <w> --max-k 11 --only basic,fast --rounds 1
```

新增归因开关（`src/bin/l06l13mem.rs`，保留给后续排查）：
`L06L13MEM_TRACE_EXACT`（只采某精确大小）、`L06L13MEM_TRACE_SKIP`
（越过 parse 段）、相位闸 `trace_arm()`（parse 结束后才开）、
**重入闸**（低阈值下 `Backtrace::capture()` 自身分配会经本分配器重入、
死锁在 backtrace 库内部锁——嵌套采样直接抑制）。
