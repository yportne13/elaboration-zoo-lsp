# L11_macro 实现剖面

> 对象：工作树 HEAD `8443586e`（2026-11-08）。只读静态分析，未运行任何 cargo/bench。
> 引用规则：代码 `src/...:LINE`，文档 `path §N`；判定标注 [码]/[文档]/[推断]，无法核实标 [未核实]。
> 一句话结论：**L11 是 L13 引擎的"宏 + decl 表"原型：语义基线清晰、可作教学与迁移参照，但性能口径缺环、工程性未达标，不宜当产品层。**

## 1. 定位与语言特性增量

L11 在链上是**「再定基（换全局名字世界）+ 增糖（宏）」的混合**，不是纯重写：参考版即
L13 引擎的早期形态（Arc 持久化 + decl 表贯穿），README 自述见 `src/L11_macro/README.md:3-9`；
`type Rc<T> = std::sync::Arc<T>` 与名字键 decl 类型见 `src/L11_macro/mod.rs:20-22`。
它保留 L10 的全部语言面（trait/impl、接收者方法调用、`outParam`、typeclass 求解），在其上新增：

| 增量 | 本层取值 | 锚点 |
|---|---|---|
| `macro_rules`（声明级/表达式级） | parser 内匹配 + 转写，**类型检查器无感知** | `parser/mod.rs:1310-1381`、`parser/macros.rs:10-33` |
| 宏深度守卫 | `MAX_MACRO_EXPANSION_DEPTH = 256`，thread_local + RAII | `parser/mod.rs:140-183` |
| 展开 LSP 记录 | `MacroExpansionInfo`（调用点 span/展开文本/宏定义位置/消歧位） | `parser/mod.rs:9-29` |
| 内建 5 个 | `string_concat` / `string_to_global_type` / `create_global` / `change_mutable` / `get_global`，注册进 decl 表 | `cxt.rs:28-92`、`:94-115` |
| 可变全局 | `Infer.mutable_map`（每轮清空） | README §1.2；`cxt.rs:51-92` |
| `#[macro_export]` | 声明点解析属性 | `parser/mod.rs:2038-2041` |
| 语法小项 | `f[A, B]` 隐式实参逗号合写（已回移植 L06–L10，`e2d04bb`）、`f a (b)` 括号消歧（`0958e2e`） | README §1.1 |

**丢弃/回归**：`Infer.global` 表与 `Tm::Var(Ix(global_idx + 1919810))` 大下标哨兵在本层同源位置消失
（FACTS §8；a5-r1 §1 判"L11 起为 decl 表/名字键世界"）；不再有 L07 的 `Enum.case` 限定名别名，
构造子只以裸名登记（README §1.2）。**时代缺口**：L07 加固轮 P1–P11 未回灌（CONVENTIONS §2），
L10 的实例求解 `effort > 1000` → `panic!("Too much effort :(")` 崩溃面仍在（`typeclass.rs:201-205`）。

要点补充：

- **Q2（宏在 parser 内展开的取舍）**：展开发生在造 `Raw` 之前（`parser/mod.rs:1310-1381`），
  类型检查器完全不知道宏存在——代价是**语义/诊断/LSP 全在解析层补偿**：①`MacroExpansionInfo`
  每个展开点记调用点 span、`expanded_text`、宏定义 `def_start/end_offset + def_path_id` 和
  `name_token_is_macro` 消歧位（`parser/mod.rs:14-21`、`:1333-1342`），这是 goto-definition 的
  唯一数据源；②模板字面量 token 的 span 被整体改写成"整个宏调用区间"，捕获 token 保留调用点
  span（`parser/mod.rs:239-246`），于是报错定位落在调用处而非宏内部——诊断精度是刻意代价；
  ③`expanded_text` 在**每次展开都无条件序列化**（`parser/mod.rs:1337`、`:206-222`），即使本次
  运行没有 LSP 消费者也不省略（开销占比 [未核实]）；④token 级拼接、名字是 String 键，机制上
  看不到卫生宏/gensym（是否有意 [未核实]）。L11 自身没有 LSP 接线（`tests/` 只有
  `l11_fast_parity.rs`），生产 goto-definition 由 L13 的 parser 版本 + `src/lib.rs:469/2981-3015`
  消费（`goto_macro_definition_name` 按 `name_token_is_macro` 过滤）。
- **`be8ec25` 直接 token 拼接 vs 旧「序列化文本 → 重词法」**：旧路把展开结果落成字符串再整串
  重词法，需要 `span_map` 回查位置，且捕获 token 要深拷贝 `String`；新 `splice_transcriber`
  （`parser/mod.rs:247`）沿转写器树直接按借用拼接 token，按构造复刻旧词法的两个归一化
  （相邻 EndLine 折叠、丢 Eof，`splice_push` `:224-237`），并把模板字面量 span 改写成调用区间。
  收益：免去序列化/二次词法与捕获深拷贝，提交实测 fast_run −15~−18%（README §1.1）；
  代价：归一化从"词法器保证"变成"手工复刻保证"，任何词法层新增行为都要同步这里 [推断]。

## 7. 优劣评估

**优点（≥3，均给证据）**
1. **名字键 decl 表 + Arc 持久化**：quote/rename 对 `Tm::Decl` 原样往返，没有 L09/L10 大下标
   哨兵的边界 off-by-one 类风险（a7-r1 §2.2 表：L11–L13 无哨兵）；且与 L13 同构，迁移/对照成本低。
2. **宏实现的自包含性**：parser 内展开令类型检查器零改动获得 `macro_rules`；直接 token 拼接
   免二次词法（fast_run −15~−18%，`be8ec25`）；`MacroExpansionInfo` 一次记录同时服务
   goto-definition/展开文本（`parser/mod.rs:9-29`）；256 深度守卫把自递归宏从栈溢出降为解析错误
   （`parser/mod.rs:136-183`），对"LSP 可喂任意源码"是必要的健壮性。
3. **匹配编译器与 L07/L08 统一**：逐臂 + 值级探测后，match 参考版 1.250→0.542 ms、孪生 fast_ss
   1.524→0.180 ms（README §2.1）；探测热点 6.2×（孪生）且判定与旧探测逐例一致（README §2.2）；
   P0 嵌套覆盖以两段式恢复，且参考/孪生共用 `fmt_path` 保证文案逐字节一致（README §2.3）。
4. **trait 面错误文案比 L10 细**（`cannot infer typeclass` / `no (matching) instance` + available
   instances，`elaboration.rs:383-418`），且孪生复用同一 `Synth` 避免两套求解器漂移。
5. **`Cxt.decl` COW** 把每次 Cxt 构造的整表克隆降为 O(1) 计数递增（`cxt.rs:17-23`），实测大值负载
   3.2–3.5×。

**缺点/风险（≥3，均给证据）**
1. **bench 口径缺口 + 无 golden/blackbox/LSP 测试**：参考版缺 `bench_check_nf` 使跨层参考版
   数字不可比（a7-r1 §4 P3）；无字面输出 golden（a7-r1 §2.6）；L11 无 LSP 套件（LSP 消费方在 L13）。
2. **第二套实现的文档腐化**：8.4k 行孪生的模块头仍描述 `update_cxt`/`refresh`/`lvl_types`
   （`bump_spine_iter.rs:40-43`），与 HEAD 的 σ 实现矛盾；`*.bak` 14 个副本、拆分为纯机械搬运
   （无真模块边界），长期双实现维护面积仍是 ~7.9k 行/层。
3. **参考版固定开销与残留 O(n²)**：`DeclTm::Def` 的 `typ_pretty` 每 def 做一次 nf+pretty 而
   **无消费方**（`elaboration.rs:420`；body 侧已置空 `:421`）；decl 插入仍先 clone 再 `make_mut`，
   共享时整表克隆 ⇒ O(n²) 残留，且键仍是 `String`（L12/L13 已 `SmolStr`）
   （`docs/perf-l08l13-followup-2026-09-17.md` §3.4）。
4. **匹配诊断仍弱于决策树旧口径**：遮蔽只认通配臂、特化方程失败的臂静默跳过（README §2.3 保留
   两条收窄）；恢复路径感知遮蔽需另建 usefulness 分析——这是全仓统一算法的共同代价。
5. **健壮性/语义缺口**：`get_global` 对未注册名字 `unwrap` panic（`cxt.rs:88`）；
   `Too much effort :(` 是崩溃不是类型错误（`typeclass.rs:201-205`）；无 K 公理层保护（教学取舍）；
   `enum` 负载孪生 check+nf 失败、`gadt` 快版缺陷区。
6. **宏是"解析期重写"不是独立语言机制**：无卫生宏、无宏级类型检查、错误定位锚在调用点
   （模板 span 被改写，`parser/mod.rs:239-246`），`expanded_text` 无条件分配（LSP 之外也付）。

## 8. 与相邻层的关系与当前状态

- **继承/分叉**：L11 从 L10 继承全部语言面与 `Synth` 求解器，但**换掉名字世界**（decl 表回归，
  Q1 的动机链）：①`macro_rules` 在解析期产生顶层声明/表达式，名字键表与 parser/AST 的天然键一致；
  ②LSP 跨文件 goto-definition 需要名字而非 elaborator 内部序号；③L09/L10 的哨兵方案把名字解析
  耦合到 global 索引（`lvl2ix` 的 `>=` 边界，L10 README §2），a7-r1 §2.2 显示 L09/L10 有 20 处
  哨兵使用、L11–L13 零处——换回是为 L12/L13 生产化铺路。**收益/成本**：一次性成本在 L11 付清
  （所有核心函数穿 `decl: &Decls` 参数、decl 表 COW/O(n²) 残留、匹配编译器适配点从"无 decl 表"
  变成"String 键 decl 表"），收益被 L12/L13 摊薄——L12 只把键换成 `SmolStr`（`L12 mod.rs:24`）
  并在此表上做 canonical/Val 级求解，L13 再在其上加 namespace 做生产引擎；此后无层回退，说明
  该选型被验证 [推断，证据：L12/L13 的 `type Decl` 同构]。
- **L11 → L12**：演进为主、裂缝清零（a5-r1 §1/§2 行 11–12：Val 级求解器、`Val::Call`、canonical
  重试、`Either` icit、`SmolStr`）。L11 保留的两条匹配诊断收窄与 effort panic 被 L12 原样继承。
- **与 L13**：L13 是生产化层，出发点是 L11 式 decl 表引擎（README §1："参考版是 L13 引擎的早期
  形态"）；L11 的 `MacroExpansionInfo` 数据形状被 L13 的 parser/LSP 沿用（`src/lib.rs:469/2981-3015`），
  但 L11 自身不接线 LSP。参考版无 `PreludePool`/迭代 Drop 等 L13 设施，孪生无 L13 的常驻检查点/
  `compact` 压实（FACTS §4 "只在某侧"清单）。
- **当前状态**：HEAD `8443586e` 为文档终报，不波及代码；09-20 后 L11 仅 `3b907be9`（拆分）、
  `bbb673fd`（卫生）、`1719292d`（尾任务寄存器化）三次结构/微调提交。A5 轮修复（探测隔离、臂位次、
  可达性记录、pretty 降级）已在 HEAD 生效，parity 52 全绿 [文档：提交记录；未执行]。
- **待 Lead 汇总的口径订正**：(1) FACTS §2 "L11 孪生单文件 7873 行"过期（HEAD 为入口+14 子模块，
  `3b907be9`；L12 同理 `7700b50e`）；(2) README §6 测试数 29/48 过期（实际 33/52）；(3) 孪生模块头

  未达标，不宜当产品层。
