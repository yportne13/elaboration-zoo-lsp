## 0. 结论（先回答两个问题）

### 0.1 L08/L09 是不是弱于 L07？——是，但"弱"的维度不同

| 维度 | L08 相对 L07 | L09 相对 L07 | 判定依据 |
|---|---|---|---|
| 健壮性（深值栈安全） | **弱**：10 万层 succ 链在 1MB 栈上 quote/occurs/struct_eq 直接栈溢出（exit `-1073741571`） | **弱**：quote/occurs 同样栈溢出（且 force 无防御，跨 meta 环也溢出） | 实测探针（§2.1） |
| 诊断分层（P3 三档） | **弱**：无 `UnifyKind`（0 处），判不出统一报"分支不可达" | **弱**：同上（0 处） | 静态缺失 + 用例编译失败 |

## 2. "弱"的实测证据（回灌前）

### 2.1 P11 深值栈安全（最硬的崩溃证据）

构造 100,000 层 `Nat.succ` 链，在 **1 MB 显式栈线程**内跑；每例单独进程。

| 用例 | L07 | L08 | L09 |
|---|---|---|---|
| occurs（`val_mentions_lvl`） | ✅ exit 0（0.22s） | ❌ 栈溢出 exit `-1073741571` | ❌ 栈溢出 |
| quote（`Infer::quote`，深度 100001） | ✅ exit 0（0.18s） | ❌ 栈溢出 | ❌ 栈溢出 |
| struct_eq（100k 同构链） | ✅（迭代 EqTask） | ❌ 栈溢出（递归 + 2 万预算） | 无该模块（静态） |

### 2.2 P5 跨 meta 环

| 层 | 现象 |
|---|---|
| L07 | 环守卫命中：`fuel 64→62`，展开栈清空，43µs |

## 3. 回灌方案

### 3.1 L08：整层重定基（= L07 HEAD + 积类型增量）

L08 原本是 L07 的**滞后拷贝**（2026-09-15 前后复制，之后 L07 的 09-18 深值轮 / 10-31～11-08 P1–P11 未回灌）。最省事且最不易漏的做法是把参考版整体换回 L07 HEAD，再把 L08 的 5 处积类型增量重新落位：

| 增量 | 落位 |
|---|---|
| lex：`struct`/`new` 关键字 | `parser/lex.rs`（StructKeyword/NewKeyword + KEYWORD 表 9 项 + Display） |
| parser：`p_struct`/`p_new`/多段投影链 | `parser/mod.rs`（p_atom1 + many0 fold、p_raw `.or(p_new)`、p_decl `.or_far(p_struct)`） |
| elaboration：类型级 `.mk` 剥链投影 | `elaboration.rs` `Raw::Obj` 的 `Val::Sum` 臂（单 case 且名字含 .mk） |
| unification：`(Obj,Obj)` 合同臂 | `unification.rs`（字段名同 → 比接收者 + spine） |
| pretty：`{Type}.mk` 去重 | `pretty.rs`（SumCase 显示） |

其余参考版文件（mod/cxt/struct_eq/pattern_match/syntax/parser/syntax/tests）为 L07 HEAD 原样；`tests.rs` = L07 的 64 用例 + L08 的 12 积类型/回归用例（共 76；整层 lib 测试 81 通过）。孪生 `bump_spine_iter/**` 未做功能移植，仅修编译（`Error` 两字段、parser 签名、`Error::new`）。

### 3.2 L09：按架构适配（逐项）

L09 是"再定基"层（无 decl 表、哨兵 global、walk_pat、σ 精化），不能整层覆盖，逐项适配：

| 项 | L09 落点 | 验收 |
|---|---|---|
| P11 quote 迭代 | `quote/quote_sp` → `quote_deep` + Frame 任务栈 + 浅链快路径 | `deep_value_iterative_under_default_stack` 通过 |
| P11 rename/occurs | `rename_deep`（Sum/SumCase/Obj 帧式收集）+ `InlineStack` 版 `val_mentions_lvl` | 同上（深链探测） |
| P11 pretty 定深 | `MAX_DEPTH=1024` + DepthGuard | 深值显示不爆栈 |
| P11 struct_eq | 新文件 `src/L09_mltt/struct_eq.rs`（EqTask/InlineStack/budget），接回 Match/Match 快路径，中性视图作 fallback | `struct_eq_compares_match_pending_values` 通过 |
| B1 pending splice | `Val::Match` 第 4 字段 `Rc<Vec<(Rc<Val>, Icit)>>`；`v_app` 累积、分支选中后应用；force/quote/rename/unify/struct_eq 全链 | `test_stuck_match_splice` / `..._applied_with_outer_binder` 通过，原 panic 消失 |
| P2 预算 | `MATCH_CMP_BUDGET=64` + `Infer.match_cmp_budget` | 有界（L07 用例通过） |
| P3 三档 | `UnifyKind{Absurd,Undecided,Fuel}` + note/reset/read；覆盖探测 "Undecided→保守可达" | `test_unify_kind_separates_absurd_from_undecided` 通过 |
| P5 环守卫 | `meta_expanding` 压栈/检查/弹栈 | `cross_meta_cycle_force_is_bounded` 通过 |
| P10 | **N/A**：L09 已有 `Error(Span<String>)` + parser 前缀恢复 | — |
| P8 / P1-2 / P0-2 | **N/A**：P8/P1-2 依赖 decl 表；L09 探测回滚不走整表 clone（undo-log 无宿主） | 已在 README 记录 |

## 6. 与孪生版的边界（用户要求"先不看孪生"）

- L08 孪生、L09 孪生**均未做功能回灌**，只做编译适配；因此两层的"参考版"现在领先孪生（P3/P10/P11/深值轮/pending 等）。
- L08 `l08_fast_parity` 对 P3 唯一可观测差异登记为 `assert_parity_err_kind_divergent`（参考版"无法判定"vs 孪生"分支不可达"）；其余 115 例 Ok/Err 严格一致。
- 若后续要把孪生拉齐：L08 孪生需补 P3/P10/P11/深值轮（技术上同 L07 孪生已有实现，可直接对照移植）；L09 孪生需补 pending/struct_eq/P2/P3/P5/深值轮。

## 7. 遗留风险与建议

1. **L09 参考版吞吐仍明显落后**（struct 负载 ~71×、enum ~4× 于 L08）——根因在 L09 的 `src_names` 逐 decl 克隆 / 无 decl 表结构，**本轮未改**（超出"回灌 L07 加固"范围）。若 L09 要当性能基线，建议优先做名字表搬 `Infer` 或等价的结构优化。
2. **L09 多段投影断裂**：黑盒测试钉住 `l.a.x` 解析通过但类型检查失败（L09 血统缺 L08 的多段投影链），README 旧称"继承 L08"已不实；本轮未修（属语言面而非 L07 加固）。
3. **L09 孪生与参考版行为分叉扩大**：pending/struct_eq/P3 等只在参考版；parity 套件未覆盖这些分叉（l09_fast_parity 仍 46 绿，因为语料不触达）。建议下一轮要么镜像，要么在 parity 头注登记。
4. **L08 文件 IO 失败契约变化**：从 panic 改为卡住值（L07 口径）——黑盒 v2 已按新契约更新；依赖 panic 的外部用法需注意。
5. **性能测量受宿主负载影响较大**（同机不同时段 k=13 可差 2× 以上）；本报告的 A/B 采用 old-new 交错取 min，仍建议以同次会话内的相对比值解读。
