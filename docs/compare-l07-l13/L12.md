### 1.1 三件增量的动机、代价、可观察差异（问题 1）

- **Val 级求解器**：动机是消除 L10/L11 `val_to_typ` 的有损桥（[文档] `bump_spine_iter.rs:19-24`）；
  代价是求解器必须自己实现 `Val` 的结构 DI（`typeclass.rs:123-193`）、`vals_eq_ground`（`:196-249`，
  Flex 视为等于一切 `:205`，Match 分支体用 `Rc::ptr_eq` 判同源 `:235-246`），孪生侧另搭
  `v_to_ref_val` 桥（`:19-24`，非热路径）。可观察差异：实例匹配精度与个别错误文案；护栏仍是
  `panic!("Too much effort :(")`（`typeclass.rs:311-316`）。
- **Call 节点**：动机是 HDL 泛型调用/卡住 match 的显示还原；代价是 7 个模块都要加臂（含
  `v_applicable` `mod.rs:435-445`、quote `:1134-1137`、rename `unification.rs:391-393`）。
  可观察差异：卡住 match 经 `lookup_function_by_cases` 反查后 quote 成 `Tm::Call` 外衣
  （`mod.rs:1172-1181`）——这是**唯一**真正生效的面；`Val::Call` 是纯消费型变体。
- **canonical 搜索**：动机是 LSP quickfix 的"再试一次"（`canonical.rs:20-23`）；代价是
  `check<const CANONICAL: bool>` 泛型穿参（`elaboration.rs:274`）+ `check::<true>` 只服务
  `search` 的候选探测（`canonical.rs:114`）+ 每候选 `refuel()`（`canonical.rs:112`）。
  **可观察差异 = 0**：`run`/`run_fast`（`mod.rs:1249-1287`）不经；重试闭包由 `Error` 携带，
  而仓库内唯一 LSP 只接 L13（`src/lib.rs:100-104` 全是 `L13_namespace::`；L12 在
  `lib.rs:66-67` 以 `#[cfg_attr(not(test), allow(dead_code))] pub mod` 存在），
  没有任何二进制/测试/服务调用 `Error.1` 的闭包 ⇒ iddfs 在仓内**不可达**。
  - **判定**：既不是"参考版功能更全"的可用功能，也不完全是"死代码"——准确说法是
    **未接线的设计资产**（L13 quickfix 机制的提前移植）。按可观察行为算死代码；按文档价值算
    机制预演。风险：一旦将来接线，它没有任何测试（`canonical.rs` 无 `#[test]`，parity 也不比对），
    且其 `search` 递归里大量 clone + 反复 `check::<true>`（`canonical.rs:79-146`）。
  - 附带：README §6 说 iddfs 预算已修（1,2,3,…）；`docs/test-catalog.md:298` G11-01 仍写
    "1,3,5,…/target_limit=6 缺口"——**文档过期**。当前实现 `canonical.rs:24-29` `+=1`、`<=`。

## 3. 核心机制现状（逐项 + 锚点）

- **精化载体**：σ 显式替换（`Subst` 持久单链 `mod.rs:306-428`、`Val::VSub` `:288`、`SpecSolve{acc}`
  `elaboration.rs:23-25`、`check_pm_final` 返回 `(Tm, Subst)` `:87-104`）。`lookup_hit` 条件包裹
  （`:327-340`）、`mentions_level` 宁宽勿窄（`:358-397`）、`compose` 对齐"后写覆盖"（`:413-428`）、
  `subst_cxt` 只包 env/src_names（`cxt.rs:320-338`）。第二方程失败容忍丢弃（`elaboration.rs:99-102`）。
  可解集 = **任意裸 Rigid**（无 bind-slot 白名单，`SpecSolve` 没有 `solvable` 字段）。
- **σ 的机制边界（问题 2）**：frcs 只推进到中性头——spine 槽**只包裹不推进**（`mod.rs:750-759`，
  物化会破坏后续 invert）、闭包 env 只包裹不进体（`:770-781`）、Match scrutinee 推进并按首匹配
  重选（`:813-830`，等价旧 refresh 的重选）、被解变量读点烧 1 fuel（`:727-736`，耗尽按未解降级）。
  **只有 σ 能做、update_cxt 做不到的**：① 槽位布局恒等于运行时布局（`cxt.rs:312-319`），
  "已捕获旧上下文的值过期/槽位错位" bug 族按构造消除；② 解值带头应用时在 frcs Rigid 臂把
  spine 实参逐个 `v_app` 到解值上（`mod.rs:731-748` 的"解出函数型索引槽后再应用"路径，
  非可应用头则保持卡住 `:741-743`）；③ 臂边界回滚 = `Rc` 指针赋值（O(1)），臂序无关有钉
  `test_stale_solvable_order_independent`（`mod.rs:2627`）。
  **边界**：canonical 搜索与 trait 实例求解**不走** `unify_pm`（`elaboration.rs:119-123`），
  拿不到特化解；`force_arg`/`force_deep` 两档视角分离（README §3）；σ 驱动全部来自 pattern 方程。
  **已知分叉家族与 σ 的关系**：`tests/l12_fast_parity.rs:9-13` 剔除的 GADT 索引宇宙×trait、
  struct 接收者实例、单臂构造子匹配、Prim 求值时机——[推断] 均非 σ 产物（σ 在参考版与孪生
  中都实现，`bump_spine_iter.rs:99-101/187` `SubstV`/`SpecSolve`），更可能来自孪生侧
  `v_to_ref_val` 桥、`TraitState`、求值时机差。真正与 σ 相关的分叉是**层间**的 L12(σ) vs L13
  参考版（`update_cxt`，`docs/l09l13-match-compiler-analysis-2026-09-17.md:38-42`）——L13 五轮
  σ 迁移失败是反向证据（`docs/explicit-subst-refactor-status.md:44-46/116`）。
- **匹配编译器**：逐臂下钻 `Compiler::compile`（`pattern_match.rs:177`）→ `walk_pat`（`:376`）；
  值级覆盖探测 `probe_accessible`（`:87`）+ 独立充值 fuel + 耗尽按可达处理；嵌套覆盖两段式

  Rc<Decl>` 写时复制（`cxt.rs:17-21`，`53e8adb`）；无 `Infer.global` 哨兵（L09/L10 专属）；

### 4.1 parity 15 例是否意味着可信度更低（问题 4）

静态口径：parity 15 例（自有）＜L11 19＜L10 21（`FACTS.md` §3）；但参考侧 lib 静态测试是 L10 25 /
L11 33 / **L12 35**（本层 `#[test]`：`mod.rs` 21 + `parser/mod.rs` 13 + `lex.rs` 1），数量并没降。
**不能只看 15**：真正的问题是**剔除面刚好覆盖 L12 的增量面**——所有 mod.rs 语言特性源（trait/impl、
GADT、struct 接收者）都被移出比对，孪生又结构性缺失 Call/canonical，所以"双引擎可信"只覆盖共享
内核（eval/force/quote/unify/rename/逐臂编译器），恰好在 L12 自认的紧点上无保证。
判读应为**可信度结构性分布**：内核高（deep_workloads/steady_state/errors/packed-cell 钉硬）、
增量面低甚至为零；而不是"整体比 L10/L11 低 30%"。
历史证据支持该判读：eprintln 回归（6.56×）是 bench 发现、不是 parity（`docs/bench-matrix-2026-09-20.md:
39-47`）；canonical 与 Call 从未被任何 parity 触碰。可抵消项：本层新增了 σ 跨轮回收钉
（`fast_substv_reclaimed_across_rounds`，`tests/l12_fast_parity.rs:844`）、packed-word 对齐、
η 守卫/u64 溢出/宏深度/trait 可恢复/pruning 掩码等 probe（`:443-570`），这些是 L11 没有的。

## 7. 优劣评估（问题 5）

**优点**：① 语义增量密度最高：Val 级求解 + σ + namespace + 宏 + Call 骨架，是 L13 之前最接近
产品语义的一层；② σ 路线在本层最完整（条件包裹/组合/两档 force/燃料降级都有代码与注释），
是读 dpm-nbe 对齐实现的现成样本；③ 逐臂编译器 + 值级探测让参考版 match 修后 0.196 ms，
在七层参考版中列第 4（慢于 L07/L08/L10，快于 L11/L13/L09）；④ 回归钉质量高（嵌套覆盖两段式、
构造子 WF、臂序无关、σ 跨轮回收），错误文案与 L07 统一；⑤ 孪生大值负载 47–85×，`Tycker` 稳态
复用 + σ 跨轮回收解决了长生命周期泄漏。
**缺点/风险**：① **死面**：canonical/iddfs、`Val::Call`、hover/completion 都是"只建不用"，
维护与文档成本换不到可观察行为，且 canonical 无测试（§1.1）；② 文档漂移严重：孪生模块头
`bump_spine_iter.rs:62-65` 仍称参考版走 `update_cxt/refresh`（实际 σ）、README §5 称孪生"无燃料池"
（实际 `force.rs:164-181` 有 `UNIFY_FUEL=4096`/`PM_FUEL`）、README §7 测试数 17 vs 静态 21、
FACTS §2 说孪生单文件（已拆 13 子模块）——都发生在 L12 的关键增量处；③ 双引擎可信度在增量面
为零（§4.1）；④ 参考版性能在深负载上无优势（645/522 ms，L07 122/134），无 LSP 接线（lib.rs 只接
L13），hover/completion 无输出；⑤ 维护面：mod.rs 2305 行 + parser 2402 行巨型文件，3 个 `.bak`
~3.6k 行；panic 面（Too much effort/get_global unwrap）以崩代诊断；⑥ `Preprocess` 等字节长重建的
复杂度与 L13 同源，非本层收益。

| 维度 | 分 | 依据 |
|---|---:|---|
| 教学清晰度 | 4 | README 413 行 + 代码注释密度高；扣分在 §7 的四处漂移 |
| 语义健全性 | 3.5 | σ 构造性消除槽漂移；但 panic 面、剔除族、canonical 未验证 |

| 孪生性能 | 5 | 47–85× 大值负载，match 持平，σ 跨轮回收完整 |

**适合当什么用**：σ 路线的**参考实现与教学样本**、L13 机制的**沙盒预演层**、孪生移植的**性能基线**；
