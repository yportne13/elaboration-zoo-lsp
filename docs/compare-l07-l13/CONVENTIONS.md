## 0. 硬约束（务必遵守）

1. **只读分析，不构建**：仓库所在盘剩余空间不到 1 GB，`cargo build/check/test` 会写几 GB 的
   target。**禁止运行任何 cargo 命令**。需要运行程序时只用 `target/release/*.exe` 现有二进制
   （且不要跑耗时 bench，性能数字由 Lead 统一测，避免并发干扰）。
2. **只写自己的文件**：每人只创建/修改分配给自己的那一个 `.md`，不改源码、不改他人文件。
   发现别人的事实错误时写进自己的文件并在 send_message 里告知 Lead。
3. **事实必须可追溯**：每条关键断言带锚点——代码用 `src/.../file.rs:LINE`，文档用 `docs/xx.md §N`
   或 README 的 §N。无法核实的写 `[未核实]`，推断写 `[推断]`。**不要复述 README 就当事实**：
   README 有多处过期（见 FACTS.md §7），至少抽样对照源码。
4. **中文写作**，术语保留英文（NbE / σ / frcs / parity / decl 表 / bump arena…）。Markdown 表格优先。
5. **时间纪律**：单层报告 120–220 行；先读 README 与本层关键源码，再按需 grep，不要逐行通读全部
   15k 行。20 分钟内收口。

## 1. 每层报告的必答清单（八节，顺序固定）

1. **定位与语言特性增量**：本层在链上是"重写 / 增糖 / 再定基 / 生产化"中的哪一种？相对前一层
   新增了什么语言面（语法、类型系统、内建、LSP 面），**丢弃或回归**了什么（时代缺口也算）。
   引 README 与源码两处证据。
2. **代码结构与双实现**：参考版文件布局、孪生（`bump_spine_iter*`）布局；用 FACTS.md 的 LOC 表
   说明规模；指出"单文件巨兽 / 分文件 / 子目录拆分"的形态差异；列出关键模块职责（值表示、
   求值、force、quote、rename、unify、模式编译、elaboration、parser）。
3. **核心机制现状**（逐项给出本层取值 + 锚点）：
   - 精化载体（pm_defs 事实表 / `update_cxt` 改写 / `Subst`+`VSub`+`frcs`+`SpecSolve` 显式替换）；
   - 匹配编译器（决策树矩阵 / 逐臂下钻；覆盖探测是推断级还是值级；嵌套覆盖两段式）与诊断收窄；
   - 全局名字世界（decl 表 / `Infer.global` 哨兵 / 命名空间全限定键）；
   - 依赖类型核心（宇宙、`SumCase.typ`、`Match` 卡住值能否再应用、`struct_eq`/`force` 的重选与记忆化）；
   - trait/typeclass（若有）：求解器共用还是各写、Typ 桥 vs Val 级、outParam、护栏；
   - 内建/prim/副作用（`Tm::Prim` vs decl 表 prim、可变全局、文件 IO、replay、宏）；
   - 防护与健壮性（fuel/`UNIFY_FUEL`/`PM_FUEL`/`MATCH_CMP_BUDGET`、深值迭代化、panic 面、
     UB/别名风险、跨轮回收）。
4. **参考版 vs 孪生版**：两版实现差异（值表示、名字表、记忆化、错误处理、只在一侧存在的机制）；
   parity 套件的判据与已知偏差（span、`?N`、文本归一化、剔除的用例族）；哪些机制**只在参考版**
   （L13 孪生不移植项）或**只在孪生版**。
5. **测试与验收**：lib/黑盒/parity 的**静态**用例数（用 grep 数 `#[test]`，注明未执行）；测试
   强度评价（真覆盖 vs 假阴性，例如单行 enum；大栈线程；`#[ignore]` 探针）；门禁命令。
6. **性能**：本层 bench 负载族与特色负载；参考版 `basic` / 孪生 `fast_ss` / `fast` / `fast_run`
   口径差异；引用最新矩阵数字（注明 2026-09-20 后 HEAD 已有改动）；哪些数字**不可跨层直接比**
   （参考版地板差异、窗口漂移、负载语义不同）。
7. **优劣评估**：优点 ≥3、缺点/风险 ≥3，每条给证据；附"评估卡"表（维度 1–5 分 + 依据）：
   教学清晰度 / 语义健全性 / 参考版性能 / 孪生性能 / 可维护性 / 测试强度 / 生产就绪度。
8. **与相邻层的关系与当前状态**：继承/分叉点；README 声称但代码已不一致处；HEAD（8443586e，
   2026-11-08）后最近的改动是否波及本层；一句话结论（"本层适合当什么用"）。

## 2. 跨层共同关注点（报告里要能支撑 Lead 汇总）

- **重写 vs 继承**：L07 是理论正向重写；L08 是"零新核心机"的糖层；L09 是再定基（换名字世界）；
  L10 加 trait；L11 换 decl 表世界 + 宏；L12 换 trait 求解到 Val 级 + Call/canonical；L13 生产化。
  每一层的"技术选型"是否被下一层延续？哪些是死胡同？
- **精化载体四条路线**：事实表（旧 L07/L08）→ σ 显式替换（L07 定稿并移植 L08–L12）→
  `update_cxt`（L09–L12 旧路、L13 现状）。L13 五轮 σ 迁移失败是重要证据链（见 docs/wip/）。
- **匹配编译器统一史**：L07/L08 一开始就是逐臂；L09–L13 原本决策树，2026-09-18 全部改成逐臂，
  代价是诊断收窄（路径感知覆盖/遮蔽分析弱化）。这属于"全仓统一算法"的收益/代价。
- **双引擎策略的收益/成本**：每层两个实现（参考版 + bump 孪生），parity 为闸门。它带来了
  ~2–10× 的 match 加速、10–800× 的大值负载加速，但也使维护面积翻倍。哪些层收益最大？
- **加固不对称**：2026-11 的 L07 加固轮（P1–P11：occurs 传递、match 比较预算、三档判定、
  span、深 quote/pretty、跨 meta 环守卫、宽松合一收窄）只落在 L07；L08 迁了 P1/P2/P9；
  L09–L13 未迁移。这是当前**层间语义/健壮性差异的最大来源**之一。
- **工程性**：重复代码规模、文档膨胀（每层 README 200–650 行，与代码同步成本）、过期数字、
  `.bak` 文件、调试打印残留、单文件 vs 多文件、已知 UB（Stacked Borrows）、
  panic 而非诊断的缺陷面（如 `Too much effort :(`、文件 IO panic）。
- **给使用者的决策建议**：哪层适合教学、哪层适合当性能基线、哪层是事实上的产品层、迁移/重构
  的优先级（如 L13 是否值得继续 σ 迁移；L09–L13 是否值得回灌 L07 加固；是否应抽公共 crate）。

- 对"优劣"要敢下判断并给代价，不写"各有千秋"式空话；但区分**事实**与**判断**。
- 引用数字必须带口径（哪份文档、哪个 k、basic 还是 fast_run）。
- 报告末尾给"给 Lead 的一句话结论"（≤ 40 字）。
