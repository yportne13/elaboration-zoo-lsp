## 2. [P0·只记录，需主线立项] 孪生 SB 别名 UB：mach_ptr 在位且比 L10-L12 修前扩展

### 2.1 事实

机制与 FINAL.md §3.1 相同：驱动把 `&mut Machine` 解构成不相交字段借用后，回调经裸指针重建整机
`&mut`（或直接 place 读写 `trait_metas`），SB 下存活中的字段借用被弹出，回调返回后继续使用
（`:3876 conv.scratch1 = a1`、`:3931`、循环继续用 spine/stack 等）属 use-after-invalidate。其余
unsafe 块（packed 解码 500-526、'static 槽位 cast、MetaSnap cast、cxt transmute）属正交的存放口径
生命周期改写家族，不构成本问题。

### 2.2 与 L12 形态的差异（为何不能逐字移植）

L12 修法 = 扁平挂起-续跑：3 个 solve 点改写 `solve_req` 信号返回，驱动 `loop { 重新解构字段 →
unify_iter(resume) → 独占 &mut self 跑合成 }`。**L13 孪生的 trait 求解被主线重写**（18-utils 分叉
修复、观察面、压实），新增了 L12 没有的结构：

1. `flex_flex_bump` 的 None-fallback 内联 trait 合成（L12 的 flex_flex_bump 无合成，纯 solve_bump）；
2. `solve_flex_side_bump` 包装（每次 Ok/Stuck solve 后跑合成 + Stuck 约束挂账 `constraints`）；
3. **Call/Call spine 快路径的嵌套 unify_iter**（`:3733/:3762`）+ 三重快照/回滚（metas / trait_metas /
   constraints）——挂起信号会从嵌套帧冒泡，而嵌套帧的续跑状态（子栈 `sub`、快照三元组、`conv_fresh`、
   `cons`）全在栈帧局部。从驱动侧"重放"不可行：合成已改 meta 状态，重跑会把这些变更排除在回滚窗口
   外（语义分叉）；保留帧则需把快照/子栈搬进常驻 UItem 栈（delimited-continuation 重构）。
4. `trait_metas` 字段在循环中途读写（L12 无）。

扁平站点（flex_flex/solve_flex_side 的尾部）本可按 L12 挂起，但**混合协议不可行**：嵌套 unify_iter
挂起返回 false 会被 Call/Call 臂当真实失败处理（触发回滚 + 落退化臂），驱动侧 resume 又会复活已被
回滚的外层栈——状态彻底错乱。因此要么全有要么全无；"全有"= 上述 continuation 重构，超出本轮
"最小外科 + 不动孪生行为语义"约束，且无 Miri 无法验证。

### 2.3 立项建议（给主线）

1. `trait_metas` 参数化（与 `constraints` 同款下传），先消掉 `:3741/:3773` 两处裸读写；
2. 扁平站点按 L12 挂起化；
3. Call/Call 嵌套臂三选一：(a) 臂状态入常驻 UItem 帧（显式但贵）；(b) 实参含 flex 时跳过快路径
   落体比较（行为变更，需 parity 裁决）；(c) 维持现状 + CI Miri 白名单；
4. 终裁：`MIRIFLAGS=-Zmiri-strict-provenance cargo miri test`（与 a4-r1 建议同款）。

### 3.2 主嫌疑：prelude 池交接的 `unsafe impl Send` 依赖未声明的 TLS 析构序

- 位置：`src/L13_namespace/mod.rs:3459-3512`（PoolState SAFETY 论证 + `Drop for PreludeSlot` 推回池）；
  交互方：`FORCE_MEMO`（mod.rs:137，持有 `Rc<Val>` 强引用 keepalive，指向池化状态的共享图节点）与
  `DECLB_CACHE`（mod.rs:997，`Rc<Decl>` 内含共享 `Rc<Val>` 节点）。
- **论证缺口**：SAFETY 注释称"濒死线程在仍持有最后引用时推回池"。但线程退出时 lazy TLS 析构按
  **初始化逆序**运行：若某线程的 FORCE_MEMO/DECLB_CACHE 先于 PRELUDE_CACHE 初始化（即该线程先做过
  不带 prelude 的参考版 elaboration、后用 prelude），则 PRELUDE_CACHE **先**析构（状态入池、解锁、
  可被任意线程取走），FORCE_MEMO **后**析构——其对池化图节点的非原子引用计数递减与取用线程的
  `Rc::clone`（clone_prelude_state/infer.clone 的图共享）**无 happens-before 边**→ 计数漂移 → 过早
  释放 → use-after-free → STATUS_ACCESS_VIOLATION。间歇性（需时间窗重叠 + 漂移向下）、单线程绿
  （-j1 全在主线程串行，无并发取用者）——与症状全吻合。
- **当前触发面核查**：逐个扫描 8 个 crate 内测试模块，**现存测试没有单个 fn 混用"先 plain run 后
  run_with_prelude"**（唯一疑似 legacy_tests.rs:4362 经精确复核为仅 plain run；awk 边界误报源于
  测试源码 raw string 内的 `}`）。故按"初始化逆序"语义**当前不应触发**——但该结论依赖两点未在
  代码中声明的前提：(a) std 对 lazy TLS 析构确为逆序（实现行为而非常量保证）；(b) 未来无任何
  线程（含 LSP worker、未来测试）先摸 force/simpl_decl 再进 prelude 缓存。
  docs/l13-perf-review-4.md §19.5 本身已把"多线程 elaboration 下池的 Send 论证需重新审视"列为遗留。
- **验证配方（协调者可跑）**：
  1. 在 `Drop for PreludeSlot` 推池前插入 `FORCE_MEMO.with(|m| m.borrow_mut().clear());` 与
     `DECLB_CACHE.with(|c| *c.borrow_mut() = None);`（恢复"最后引用"契约）→ 反复 `cargo test`
     若 AV 消失即坐实；
  2. 或临时写一个混合序测试（同 fn 先 `run` 再 `run_with_prelude`）+ 并行 prelude 长测
     （module_probe_tests 类）复现 AV；
  3. 崩溃现场 `RUST_BACKTRACE=1` + Windows WER/cdb 取故障模块栈，确认落在 Rc drop / Val 图访问。
- **修复建议（主线立项，src 内不擅改）**：如上 1 的两行清空进 `Drop for PreludeSlot`（语义中性——
  均为纯缓存），或池交接改 `Arc` 化。本轮按任务规则（src 问题只记录）未改。

### 3.5 排除项（负面结论，供后续排查减负)

- mimalloc：`#[global_allocator]` 声明在 lib/main（未编入这两个集成二进制）→ 系统分配器，无关。
- 巨栈 worker（256MB）：spawn 失败会是 panic 非 AV；输出捕获为 std 线程安全机制。
- 栈溢出假说：深度确定的递归在 -j1（主线程同栈规模）也绿，且症状应为 STATUS_STACK_OVERFLOW 非
  ACCESS_VIOLATION——降级为次要假说。
- T4 的 mach_ptr SB UB：模型级 UB，真实 codegen 下 `(&mut *mach_ptr)` 与字段借用编译为同一指针，
  不构成运行期 AV 机制（与 L10-L12 修前"实践中不崩"一致）。
