## 0. TL;DR

**机制贡献分解（本机，`--only fast`，`med_of_min`，同批交错配对判定）**

| 消融 | 被关掉的机制 | conv | conv_dup | church |
|---|---|---|---|---|
| `L02_NO_BITEQ=1` | 位相等快速路径 + 连续中性链内联环剪枝 | **+102% / +117% / +121%**（k=11/13/15）⇒ **2.02–2.22×** | +7.6% / +8.0% / +8.8% ⇒ 1.08–1.09× | +4.6% / +3.8% / +1.8% ⇒ 1.02–1.05× |
| `L02_NO_CONV_MEMO=1` | conv 工作表判等记忆化 | ≤0.6%，**未判定**（readme「零税」未被推翻） | **+48.2% / +49.4% / +47.6%** ⇒ **1.48–1.49×** | 未测（不触发） |

**三条结论**

1. **conv 今天的速度有一半以上来自 BITEQ+链内环**（关掉后时间翻倍多）。这条轴**接近榨干**：位相等已经把同一句柄/同一立即数的子比较全部 O(1) 剪掉，剩下的只有「结构不同、必须真走」的部分。但反过来说明**这类「用 O(1) 等值判定替代结构比较」的剪枝极值钱**——值得找**同类下一处**（η 展开、闭包体判等、跨 conv 调用共享）。
2. **conv_dup 的收益几乎全部来自判等记忆化**（1.49×）；BITEQ 在该负载只有 8%——因为 conv_dup 的关键子对 `(p_k, add p_k zero)` 两侧**形状不同**，位相等只在叶子/小子项命中，而 memo 把「同一子对比较 3 次」塌缩成 1 次。**哪个负载触发哪个机制**由此可判。
3. **确定性分配计数证明 BITEQ 省的不是「几次比较分支」，而是整段求值**：关掉后 conv k=13 的 arena 高水位 10.0→23.6 MB（2.35×），稳态 churn 从 **295 allocs / 49.5 KB（arena 0 块）** 变成 **484 allocs / 2.58 MB（arena 1.25 MB/轮）**——每轮都新长 arena。memo 关掉后 conv_dup k=15 的 arena 高水位 55.1→87.2 MB（1.58×）。

**方法学结论（本文件 §2，最重要的一条）**：本机 `walt` 有离散档位，**非配对** bootstrap 地板 16–19%（块状漂移）；**严格同批交错 + 配对相对差**的地板 p95 实测 **0.2%–10.6%（中位 ~0.5%）**。判定必须用**同批空对照**逐格作地板；档位刀锋格（本批 1–2 个/工作负载）可达 8–10%，这类格上的 1–6% 效应判不了。四条补救路线（加大 `--rounds`、`scaling_cur_freq` 分层、进程内 k 归一化、总时间配对）经预实验**全部否决或未成立**（§2.5）。

## 1. 开关语义（读码 + 确定性验证）

### 1.1 代码事实（`src/L02_tyck/bump_spine_iter.rs`，`src/**` 只读）

```rust
static NO_BITEQ: LazyLock<AtomicBool> = LazyLock::new(|| AtomicBool::new(
    std::env::var("L02_NO_BITEQ").is_ok_and(|v| v != "0")));          // :591-596
static NO_CONV_MEMO: LazyLock<AtomicBool> = LazyLock::new(|| AtomicBool::new(
    std::env::var("L02_NO_CONV_MEMO").is_ok_and(|v| v != "0")));      // :600-605
// Machine::conv（:909-924）：
let biteq  = !NO_BITEQ.load(Ordering::Relaxed);        // :911
let memo_on = !NO_CONV_MEMO.load(Ordering::Relaxed);   // :912
```

- **不是逐调用 `env::var`**：`LazyLock` 首次使用时读一次并缓存；此后每次 `Machine::conv`
  入口只做一次 `Relaxed` 原子 load。**两臂都执行同一对 load**（`:911-912` 无条件执行），
  所以「默认臂」不会被开关凭空加成本——**task-8 的 A/B 混合因素干净**。
- **`v != "0"` 语义**：变量**存在且值 ≠ `"0"`** 才置真 ⇒ `=1`、`=yes`、**空串**都算「开」；
  未设置或 `=0` 算「关」。
- **只影响性能实现**：`basic` 是 `mod.rs`（参考版），不读这两个开关。

### 1.2 「关掉」是关几处

`NO_BITEQ` 置真 ⇒ `biteq=false`，同时废掉 **4 个决策点**（= readme 所说「两处剪枝」之和）：

| 位置 | 原逻辑 | `biteq=false` 时 |
|---|---|---|
| `:683` 顶层 | `if biteq && t.0 == u.0 { continue }` | 不走位相等，落结构比较 |
| `:784` 链内联环 f | `if !biteq \|\| f1.0 != f2.0 { push Pair(f1,f2) }` | 每个 f 都入工作表 |
| `:789` 链尾同句柄 | `if biteq && a1.0 == a2.0 { break }` | 不再提前收尾，沿 `.a` 继续 |
| `:795` 链内联环 a | `if !biteq \|\| a1.0 != a2.0 { push Pair(a1,a2) }` | 每对 a 都入表 |

`NO_CONV_MEMO` 置真 ⇒ `memo_on=false`：`:686` 查表与 `:710/:726/:742/:753/:772` 五处
`WItem::Store` 写入全部跳过（`FxHashSet` 仍在每次 `conv_iter` 新建，但不再插入）。

**语义不变**：关掉后 `(0,0)` 变量比较有 level 兜底（`:808-812`），链内环在
`biteq=false` 时无条件入栈（`:784`/`:795`）——正确性不依赖快速路径。所有 42×7 个
rep 都通过了 `l02bench` 内建 `assert!(t.bench_check(&raw))`。

### 1.3 确定性验证（`l02l05mem`，计数精确可复现）

`exp-mem-run.sh` 对同一格跑 2 次，**40/40 文件逐字节相同**（确定性）。关键探针
（conv k=13，`fast(one-shot)` / `fast_ss churn`）：

| 环境 | allocs | bytes | churn allocs / bytes |
|---|---|---|---|
| 默认（未设置） | 304 | 10 498 376 | 295 / 49 528 |
| `L02_NO_BITEQ=0` | 305 | 10 498 377 | 295 / 49 528 |
| `L02_NO_BITEQ=`（空串） | 495 | 24 717 616 | 484 / 2 701 680 |
| `L02_NO_BITEQ=1` | 496 | 24 717 617 | 484 / 2 701 680 |

- **`=0` ≡ 默认**（工作路径）：churn / arena 序列完全相同 ⇒ `v != "0"` 语义被钉死。
  多出的 **+1 alloc / +1 B** 恰好是 `std::env::var` 对找到的变量**值** `"0"` 的一次
  String 分配（找不到时无值分配）——**这不只证明 `=0` 不关，还证明变量只被读了一次**
  （若逐 conv 调用读，成本会随 conv 调用数放大）。
- **空串 ≡ `=1`**（工作路径逐项相同）；空串与 `=1` 恰好差 **+1 alloc / +1 B**（k=13：
  495/24 717 616 vs 496/24 717 617；k=15：544/68 306 440 vs 545/68 306 441），
  正是值 `""`（零容量 ⇒ String 不分配）与 `"1"`（1 字节）之差 ⇒ 空串按「开」处理。
- 于是「开着开关的默认臂被加成本」这一担忧**不成立**；无需任何规避措施。

## 2. 消融测量协议（含 walt 档位问题的完整处理）

### 2.1 计时口径

同一二进制 `target/release/l02bench`
（`sha256=28d9884383ef0440d4832bf911b84e0dea067e3ef25b889d223ebcd6f0f5e87a`，mtime 11:21:58）
+ 环境变量；`--only fast`（一次性口径，与 readme 消融数字同口径）；`--rounds 5`；
`--max-k 15`；`taskset -c 7`（Cortex-X2）；`SCHED_IDLE` keep-alive 保频；独占锁
`docs/perf-l02/.benchlock`（协议同 task-6 harness）。判定取 k=11/13/15。

每次取锁为一个「窗口」，窗口内按段跑，**段内严格交错** `A1 B1 A2 B2 …`（21 reps/侧，
每 rep 一个全新进程）：

| 段 | 两侧 | 作用 |
|---|---|---|
| `nullA` | 同 A 臂环境 | 该批地板（含首位效应） |
| `ab` | A 臂 vs B 臂 | 实验 |
| `nullB` | 同 B 臂环境 | B 环境下地板 + 检查「env 传参本身」是否带偏差 |

`exp-ab-run.sh` 另记录每 rep 的 `scaling_cur_freq`（前后各一次）到 `*_freqs.tsv`。
E1/E2/E3 用的是「A 侧恒先」的初版协议（`--order-fixed` 无）、E4/E5/PRE 用**配对顺序奇偶交替**
（pair 2 的 A/B 位置对调，消掉首位系统偏置）——两版都记录在各自 spec 里，效果量级远大于协议差。

### 2.2 预注册与「配对 vs 非配对」更正（本轮最重要的方法学贡献）

结构与「同批交错」等价）算出：

|---|---|---|---|---|---|---|---|
| 9 | 0.000% | 0.000% | 0.000% | 1.70% | 4.84% | 22.0% | 0.00% |

该批序列在 ~1.03 ms 与 ~0.85 ms 两个 `walt` 档位间**块状漂移**（前半/后半差 18.8–19.3%）——
这就是「跨 invocation / 非配对 A-then-B 假阳 ≈19%」的来源。**配对**把同 pair 内共模的档位

> **主判定 = 配对相对差中位数** `md = median_i (B_i−A_i)/A_i`，地板 = 同批 null 段的

> `(median(B)−median(A))/median(A)` 照报（与 task-6 `null_ab.py` 同族）但**不作门槛**，
> 因为它在漂移批上的地板高一个数量级。

> 说明：task-8 任务书写的判定规则是「|<同批空对照 p95> 的差异判未判定」；本文件把「该统计量」
> 明确为配对统计量，并在取数前写入预注册（非事后换指标）。E1/E2/E3 的配对 CI 与
> 同批 null 数字在 `raw/exp-20261006_report.txt` 中逐格可查。

### 2.4 刀锋格（knife-edge）机制

E1 的 conv 序列直接暴露了档位结构：k=11 的值在 **0.384 / 0.460 ms** 两档（差 19.8%）、
k=15 在 **16.4 / 17.9 ms**（差 9%）之间**相邻进程级翻转**，且同一进程内 k=11 与 k=15 可以
落在不同档（所以**进程内归一化无效**）。当约 40% 的 pair 跨档时，配对各差呈现「大正/大负/近零」
三簇，中位数落在零点附近的**刀锋**上——点估计依然无偏（null 段配对中位 −0.2%~+0.9%），
但 bootstrap 重采样可以把中位推到相邻簇 ⇒ p95 抬到 8–10%。这就是 `null_p95_p` 尾部大的原因。

### 2.5 补救路线预实验：四条全部否决/未成立

Lead 指定优先验证的路线 (c)（加大 `--rounds` 让每 rep 的 min 跨过档位边界）与另外三条：

| 路线 | 做法 | 预期 | 实测 | 判定 |
|---|---|---|---|---|
| **(c) 加大 `--rounds`** | 同批内 3 vs 25（PRE1、PRE2，双向顺序） | 双峰塌缩，地板 →0.5% | PRE1：r25 地板 0.218/0.387/0.394，r3 0.651/0.328/0.996 → 看似成立；**PRE2 反序**：r25（第一段）地板 0.654/0.602/**6.873**，r3（末段）0.435/0.885/2.532 | **不成立**：同一协议换段位置就回到 6.9%；地板由**段位置/机器状态**主导，不由 rounds 主导。另注：r25 使 k=15 的 min 系统性 **+8.1%（更慢）**（7.561→8.173 ms），因为 k=15 的测量窗被推到进程更晚、更热的位置；同臂同 rounds 时该项在 A/B 中抵消，但绝对值不可跨 rounds 比 |
| **(b) `scaling_cur_freq` 分层** | 每 rep 前后读频率做档位过滤 | 过滤跨档 pair | 63/63 rep 全为 `2246400 kHz`（E4），**而** PRE2 nullA 21/21 pair 全部「四读数相同」却仍有 6.873% 地板 | **无效**：边界采样测不到进程内/亚 100 ms 的档位变化，不能当档位代理 |
| **(d) 进程内 k 归一化** | double-ratio `(B_k/B_kref)/(A_k/A_kref)` | 消掉进程级乘性档位因子 | E1 nullA k11 地板 10.58→11.57(kref9)/15.30(kref13)；PRE1 nullA k11 0.65→**8.60** | **更差，否决**：噪声含 k 特异分量，归一化把它放大 |
| **(e) 总时间配对** | 每 rep Σ_{k∈{11,13,15}} t(k) 再做配对 | 平均掉单 k 抖动 | E1 nullB 6.28%（vs 单 k 0.31/0.33/8.06）；PRE2 nullA 5.20% | **不改善，否决**：跨 k 存在共模分量，求和保留它 |

### 2.6 本轮实际可达分辨率（给 task-9 的结论）

- **可判**：效应 ≳ 同批 null 地板。本轮的 5 条消融效应 1.8%–121%，全部 > 各自地板，全部判定。
- **1–6% 效应的现实分辨率**：取决于**该批该格**的 null 地板。观察到的地板分布：
  **中位 ~0.5%、多数 ≤1.3%、约 1/4 的格 2–10%**。因此：
  - 同一批 null 地板 ≲1% 时，2–6% 效应**可判**；
  - 地板 2–10% 时，1–6% 效应**注定未判定**，必须**重跑该批**（换时间窗/等机器安静），
    或把判定寄望于别的格（k=13/15 常比 k=11 稳）。
- **正交的零噪声证据**：凡改动涉及分配/容量/哈希税，用 `l02l05mem`（§4）做**确定性**判据；
  纯搬运类改动（C1/C2）的正确预期是**分配计数逐字不变**——这比时间数字更能防「改错地方」。
- 不要用 min-of-N 跨批、不要用「先 A 后 B」、不要用非配对地板判 1–6% 效应。

## 6. 解读：机制贡献分解与剩余空间方向

### 6.1 今天的速度有多少来自这些机制

- **conv**：总时间的 **51–55%** 是 BITEQ+链内环省下来的（1/2.17≈46% 残留为纯结构比较 +
  固定成本）。**conv_dup** 的关键路径是 memo（1/1.49≈67% 残留），BITEQ 只值 8%。
  **church** 只有 ~2–4% 来自 BITEQ。
- 两个机制**服务于不同的重复结构**：位相等服务于「两侧是同一句柄/立即数」的 O(1) 判等；
  判等记忆化服务于「同一昂贵子对在类型里多处重现」。conv 属前者，conv_dup 属后者——
  这就是任务书问的「哪个负载触发哪条剪枝」的答案，且有确定性计数与配对 CI 双重支撑。

### 6.2 由此推出的剩余空间方向（正/反两个推论）

**推论 A（贡献大 ⇒ 该轴接近榨干）**：
- BITEQ 在 conv 上已经删掉一半以上工作量，剩余的是「结构确实不同、必须真走」的比较树。
  **不要再在 conv 上加同类位相等剪枝**（收益上限就是那 46% 残留），也不要把「conv 还能再快 2×」
  当作目标。
- conv_dup 的 memo 命中率已满（3 次→1 次 + 2 次哈希命中）；继续扩大/加深 memo
  （跨 conv 调用、条件化记忆化）在**当前负载结构**下收益上限有限，且 conv 无重复子对
  ⇒ 全局 memo 只会给 conv 加税（readme 的 C3 方向，本轮未做）。

**推论 B（这类剪枝值钱 ⇒ 找同类下一处）**：
- BITEQ 的 2.2× 与 memo 的 1.49× 说明：**把「要结构比较/要重复求值」的地方换成 O(1) 判定，
  是本机目前最值钱的优化形态**。尚未被覆盖的同类位置（审计/消融共同指向）：
  1. **η 展开路径**（`:691-713`）：`(λ, 值)` 每次都新建 `EnvCons` → `eval_iter` → 新 `/ 值`，
     没有「该 η 对已比较过」的记忆化；而 conv 的重复结构里 η 对可能重现。
  2. **跨 conv 调用的共享**：每次 `conv_iter` 都 `FxHashSet::default()` 新建表
     （`Bump::reset` 后键失效是硬约束，但**同一轮内**多次 conv 调用之间的共享表在
     `conv_dup`/依赖类型场景下可能有命中；L03+ 的 `ConvScratch` 是这条路的形态）。
  3. **`ChainRun`/spine push 记账与 `nth`**：这些是残留结构比较的固定成本（readme 画像：
     quote 相 93%、conv 相 99.5%），但已判死过「预分配/小标展开」等轴，不要再碰。
- 反向提示：**不要往「减少比较次数」上找油水**，因为最大的那类比较已经被 O(1) 判等删了；
  剩下的油水更可能在**残留路径的常数**（求值/分配形态，即 C1/C2 一类）与
  **别的相位**（如 quote，但 L02 的 quote 已有 memo 且 readme 已量化为近似中性）。

### 6.3 对 task-9 的直接输入

- C1（`W` 40B→24B）、C2（β/let 尾任务寄存器化）都是**纯数据搬运**：预期效应 1–6%，
  必须按 §2.6 的协议做（同批交错配对 + 同批 null 逐格地板 + 42 对/侧更佳），
  并用 `l02l05mem` 做**分配计数不变性自检**（若变了说明补丁写偏）。
- 消融显示 conv 的残留 46% 里主体是**比较树的求值/分配**（§4.1），而 C1/C2 改的是
  eval 主循环栈流量——两者正交，**不应期待 C1/C2 在 conv 上出现消融量级的效果**；
  若 A/B 显示 >10%，先怀疑协议而不是惊喜。

（配对差为负 = c2 更快；非配对值为 −6.98/−6.49（church）、−7.28/−5.51（conv），与配对同向。）

**该批的特殊之处与排除的伪影**（这是本轮最需要小心的一条）：

1. C2 的 church 窗口里机器**在段内逐步降频**：`scaling_cur_freq` 从 1766400 阶梯降到
   921600 kHz（无他人计时，属 `walt`/热的自主降档）。后果是**段间绝对水平漂移 2.27×**
   （nullA 0.99 ms → ab/nullB 2.06–2.24 ms），非配对地板因此被抬到 52–55%——
   但**配对把共模漂移消掉**，同 batch 的 null 段配对地板仍只有 0.65%/1.36%。
2. **同频平台子集**（两侧四个频率读数都等于 921600 kHz，n=27 pair）：
   church k13 **−6.295%**（base 2.2500 → c2 2.1020）、k15 **−5.909%**（9.2940 → 8.7450）；
   同平台 nullB 地板 0.701%/0.542%。⇒ 在**严格同频**下效应不变。
3. **时间/顺序分割**：前半 −7.162% / 后半 −6.236%；奇数 pair（A 先）−6.295% /
   偶数 pair（B 先）−6.545% ⇒ 不是漂移或首位顺序伪影。
4. **频率分布几乎对称**：A 侧 27 rep@921600 + 1 rep@1766400，B 侧 28 rep@921600；
   A 的分布略偏高频（应略快）却仍慢 6% ⇒ 混杂方向**对效应不利**。
5. **跨树混杂（§10）只有 0.1%**、跨构建差异无法解释 6%。
6. conv 批次的频率也在抖（A 侧 19 rep@787200 + 7 rep@1766400，B 侧 31 rep@787200 +
   5 rep@1766400）：787200 是最低档，**B 侧反而更多地落在最低档**，频率混杂的方向
   使 B 更慢 ⇒ 实测「B 快 7.4%」对该混杂是保守的。
7. 机制：审计预测 2–6%；实测落**上界并略超**（5.7–7.4%）。β 密度主导
   （church β=3n、conv 两侧各 3n），而 L02 的 `cur` 是干净的局部寄存器/栈槽，
   省下的 40B store+load 与一轮 jump-table 分发**没有被 store-forwarding 完全吸收**——
   审计自评「最可能被证伪」的一条在此**未被证伪，反而成立**。

## 13. 正确性复验与确定性分配不变性自检

- **测试**：C1 `cargo test --release --lib L02_tyck` = 27 passed / 0 failed

- **分配不变性**（`l02l05mem --chapter L02 --no-basic`，2 次重复逐字节相同）：

  不随构建差异变化）。
