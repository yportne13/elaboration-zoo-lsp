## 0. 结论

1. **孪生把"每节点一次 malloc"换成"每章一个 bump arena"**：同负载分配次数低
   **2.9–4.7 个数量级**（754×–55,705×），分配字节低 **4.8×–971×**（L05 chain
   参考版 4.52GB vs 孪生 4.65MB）。这是四章性能版内存占用的主结构。
2. **单轮峰值 = arena chunk 链 + Machine 常驻缓冲 + 逐调用草稿**。k=11 常规负载
   每轮总分配 1.5–9.1MB（其中 arena chunk 占 58–92%）；L05 `prune` k=9 34.9MB、
   k=11 143MB（唯一的重负载，`solve/prune` 路径每 let 造 telescope + 掩码）。
3. **稳态（每轮 `Bump::reset`）只保留"最大的一个 chunk"**（bumpalo 3.20.3
   `reset()` 源码语义：释放除当前 chunk 外的全部 chunk，见 §3.2）。故常驻 arena
   = 最大 chunk（1–128MB），∈ [当轮需求, 2×当轮需求]；多数负载第二轮起
   **零 arena 分配**。当"需求 > 保留 chunk"时下一轮会再申请一个 2× 新 chunk
   （一次性，随后稳定）——`conv_dup`/`chain`/`dup_deep` 的 churn 段各见一次 4MB。
4. **逐轮 churn（arena 之外的小分配）**：多数负载 **0–0.16MB/轮**（L03+ 的
   conv/solve/implicit 精确为 0——工作栈全部常驻）；L05 `prune` k=9 **0.73MB/轮
   （22.5k 次分配）**、k=11 **~3MB/轮（90k 次）**，全部来自 solve/prune 路径上
   **每次调用新建的 Vec**（force args、invert 的 lvs/mask、prune_vflex 的 slots、
   lams_from_ty 的 names）。
5. **峰值工作集**（fast_ss，bench `--rounds 50` min of 3）：常规负载
   **2.8–15.2MB**；`chain` 25–35MB（解析树 11.8MB + spine 栈 + 滞留）；L05
   `prune` k=9 **74.1MB**。参考版（basic）同负载 2.9–16.9MB，但 **L05 chain
   k=11 = 1.24GB、L05 prune k=9 = 5.20GB**（参考版 O(n²) 名字解析的既有特性，
   孪生分别是 34.6MB / 74.1MB）。
6. **分配器滞留占峰值 17–53%**：`MIMALLOC_PURGE_DELAY=0` 后 L02 church 5.2→3.7MB、
   L03 conv 7.5→6.2MB、L04 chain 34.2→24.9MB、L05 prune 74.1→34.8MB（−53%）。
   与 `docs/mem-round-2026-09-20.md`（L13，−26%）同源。
7. **quote 记忆化口径（`fast_memo`）在复制负载上把 arena 占用砍 62–68%**：
   `dup` 4.05→1.55MB、`dup_deep` 4.84→1.56MB（输出 DAG 化，逐字节一致）。
   内存优先场景（LSP 常驻）值得把它设为默认档。

## 2. 内存模型（静态）

### 2.1 arena 节点尺寸（字节，实测）

| 类型 | L02 | L03 | L04 | L05 | 备注 |
|---|---|---|---|---|---|
| `Tm` | 48 | 48 | 48 | 48 | `Let` 变体 40B 载荷 + tag（niche 打包进指针） |
| `CloCell` | 32 | 40 | 48 | 48 | name + env + body；L03+ env 含平坦区句柄（16B），L04+ 多 `icit` |
| `PiCell` | 40 | 48 | 56 | 56 | 同上 + dom 值 |
| `EnvCons` | 16 | 16 | 16 | 16 | `V` + next |
| `TCons` | 32 | 32 | 40 | 40 | L04+ 多 `source: bool` |
| `Entry`（spine 槽） | 24 | 24 | 32 | 32 | L04+ 多 `icit` |
| `BdCons` | – | 16 | 16 | – | inserted-meta 掩码链 |
| `PrCons` | – | – | – | 24 | L05 `AppPruning` 掩码链（含 none-run 跳段缓存） |
| `LCons` | – | – | – | 48 | L05 `fresh_meta` telescope 节点 |
| `MetaEntry` | – | 16 | 16 | 16 | `Solved(V,V)` / `Unsolved(V)` |
| `V`（打包值） | 8 | 8 | 8 | 8 | tag 占低 3 位（Lvl/Clo/Spine/U/Pi/Meta） |
| `Env` | 8 | 16 | 16 | 16 | L03+ = flat_base/flat_len + binder 链头 |
| `RenBuf` | – | 56 | 56 | 56 | `Vec<u32>` + `Vec<u64>` + epoch |
| `RenameScratch` | – | 96 | 120 | 120 | 4/5 个 Vec 槽 |
| 判等 memo + 实参草稿 | – | 80 | 80 | 80 | `FxHashSet<(u64,u64)>` 32B + 2 个收集 Vec |

每轮 elaboration 在 arena 里分配的就是上表前七行（+ `alloc_str` 的名字）。
以 L02 `church` k=11 计：nf 输出 2n+4 = 8196 个 `Tm` 节点 × 48B ≈ 384KB，
加上求值期的 `CloCell`/`EnvCons` 与类型树，arena 实用 ~120–130B/输出节点
（chunk 可用量 1MB ÷ 8196）；每轮总分配 1.47MB（arena + Machine 缓冲 + 草稿）。
L02 readme 记的 k=17 全口径 `run`（含类型树 quote）是 ~250B/节点，量级一致。

### 2.2 Machine 常驻缓冲（跨轮保容量）

`Machine::new()` 预分配 `spine`/`vals`/`defs` 各 4096 槽（L05：4096×32B +
4096×8B + 4096×8B = 192KB），其余（`workbuf`/`unifybuf`/`qtasks`/`qdone`/
`rename_pool`/`quote_memo`/`conv.memo`/`ren`）按需扩容。**每轮
`clear_round()` 只清长度不还容量**（L02–L05 无 L13 的 `ReclaimOnClear` 阈值
归还）：稳态常驻 = 历史最大水位。实测这些缓冲在 k=11 常规负载合计 < 1MB
（直方图里 4288B 桶的 5–20 次分配即它们的增长序列）。

### 2.3 键表

`name_map`（`FxHashMap<SmolStr,(u32,V)>`）+ `name_trail`（撤销轨迹）+
`quote_memo`（每次 quote 调用 clear）+ `conv.memo`（判等记忆化）。都是
"内容每轮/每次清空、容量跨调用复用"的口径；`prune` k=11 这类重负载下
`name_map` 约 4k 条目（~0.2MB 量级）。

  **非 chunk 大块**（1/1.5/2/3/4MB）是 Machine 的 `spine` 栈与 hashbrown 表
  扩容（见 §3.5）。

### 3.2 `Bump::reset()` 的真实语义（bumpalo 3.20.3 源码）

```rust
pub fn reset(&mut self) {
    ...
    // Deallocate all chunks except the current one
    let prev_chunk = cur_chunk.as_ref().prev.replace(EMPTY_CHUNK.get());
    dealloc_chunk_list(prev_chunk);
    cur_chunk.as_ref().ptr.set(cur_chunk.cast());   // 手指退回当前 chunk 起点
```

即 reset **释放除当前（最后申请、最大）chunk 外的全部 chunk**，只保留最大块。
推论（实测印证）：

- 稳态常驻 arena = **最大 chunk**，因此 ∈ [当轮需求, 2×当轮需求]（翻倍序列的
  最大块 ≥ 总量的一半）。例：L05 `prune` k=9 当轮 chunk 链 32.12MB、保留 16.06MB；
  k=11 链 134.50MB、保留 64.25MB，随后 churn 轮再申请 128.50MB 并稳定。
- 若当轮需求 > 保留 chunk，下一轮会**再申请一个 2× chunk**（一次性），之后
  保留块足够、零 arena 分配。`conv_dup`/`chain`（保留 2.01MB、需求 ~4.6MB →
  申请 4.02MB）与 `dup_deep`(L02/L03) 的 churn 段即此。
- L02–L05 **没有** L13 的阈值压实（`PRIME_COMPACT_BYTES`，见
  `docs/mem-round-2026-09-20.md` §3）——这些负载的单文件 arena 峰值
  （≤143MB）还没到需要它的量级；但 §6.1 给出了触发条件。

### 3.3 逐轮 churn（arena 之外）

| 族 | churn（每轮，arena 外） | 来源 |
|---|---|---|
| conv / solve / implicit（L03+） | **0 allocs / 0 B** | 工作栈全部常驻、容量已到位 |
| church / dup（L03+） | 13 allocs / 0.12MB | quote/eval 的 `done`/`qtasks` 小增长 |
| church / dup（L02） | 199–227 allocs / 0.16MB | L02 刻意"每调用新建小栈"（见 `Machine` 注：L02 上常驻反而慢 4–13%） |
| conv_dup / chain（L03+） | 0 allocs（arena 外），但首轮 churn 一次性 4MB chunk | §3.2 的翻倍补齐 |
| prune k=9 | **22.5k allocs / ~0.73MB** | solve/prune 路径逐调用新建 Vec |
| prune k=11 | **90k allocs / ~3MB** | 同上（×4） |

`prune` 的 churn 明细（直方图 Top）：64B ×20k、48B ×20k、32B ×12k、16B ×12k、
8B ×16k——即 `force` 的 `args: Vec<(V,Icit)>`、`invert` 的 `lvs`/`mask`、
`prune_vflex` 的 `slots`、`lams_from_ty` 的 `names` 这类**每次调用从
`Vec::new()` 起步**的草稿（L05 `bump_spine_iter.rs` 的 `force`/`intersect`/
`invert`/`prune_vflex`/`lams_from_ty`）。它们是 L05 `prune` 除 arena 外唯一的
可变内存项，也是"单 decl 内 churn"在 L02–L05 的对应物（L13 内存轮 §5 同题）。

### 3.5 `spine` 栈：≥1MB 非 chunk 分配的主要来源

直方图里夹在 chunk 序列间的 1/1.5/2/3/4MB 整块，经
`L02L05MEM_TRACE=1` + `RUST_BACKTRACE=1` 的调用栈定位（release-profiling 构建）
是 **`RawVec<Entry>::grow_one` ← `eval_iter` ← `Spine::push`**（L05
`bump_spine_iter.rs:722`）：中性应用栈按容量倍增跨过 1MB：

| 观测点 | spine 峰值条目 | 块大小 |
|---|---|---|
| L04/L05 `conv_dup` k=11 | 32,768 | 1MiB（32B/槽） |
| L05 `prune` k=11 | 131,072 | 4MiB |
| L02 `conv_dup` k=13 | 65,536 | 1.5MiB（24B/槽） |

L02 readme 已记录"`spine` 预分配 2^18 不值得"（时间中性、常备 6MB）——那是
**时间**轴的结论；内存轴上它意味着深中性负载会瞬时多占 1–4MB，且 `Vec` 倍增
伴随 6–8 次顺序拷贝。轮界 `shrink_to_fit`（若水位波动大）或槽位复用是可选项。

|---|---|---|---|

arena 直接从"逐出现重建"变成"一次构建 + 指针共享"。

## 4. 峰值工作集（OS 口径，MB）

`fast_ss` = 一个 `Tycker` 跨轮 reset（LSP 常驻形态）；`fast` = 每轮新建
`一次性形态`；`basic` = 参考版（含 bench 的 `mem::forget` 预热泄漏，偏大）。

| 负载（k） | fast_ss | fast | basic |
|---|---|---|---|
| church (11) | 2.8–5.3 | 2.8–5.5 | 3.1–6.1 |
| conv (11) | 6.1–7.6 | 6.0–6.7 | 7.3–10.9 |
| conv_dup (11) | 9.1–13.2 | 8.0–10.4 | 9.8–13.7 |
| dup (11) | 7.6–9.4 | 6.7–8.9 | 2.9–3.7 |
| dup_deep (11) | 13.4–15.2 | 11.2–12.4 | 3.5–16.9 |
| solve (11) | 6.2–7.2 | 6.2–6.5 | 13.5–15.4 |
| chain (11) | 25.1(L03) / 34.2–34.6(L04,L05) | 23.2 / 30.8–31.0 | 39.4–53.8 / **1235.7(L05)** |
| implicit (9) | 12.2–12.3 | 11.5 | 14.7 / **98.6(L05)** |
| prune (9) | **74.1(L05)** | 54.8(L05) | **5199.8(L05)** |

区间为 L02–L05 四章的范围。注意：

- `chain`/`prune` 的峰值里**解析树占 11.8–52.5MB**（负载源本身大：`prune` k=11
  的解析 = 52.5MB、k=9 = 13.1MB；`chain` k=11 = 11.8MB），arena 之外还有
  mimalloc 对已释放 chunk 的滞留。
- `basic` 的 L05 `chain`/`prune` 两格是参考版 O(n²) 的既有特性（时间矩阵里
  这两格 basic 也是最慢的），与孪生无关；孪生同格 34.6MB / 74.1MB。
- 空载基线：bench 二进制本身 ~2.5MB（见 `solve` 行的 fast_ss 下界）。

## 5. 与参考版的对比（分配口径）

| 对比 | 中位 | 范围 |
|---|---|---|
| bytes（basic/fast） | 10.5× | 4.82×（L04 dup_deep）– **971×**（L05 chain） |
| allocs（basic/fast） | 7,755× | 754×（L02 church）– **55,705×**（L04 chain） |

孪生的内存优势随负载的"参考版病态程度"增长：名字解析重的 `chain`
（O(n²) `Cxt` 深拷）、每声明重物化 telescope 的 `implicit`、逐层剪枝的
`prune` 都是参考版的内存灾区；纯求值负载（church/dup）只差 5–8×（此时双方
都小，绝对值都在 1–5MB）。

## 6. 问题与建议（按收益排序）

### 6.1 稳态常驻可能达实际需求的 2×（reset 只留最大 chunk）

`Bump::reset()` 保留的是"上一轮最后申请的那块"，它 ≥ 当轮总量一半。对
LSP 这类长驻进程，常驻 arena = 最大 chunk（prune k=11：64→128MB，而实际需求
~127MB）。可选处置（L13 已有先例，见 `docs/mem-round-2026-09-20.md` §3）：

- 轮界按 `Bump::allocated_bytes()` 阈值换新 arena（`Tycker` owns `bump`，
  替换成本低；`clear_round()` 已保证轮界无旧句柄可达——现有 `reset`本身就
  在做半个这件事）；
- 或给 `Tycker` 加"收缩档"：连续 N 轮需求下降超过 50% 时换成小的。

代价是重新增长 chunk 链的分配与拷贝（L13 实测阈值压实 +1.3% 时间换 −10%
活 arena 峰值）；L02–L05 的单文件峰值还没到 L13 prelude 的量级，**默认不动**，
仅建议在内存受限部署留档位。

### 6.2 L05 `prune` 的逐轮 churn（90k allocs / ~3MB @k=11）

solve/prune 路径每次调用新建的 Vec（§3.3）可以常驻化——Machine 里已有成熟
纪律（`workbuf`/`rename_pool` 的 `'static` 存放 + 进核 clear + 归还前清空）。
预计把 L05 `prune` 的每轮分配次数从 22.6k/90k 降到 <100，arena 外的可变内存
项基本清零。属机械改动，但触碰 unify/solve 热路径，需 `l05_fast_parity` +
黑盒三模式全绿。

### 6.3 `spine` 栈水位（1–4MB 瞬时）

§3.5。若接受 6MB 常备可预分配 2^18（L02 readme 已测：时间中性）；否则轮界
按水位 `shrink_to_fit`。优先级低（绝对值小）。

### 6.4 分配器滞留（峰值 17–53%）

`MIMALLOC_PURGE_DELAY=0`：L02 church −29%、L03 conv −17%、L04 chain −27%、
L05 prune −53%。与 L13 内存轮结论一致（交互进程默认不开，内存受限环境用
环境变量）。L02–L05 的 bench 之外，`typort lsp`（默认孪生引擎）同样受益。

### 6.5 `fast_memo` 作为内存优先档

复制负载 arena −62%~−83% 且输出逐字节一致（§3.6）。当前入口只有 bench 口径
（`bench_check_nf_memo`；L02 另有 `run_memo`），LSP/CLI 默认是非 memo 口径。
若目标是低内存，可在 `typort` 加 `--memo` 档或对检测到复制形态的负载自动开启
（线性负载付的哈希税很小，但也不是零）。

### 6.6 每轮 clear 不还容量（与 L13 `ReclaimOnClear` 同族）

`metas`/`defs`/`name_map`/`name_trail`/`quote_memo`/`conv.memo` 每轮清长度、
保容量。L02–L05 的表比 L13 的 `FORCE_MEMO` 小 2–3 个数量级（prune k=11 全量
也就 ~1–2MB），**不需要**阈值归还；但若未来出现"一轮巨型负载把表撑爆、之后
长期小负载"的会话形态，可回灌 L13 的 `1<<18` 阈值方案。
