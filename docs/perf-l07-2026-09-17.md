# L07 性能分析（2026-09-17）

> 口径：本机（6 核 Windows）、隔离进程、每格交错复测取 min。所有计时结论都配
> 了 null 对照（同一实现对撞，见 §1.2，噪声底 0.94–1.02×）与分配计数（确定性、
> 无噪声，见 §4）。原始数据在 `target/l07perf_*.txt`。
>
> 被测对象是**当前工作区**（HEAD `8dabd63` + 未提交的 L07 修复轮）。§3.3 用
> `src/bench_head/`（= 已提交 HEAD）把两者分开了。

## 0. 结论

1. **L07 没有性能塌方，但显式替换重构确实贵了**：模式匹配密集的负载
   （`match` / `enum` / pattern 扫描族）在**全部四个计时口径**上一致回归
   **1.18–1.35×**；非匹配负载（church / natadd）1.00–1.06×。
2. **代价是分配次数，不是算法**：分配次数比与耗时比在 26 个格子上几乎 1:1
   （§4.1）。回归全部是常数因子——比值在 16 倍规模跨度上不漂移（§3.2）。
3. **两个独立的成因，别混为一谈**：
   - **已提交的重构**（`ad08c63`/`bbcf214`/`a5eb72b`）在**无 match** 的源上
     **分配次数与重构前逐位相同**（1.000×，"σ 空则零开销直通"纪律成立），
     它的成本全部落在 match 编译上：`frcs`/`frcs_env` 的 `VSub` 包裹、
     `Subst::extend`、以及深嵌套下的 `Subst::compose`（§4.3）。
   - **未提交的修复轮**（`Tm::Prim` 改零元头 + `add_builtin` 值体改 App 链）
     让每个 builtin 的值多出 2×参数个数个 `Box<Tm>`，而 L07 的 decl 表**每次
     插入都整表深克隆**——于是这份更重的载荷被付了「decl 数」次。它在
     **无 match** 的源上也吃 **+10–23% 分配 / +11–20% 时间**（§4.4）。
4. **最值得动的不是 σ 机制，是 decl 表的写时复制**：同一份 `Rc::make_mut`
   全表克隆也是参考版唯一的超线性项（`strchain` 参考版 2.1 s vs 孪生 3.2 ms，
   约 550×）。载荷改 `Rc` 一处，既抹掉第 3 条的回归，也削掉那 3 个数量级里
   的绝大部分（§5）。**→ 已落地，复测见 §9**：L07/L08 参考版改 `Rc<DeclEntry>`
   条目后，`strchain` k=11 参考版 2120 → 124 ms（**比重构前还快 15×**），
   `match` 2.7×、`enum` 1.8×、`global` 3.3×，无 match 路径分配减少 4–8×；
   σ 侧残留回归（wild/cart/deep 的 1.1–1.35×）不受影响、仍在。
5. **对 `d5-performance.md` 的两处订正**见 §6：①「对照组逐位相同」不成立
   （只有分配计数意义上的 head==pre 成立）；②σ **读**路径（`lookup_hit` /
   `mentions_level` / `frcs` 实参条件包裹）在本仓全部负载上一次都没触发，
   P3-1/P3-7 不该按本轮数据排优先级。

- `fast_memo`（quote 记忆化）在今天这条构建上**没有可测收益**（各格与 `fast`

## 4. 归因：时间去哪了

### 4.1 时间回归 ≈ 分配次数回归

把 26 个格的「分配 × 」与「时间 × 」并排，二者几乎重合：

| 格 | 时间 net × | 分配 run × |
|---|---|---|
| flat 5 / 9 / 17 | 1.24 / 1.21 / 1.18 | 1.24 / 1.19 / 1.12 |
| wild 5 / 7 / 9 / 11 | 1.26 / 1.24 / 1.30 / 1.31 | 1.24 / 1.22 / 1.22 / 1.23 |
| cart 16 / 64 / 256 / 1024 臂 | 1.30 / 1.31 / 1.31 / 1.35 | 1.27 / 1.27 / 1.30 / 1.33 |
| deep 16 / 32 / 64 / 128 | 1.14 / 1.19 / 1.20 / 1.20 | 1.19 / 1.20 / 1.20 / 1.21 |

**解析（parse）侧的分配逐位相同（比值 1.000，全部 15 格）**，所以差量 100%
来自推导（elaboration）。这条同时验证了计数器本身可信。

### 4.2 大小直方图：三张面孔

`l07alloc --hist`（size<256 逐字节精确；`size_of::<Val>() = size_of::<Tm>() = 88`，
`size_of::<Subst>() = 8`，Rc 头 16B）：

| 场景 | 净增最大的桶 | 判读 |
|---|---|---|
| **无 match 对照** | 只有 `size = 88` | 单一新分配点：`Box<Val>` 或 `Box<Tm>` |
| match 负载（cart 1024 臂） | `88` +266486、`120` +69632、`24` +11265 | `Box<Val>` / `Box<Tm>`；`Rc<SubEntry>`（104+16）；`Rc<Subst>`（8+16） |
| deep d=128 | `120` +33671、`88` +21494、`56`/`168` 各 +16.2k | σ 链条目 + 包裹 |

`cart` 的**字节数**比次数涨得更快（cart-1024：次数 1.33× 而字节 1.57×）——
说明每个分配的平均尺寸也变大了，这正是「包裹叠包裹」（`VSub` 里套 `VSub`）
的指纹。

### 4.3 match 侧：σ 的构造与组合（已提交的重构）

`l07whoalloc`（把指定大小的分配的**调用栈**抓下来符号化）在 `impl=head` 上：

```
# cart n=8（1024 臂形态），size=88（Box<Val>/Box<Tm>）
pre = 25012      head = 66042（2.64×）
head 的头部调用点：
   8448  Compiler::walk_con  <- Compiler::compile <- Infer::check
   7424  Infer::frcs        <- Infer::force     <- Compiler::walk_con
   5376  Infer::closure_apply <- Compiler::walk_con
   5376  Infer::frcs_env    <- Infer::frcs      <- Infer::force

# deep n=64，size=120（Rc<SubEntry>）
pre = 849        head = 9496（11.2×）
   7688（81%）Subst::compose::cons_all  <-  Subst::compose::cons_all  <- …
```

对照 §3.2 的净值：**cart 贵在「每臂都会付」的 `frcs` / `frcs_env` 包裹**
（`Val::VSub(Box::new(v), σ)` 每个 88B），**deep 贵在 `compose` 逐条目
cons**（`Subst::compose` 为外层每条目新建一个 `Rc<SubEntry>`，120B）。

另一个值得记的**否定结果**：这些负载里 `lookup_hit` / `mentions_level` /
`frcs` 的 spine-实参包裹**一次都没进热点**（栈聚合里看不到 `lookup_hit`；
一次性计数器实验在四族负载上全部为 0 命中）。也就是说 σ 的**读**路径
（`d5` 的 P3-1 / P3-7 想去优化的那两处）不是本轮成本的来源，成本在
**构造**（`extend`）与**包裹**（`frcs`/`frcs_env`）与**组合**（`compose`）。

### 4.4 无 match 侧：decl 表写时复制 × builtin 变重（未提交的修复轮）

栈归因（`--imp cur --ctrl --size 88`）：多出来的 88B 分配全部落在
**decl 表的整表克隆**里——

```
Cxt::decl_insert -> Rc::make_mut -> HashMap::clone -> Val::clone(嵌套) -> alloc(88)
```

`Rc::make_mut` 在引用计数 >1 时**深拷贝整张 `HashMap<SmolStr, DeclEntry>`**，
包括每个条目的值。而工作区那轮把 builtin 的值从「λ 链 → `Tm::Prim`」改成
「λ 链 → `((Prim 名 p1) p2 …)` App 链」（`cxt.rs` `add_builtin`，为零元头的
spine 保真修复），于是每个 builtin 值多出 `2 × 参数个数` 个 `Box<Tm>`（88B），
每次整表克隆都要重新克隆一遍。L07 有 15 个 builtin、参数合计 29（`cxt.rs`
逐一可数），即每次整表克隆多 58 个 `Box<Tm>`；`flat_ctrl(17)` 实测 +2944，
对应数十次整表克隆，与该源的 decl 插入次数同量级。

三条互相独立的证据把成因钉在这一点上：

1. `head == pre` 逐位相同（§3.3）⇒ 与已提交的重构无关；
2. 差量随 **decl 表规模**走：flat 随枚举变大而增长（+1648/+2080/+2944 @ n=5/9/17），
   cart/wild/deep 的枚举固定则差量为常数（+1162 / +1108 / +1216）；
3. 栈归因指向 decl 表的 `make_mut` 深克隆，而唯一让 decl 条目变重的未提交改动
   就是 `add_builtin` 的 App 链（按排除法：其余未提交 hunk 分别落在 frcs λ 守卫、
   文件 IO 降级、错误文案、twin 私有——都不在无 match 源上执行）。

**这不是 bug，是「正确性修复 + 既有 O(n²) 语义」的乘积**：App 链是必要的
（零元 `Tm::Prim` 头的 spine 保真），放大器是 decl 表的全表深克隆。

## 5. 该动哪里（按性价比）

1. **【高】decl 表条目改 `Rc`，去掉整表深克隆**（`cxt.rs` `decl: HashMap<_, DeclEntry>`
   → `HashMap<_, Rc<DeclEntry>>`，或至少值侧 `Rc<Val>`）。一次改动同时拿到：
   - 抹掉 §4.4 的**无 match 源 +10–23% 分配 / +11–20% 时间**（当前工作区的
     唯一新回归）；
   - 削掉参考版唯一的**超线性项**——`strchain` 参考版 2.1 s vs 孪生 3.2 ms
     （545×）、`global` 61× 的主体；
   - 注意这条**不是**本轮重构引入的欠债（`bench-matrix` 已把 strchain/global
     参考版超线性登记为已知取舍），但本轮的 App 链载荷把它的日账面放大了。
   **→ 已落地（L07 + L08），实际范围比预估窄**：六层里只有 L07/L08 是
   "深值载荷 + 写时复制"，L11–L13 的值本来就是 `Rc` 元组、L09/L10 不用
   decl 表。复测见 §9。
2. **【中】别按本轮数据去优化 σ 读路径**。`d5-performance.md` 的 P3-1
   （`lookup_hit` 记忆化）与 P3-7（frcs spine 实参条件包裹）在四族负载上
   命中为 0（§4.3）。它们值得做的前提是「有负载真的命中读点」——先补一个
   让 `Rigid` 读点热的负载（例如把 `d5` P2-4 建议的深嵌套 + 多方程 σ 链
   固化进 bench），再谈收益排序。
3. **【中】`compose` 的 O(|outer|) 条目克隆**（deep 占 81% 的 120B 分配）。
   设计文档已把「compose 不物化」记为表示取舍；要收只能靠单链加链尾指针
   或按 `(x, σ 指针)` 给组合结果做 memo。优先级低于第 1 条：它的绝对量在
   d=128 时也才 8320 次/单次 run。
4. **【低】`match` 的 1.2× 本身**。孪生版绝对量 +7 µs（k=11），远在 1.5× 验收线
   内；它由第 1 条之外的 σ 构造/包裹成本构成，收益小、动的是刚评审过的热路径。

## 6. 文档订正（相对 `docs/perf-ab-l07l12-2026-09-16.md` / `d5-performance.md`）

- **`perf-ab` §3.5 的「对照组 pre/post 逐位相同」不成立**。正确形式是：
  **分配计数**意义上 `head == pre`（§3.3，逐位相同 ×4），而**计时**意义上对照组
  回归 1.12–1.20×（§3.2）。原文那个「0.346 vs 0.346 ms」在计时口径下更像是
  同一实现的两次采样（本轮 null 对照本就有 0.98–1.02 的散布）。因此
  §3.5「开销只落在模式匹配编译上」的结论需要改成：**已提交的重构**确实只落在
  match 编译上，但**工作区**另有一份与 match 无关的 decl 表开销（§4.4）。
- **`d5` 的 P3-1 / P3-7 优先级下调**（依据见 §4.3 的否定结果）。
- `d5` §3 的 needs-verify #1（「用自绘分配计数器量 force/frcs 每调用 Vec 的占比」）
  本轮部分落地：`src/bin/l07alloc.rs`（确定性分配计数 + 大小直方图）与
  `src/bin/l07whoalloc.rs`（指定大小分配的调用栈归因）就是那个计数器。
  force/frcs 的 per-call Vec 未单独计数，但 §4.2 的直方图里没有出现对应规模的
  新桶，暂不认为是主项。

## 8. 不确定与边界

- 全部计时在 6 核 Windows 上，单次单轮抖动可达 ±25%（本轮见过一次 65% 离群）；
  ≥1.10× 的结论都做了交错复测，但绝对量在亚毫秒格上只有几微秒量级。
- **整机在长会话里会整体变慢**：本次会话后段（连跑编译 + 测试数小时后）同一份
  未改动代码的绝对耗时比前段高约 40%（如孪生 `strchain` k=11 前段 3.16 ms、
  后段 4.5 ms，两个二进制各自都是）。故本文只用**同一时间窗内交错**得到的
  比值，跨时间窗的绝对值不可比。
- `enum` 负载是固定源（k 无关），`cart` 的 1024 臂是合成极端形态；真实源码的
  match 臂数多在十位量级，对应 §3.2 的 flat/wild 行（1.2–1.3×）。
- 分配计数不含释放侧成本；`cart` 的字节增幅大于次数增幅（1.57× vs 1.33×），
  说明还有一部分代价是「更大的克隆」，未单独归因。
- `d5` 的 P2-2（L09/L10 quote 整 `Infer::clone()`）、P2-3（force 卡住 match
  深拷贝 scrutinee）、P3-6（meta 快照）本轮**未测**（不在 L07 参考版热路径或
  未被现有负载触发）。
- 「孪生版 10–15× 快」是 bench 口径（含两侧建表）；LSP 实际路径的开销结构
  未在本文覆盖。

## 9. 修复落地与复测（2026-09-17 当日）

### 9.1 改了什么

按 §5 第 1 条：参考版 decl 表的**条目**改为 `Rc` 共享，写时复制的表克隆从
"逐条深拷贝值" 降为 "重建哈希桶 + 逐条 Rc 递增"。

| 文件 | 改动 |
|---|---|
| `src/L07_sum_type/cxt.rs` | `Decls = HashMap<SmolStr, Rc<DeclEntry>>`；`decl_insert` 包 `Rc::new`（签名不变，调用点零改动）；`decl_get` 加 `.map(\|e\| &**e)` 保持返回类型不变 |
| `src/L07_sum_type/mod.rs` | `simpl_decl` 构建 `Rc<DeclEntry>` |
| `src/L08_product_type/` | 同款三处 |

**语义不变**的论证：`DeclEntry` 构造后无处被 `&mut`（全仓 `decl` 上的可变访问
只有 `Rc::make_mut` 的插入），条目只读共享 ⇒ 无新增别名可观测性；表仍是写时
复制，"占位只对本定义的检查可见"的纪律原样保留（与孪生版平铺覆盖的等价性仍由
`l07_fast_parity` 的 66 例把守）。

**传播范围**：只有 L07/L08 是"深层值载荷 + 写时复制"的形态。L11–L13 的
`Decl` 值本来就是 `Rc<Tm>/Rc<Val>/Rc<Ty>` 元组（克隆已经浅），L09/L10 用的是
`global: HashMap<Lvl, VTy>`（非写时复制，代价在 `Infer::clone()`，是 `d5` P2-2
的另一条线），故本轮不动。
