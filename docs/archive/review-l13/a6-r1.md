### [P0] 命名片段（`MacroFragment::Name`）在**匹配阶段**递归，完全不受 `MacroDepthGuard` 约束 → 用户两行源码可栈溢出（LSP 挂/崩）

- 位置：`src/L13_namespace/parser/macros.rs:82-145`（修复前为 `:82-125`，守卫点 `src/L13_namespace/parser/mod.rs:1598/1939/3500`）
- 证据：
  - `parse_fragment_kind`（mod.rs:2302-2327）把**任何**非内建标识符都变成 `MacroFragment::Name(span)`，所以 `macro_rules Loop { ($x: Loop) => { $x } }` 里 `$x` 的片段就是宏 `Loop` 自己。
  - `MacroFragment::Name` 臂（修复前 macros.rs:82）在 `state.1.get(&mname.data)` 后对**该宏每条规则**做
    `m.matcher.to_parser().parse(input, state)`；当规则匹配器自身以同名片段开头时，这一步在**同一 token 位置**再次进入同一臂 ⇒ 输入零消费的无限递归。
  - 三个 enter 点都在"转写后 re-lex + re-parse"路径上（1598/1939/3500），而这里是**匹配阶段**、早于任何 re-parse，所以一个守卫都不覆盖。`MacroMatcher::Many0/Many1` 的零消费保护（macros.rs:175 及同款 Many1 分支的 `i.len() < rest.len()`）也管不到它（递归发生在匹配器内部）。
  - 已存在的自递归钉子 `tests/l13_fast_parity.rs:358-377` 用的是 `macro_rules m { () => { m } }`（**转写器**自递归，走 1598 守卫），与这条路径无关。
- 机制/影响：触发面是 LSP 的常规路径——`didOpen` 的任意文档文本经 `lib.rs:1810/2386/2670 → preprocess → parser_with_macros`。
  最小复现（2 行）：
  ```
  macro_rules Loop { ($x: Loop) => { $x } }
  def f = Loop 1
  ```
  解析 `def f = ...` 的 body 时 `p_raw`（mod.rs:1533 起；宏派发 `if let Some(macro_decl)` 在 :1534）派发宏 `Loop` → 匹配器 → Name 臂 → 无限递归 → 栈溢出（Windows 上即 `STATUS_ACCESS_VIOLATION`），整机进程随编辑器会话一起死。
  互相递归（`A -> B -> A`）同理。**注意**：仓库内 prelude 的所有命名片段（`Expr`/`VExpr`）都出现在匹配器**非首位**（例如 hdl-verilog-compat.typort:367 的 `always @ (...) begin $( $s: VExpr )* end`），所以存量测试全绿；这条只在用户自定义宏上触发。
- 处置：**已修（最小 diff）**。在 Name 臂入口共享同一 thread-local 守卫；触顶时**既 push 诊断又返回 Err**——因为该臂的调用方（`p_raw` mod.rs:1536、`p_decl` mod.rs:3453/3461）用 `if let Ok(..)` **吞掉**匹配器错误，只返回 Err 会让宏调用静默退化成"标识符应用"（正是 BRIEF 说的"静默截断"）。上限沿用 256（合法片段嵌套深度是个位数）。
  钉子：`tests/parser_error_tests.rs:1646-1694`（自递归 + 互递归，8MB 线程内 parse，只回传可 Send 的错误文本；断言含 `macro expansion too deep`）。

### [P1] 宏转写器 brace 分支长度下溢 → 畸形宏定义可 panic（debug 下溢 / release 切片越界）

- 位置：`src/L13_namespace/parser/mod.rs:2543`（修复前；修后 :2552）
- 证据：`let len = i_back.len() - input.len() - 1 - need_remove_endline;`
  - 不变量只有 `i_back.len() >= input.len()`（`i_back` 只在 2537 移动到 `input` 已到达的位置）；末尾 `- 1` 表示"尚未消费的 `}`"，**没有**下界保护。
  - 当循环在消费任何 body token **之前**因 2523 行的 `(kw(RParen), kw_is(Op, "*"))` 命中而 break 时，差值为 0。
  - 触发用例（宏定义本身畸形即可，不需要任何调用）：
    ```
    macro_rules m { () => { $({)* } }
    ```
    轨迹：`p_macro_transcriber_single`（mod.rs:2465 起）吃掉 `{` → :2525 行匹配 `$(` → 递归进入内层 `p_macro_transcriber_single`（:2534）→ 内层吃掉 `{` 后立刻在 `) *` 上命中 :2523 的 break，此时内层 `i_back == input` ⇒ `0 - 1`。
  - debug：`attempt to subtract with overflow` panic；release（无 overflow-checks）：`len = usize::MAX` ⇒ `i_back[..len]` → `range end index out of range` panic。两者都是**用户源码可触发的 panic**，而 LSP 每次按键都会重解析（含只输入了一半的宏定义）。
- 机制/影响：编辑器里"正在输入宏定义"是最常见状态；panic 发生在解析器内部，会把 LSP 请求线程打断（不是 UB，但属 BRIEF P1"可达 panic"）。
- 处置：**已修（最小 diff）**：`i_back.len().saturating_sub(input.len() + 1 + need_remove_endline)`。
  对 `d >= 1+nre` 的原有路径**逐位等价**（`d` = 差值），只在原先 panic 的场景返回 `len = 0`（空 token 串）。
  钉子：`tests/parser_error_tests.rs:1710-1735`——触发用例 + 该定义的**所有字节前缀**（模拟逐键输入）都只要求 `parser(..)` 返回 `Some`（不 panic）。
  L11/L12 同名拷贝仍带此缺陷 → §4。

### [P3] 自带 stable `Pattern` 的闭包臂 `strip_prefix_of` 违背 std 语义（`is(closure)` 恒成功）

- 位置：`src/parser_lib.rs:42-62`（同一个 `impl Pattern for F` 块；修复前同样 42 起）

   "impl IMasterSlave for `X` requires `#[derive(Bundle)]` on the struct" **假错**。树内无 `#[derive(Bundle)] class` 用例（grep 全仓 0 命中），需一个最小用例定案。

## 5. 设计决定讨论（不属 bug，只记录）

1. **`or_far` 的"最远失败优先"与"keep-first at equal progress"**：机制本身是 chumsky/PEG 的常规做法，且 L13 的备选链几乎全在同一 token 上失败（进度相等 ⇒ 保留第一支），所以本轮行为变化集中在文案。真正值得记录的语义代价有两条：
   (a) `parse_progress() = msg.start_offset`，而 `empty_span` 生成的错误 offset 为 0 —— 与"文件第一个 token 上失败"不可区分，且无 path_id 参与比较（跨文件错误若同处一条链会被误比；当前 L13 单次 parse 只涉及一个文件的 token，暂不可触发）；
   (b) `or_far` **不**回滚 `state`：第一支失败前 push 的诊断/宏展开记录会保留（与旧 `or` 相同，是既有语义）。真正"第一支失败更深 + 第二支也失败"时，`or_far` 会让用户看到第一支的错误，而第二支（历史上"最后尝试"）的诊断同时也已经进了 `state` —— 语义正确，但可能一条输入报两条不同来源的错误。
2. **`BiMap::insert` 不保持两侧互逆**（`src/bimap.rs:37-40`）：`map2.insert(k2,v)` + `map1.insert(k1,k2)`，同名 key1 二次插入会留下 map2 孤儿 ⇒ `len()`（= map1 计数）与 `values().count()`（= map2 计数）可不等，`get_by_key2` 可能返回陈旧值。**本仓是刻意如此**：`L13_namespace/cxt.rs:1373` 的 `src_names.get_by_key2_mut(&Lvl(..))` 依赖 map2 的"层级持久"（同一名字在多个层级都要能按 level 查到），且 doc（bimap.rs:3-6）已说明迭代用途只有内存画像。建议只在 `insert` 上补一行注释说明"map1 精确、map2 持久超集"，不改行为。
3. **`MacroFragment::Name` 与转写器共用 `MAX_MACRO_EXPANSION_DEPTH = 256`**：两者语义不同（一个是片段组合链，一个是展开嵌套），但都在"宏嵌套"维度上、都远小于 256，共用可避免再加一个 thread-local。若后续出现"合法程序触及 256"的实测案例，再拆成两个独立计数。
4. **`p_expr_block_stmt` / `p_def_stmt_block` 的 temp_state 隔离**（mod.rs:1603、1943、3515）：re-parse 用 `(vec![], state.1.clone(), vec![])` 隔离错误与展开记录，成功后才并回 —— 这保证了"匹配尝试的副作用不外泄"，但也意味着失败路径的 `temp_state` 诊断被丢弃。与 `or_far` 的"备选错误只在全部失败时浮出"是同一设计取向，记录备查。
