### 2.1 `XCell`/`CloCell` `#[repr(align(8))]` + 编译期断言是否改变 64 位布局 —— 否
- 位置：`src/L07_sum_type/bump_spine_iter.rs:265/390/412-415`、
  `src/L09_mltt/bump_spine_iter.rs:270/405/429-432`（同款）。
- 证据：
  - `XCell` 变体含 `Obj { val: V }` / `SumCase { typ: V }` / `Match { scrutinee: V }`，
    `V` 是 `u64` 包装 ⇒ 64 位下 `align_of == 8` **本就成立**（L07 `:273/282/289`，
    L09 `:294/...`)。
  - `CloCell` 无 `u64` 字段，但含 `&str`、`&Tm`、`Env`（`Env` 含 `Option<&EnvCons>` 指针）
    ⇒ 64 位下 `align_of == 8`。
  - `#[repr(align(8))]` 对一个**已经是 8 对齐**的类型是 layout 恒等变换：size、字段偏移、
    枚举判别式布局均不变；`const assert!(align_of::<T>() >= 8)` 在 64 位是编译期恒真。
- 结论：**64 位零行为变化**，wasm32 上把 `& !7` 解码所需的低 3 位为 0 钉死。正确。
- `CloCell` 的 repr 确认到位（A3 第 2 轮补，`L07:390`、`L09:405`）。

### 2.3 `lvl2ix`/`rename`/快版 6 处 `>= GLOBAL_BASE` 边界统一 —— 对既有 `global_idx>=1` 行为不变

  `elaboration.rs:289/374`）⇒ 0 号全局层级**恰为** `1919810`；eval 以
  `x - 1919810` 取表（`mod.rs:294`）、快版 `*i >= GLOBAL_BASE`（`:888/997`）。
