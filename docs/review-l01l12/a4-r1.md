### [P0] 快版 `unify_iter` 回调 `(&mut *mach_ptr)` 与已借出的字段引用别名（Stacked Borrows UB）
- 位置：`src/L10_typeclass/bump_spine_iter.rs:3705-3737`（取 `mach_ptr` 并解构字段），
  回调点在 `:2198-2200`、`:2313-2315`、`:2336-2338`。
- 证据：
  ```rust
  let mach_ptr: *mut Machine = self;            // 3707
  let Machine { spine, vals, icits, defs, metas, globals, ren, conv,
                unify_work, unify_stack, .. } = self;   // 3709-3721 字段 &mut 借出
  ...
  unify_iter(bump, spine, work, stack, ..., mach_ptr, trait_err)   // 3734
  ```
  `unify_iter` 内部在字段引用仍存活时执行
  `let tr = unsafe { (&mut *mach_ptr).solve_multi_trait_ref(bump, cxt, mv) };`，
  而 `solve_multi_trait_ref`/`solve_trait_ref` 以 `&mut self` 重新借用整台 `Machine`
  （`bump_spine_iter.rs:3742-3766`，内含 `let Machine { spine, defs, metas, globals, .. } = self;`
  的整机重借）。返回值后 `unify_iter` 继续使用 `work`/`stack`/`vals`/`conv` 等引用
  （如 `conv.scratch1 = args; continue;`）。
- 机制/影响：从 `&mut self` 派生裸指针后再经 `self` 解构字段，随后又经裸指针构造整机
  `&mut`——按 Stacked Borrows，中间对 `self` 的字段重借会使先取的 `mach_ptr` 失效，
  后续 `&mut *mach_ptr` 属 use-after-invalidate，是语言级 UB（当前 rustc 未必误编译，
  Miri 很可能报警）。`:3730-3733` 注释声称"字段已按不相交集合借出"，但被回调方法重借的
  恰恰是同一批字段，该不变式描述不成立。
- 处置：仅报告，needs-verify（需 Miri 确认）。修复需把回调改成"不跨借出重入"的形态
  （例如调用前后重建字段引用），属较大重构，超出最小 diff 范围。

### [P1] `Synth::unify` 无 occurs check + 双向合一 + 原始 level 混用 → 可能选出错误实例
- 位置：`src/L10_typeclass/typeclass.rs:366-397`（`// Occurs check omitted for simplicity` 在 `:378`）。
- 证据 / 机制：`unify` 把 `Typ::Var(i)` 与任意 `t2` 直接记入 `subst.insert(*i, t2)`，且对
  `(_, Typ::Var(i))` 也反向记入；`Typ::Var(lvl)` 里的 `lvl` 是**裸 de Bruijn level**，
  不同声明的 level 空间相同。静态可推的假匹配：
  ```text
  trait Say { def say: String }
  enum List[A] { nil  cons(head: A, tail: List[A]) }
  impl[T] Say for List[T] { def say: String = "list" }
  def f[T](x: T): String = x.say
  ```
  - `impl[T] Say for List[T]` 登记断言 `Say[Construct("List",[Var(0)])]`
    （`elaboration.rs:462-490`，`T` 在 lvl 0）。
  - `x.say`：receiver `x: T`，类型 `Rigid(0)` → `Typ::Var(0)`（`trait_wrap` `args[0]=typ`，
    `elaboration.rs:828-849`）。
  - `try_resolve` 走 `unify(Var(0), Construct("List",[Var(0)]))`：无 occurs check ⇒
    `subst[0]=List[Var(0)]` 返回 true ⇒ 泛型 `T` 被"匹配"成 `List`，选中 List 实例。
  - 该 substitution 也自引用（`Var(0)` 出现在值内）；后续再比较 `Var(0)` 会令
    `apply_subst_to_typ` 每轮多展开一层，理论上可发散（栈溢出）。
- 旁证：L12/L13 的 `typeclass.rs` 已把这套双向 `unify` 重写成单向一阶匹配
  `val_match`（`src/L12_canonical/typeclass.rs:121-170`），并对重复变量用
  `vals_eq_ground` 校验——即后续层认定旧版是错的；L10/L11 是未跟进的旧拷贝。
- 处置：仅报告，needs-verify（最终可观测量是"错结果"还是"错误地 Err"未运行无法定论；
  但求解器返回了错误答案已成立）。修复为匹配语义重写，超出最小 diff，且 L11 同码需协同。

## 5. 设计决定讨论（不属 bug，只记录）

- **`Synth` 的实例依赖恒空**：L10 未实现 `where` 约束/超 trait，`Instance.dependencies`

  比较/代换，是上面 P1 假匹配的根因。L12/L13 改为单向 `val_match` 后语义更清晰，建议 L10
  按同路线收敛（属行为变更，需独立验证）。

  parity 契约锁定；是否统一属跨层显示决策，非缺陷。
