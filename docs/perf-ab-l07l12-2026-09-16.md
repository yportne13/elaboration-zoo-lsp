> 目的：验证 L07–L12「精化载体 → 显式替换」（2026-09-15 的 `ad08c63` /
> `8931d78` / `efa47b9` / `ad412ab` / `ccfcb87` / `2129975` / `58073dd`）

## 0. 结论

1. **总体无回归**：42 个单元格的同机 A/B，basic 列几何均值 **0.969×**、
   fast 列 **1.000×**；35 个落在 ±10% 以内。
2. **本文实测与文档 §4 存档一致**（几何均值 basic 1.012× / fast 1.002×），
   说明 §4 的表可作为重构前基线使用，机器间可比。
3. **确证的显著变化**只有四处（§3），其中两处是收益、两处是 7–26% 的
   小幅回归；其余差异经交错复测判定为噪声。
4. **L10 `enum` 单元格**前后都不可测，但失败形态从"栈溢出/挂死"变成了
   "孪生 check 有界返回 false"。定位实验证明**发散在孪生版**，参考版从未
   跑到该步骤——`bench-matrix §4` 把它归因为"参考版栈溢出"是**误归因**。
   这不是重构引入的回归（见 §5）。

## 1. 方法

**同机同会话 A/B（主证据）**。仓库里 `target/release/l0{7..12}bench.exe`
的构建时间是 2026-09-14 23:57–23:58，早于 09-15 的重构提交，因此**重构前的
二进制仍在**。直接备份为 `target/pre_refactor_bins/`，再用 HEAD 源码构建
一份到 `target/post_refactor_bins/`，两者跑完全相同的命令。

- 六个 bench 的**驱动源码自 09-12/09-13 起未再改动**（`git log` 核过），
  所以 A/B 的唯一变量就是被测的层模块本身。
- 口径对齐 §4：隔离进程、`--max-k 11`（`enum` / `traitchain` 按各 bench
  固有规模取 k=9）、`--rounds 3`（`traitchain` 1 轮），取每行 min。
- L11/L12 的 `--only fast` 是孪生 bare 口径，而 §4 的 fast 列用的是孪生
  **全流程** `fast_run`；对照文档时另补跑了 `--only fast_run`。

**噪声控制**。单次 min 的抖动可达 ±25%（同一二进制重跑即可见）。凡
A/B 比值偏离 1±0.10 的单元格，一律再做**交错复测**：pre/post 交替、每轮
`--rounds 9`（重负载 5）、共 3 轮，取全部轮次的最小值。复测否掉了绝大多数
"回归"（例：L08 church basic 首测 1.41×，复测 1.01×；L12 strchain fast
首测 2.08×，复测 1.06×）。

## 3. 确证的四项变化

### 3.1 L09 参考版 match / enum 快约 2×（收益）

| 负载 | pre | post |
|---|---|---|
| match（k=11） | 4.437 ms | **2.213 ms**（0.50×） |
| enum（k=9） | 27.721 ms | **13.194 ms**（0.48×） |

两者都被交错复测确认（0.50× / 0.49×）。机制上说得通：enum / match 正是
依赖匹配最重的负载，L09 原来每次精化走 `unify_pm` + `Cxt::update_cxt`
（改写 env 槽 + `refresh` 全量重引用），换成显式替换后这步退化为 O(1) 的
σ 叠加。与 `explicit-subst-refactor-status.md` §2 记的"L09 bench
≤1.24×（match/enum 变快）"同向。

### 3.2 L07/L08 孪生 match 慢 24–26%（已知偏差）

`fast` 列 0.038 ms → 0.047/0.048 ms，**绝对量 +9~10 µs**。首测与交错复测
一致（1.20/1.22/1.24× 与 1.25/1.26×），故是实的。这与 status doc §2 已
登记的"L08 最差 match +17%（绝对值 8 µs）"同量级同方向——属**已知且已披露**
的偏差，远在 1.5× 验收线内，但此前记录的是 L08、本次实测 L07 也有同款。

### 3.3 L11 macro / L12 strchain 参考版慢 7–10%（待定性）

| 单元格 | pre | post | 比值 |
|---|---|---|---|
| L11 macro basic（k=11） | 2800 / 2827 ms | 3020 / 3019 ms | 1.08 / 1.07× |
| L12 strchain basic（k=11） | 1858 / 1879 ms | 2038 / 2038 ms | 1.10 / 1.08× |

两轮独立测量（主矩阵 + 交错复测）各自一致，故为真实差异，绝对量
~160–190 ms。注意这两层 `--only basic` 是**参考版全流程 `run`**（含
preprocess/parse/pretty 打印），且这两个负载的耗时大头是输出而非精化
（见 bench-matrix §3 注：L11/L12 的 strchain/macro 同类负载里 pretty 占
绝大部分）。因此这 7–10% 更可能来自打印/kernel 外的间接影响，**成因未定位**，
登记为待查项而非已判定回归。

### 3.4 L09 孪生 natadd 慢 8%

0.866 → 0.937 ms（+70 µs）。绝对值极小，两轮一致。可忽略但登记。

## 3.5 L07 的回归到底出在哪（补充实验）

§3.2 只给出了 L07 孪生版 `match` +24% 这个单点。它的绝对值太小（+9 µs）、
且文档 §2 声称孪生版 match 是 **0.66×（变快）**——与实测方向相反；而设计
文档 §2 又记着另一处 L07 回归（deep40/deep80 约 +9%），评审
（`docs/review-l07l12/d5-performance.md` P2-4）明确指出**那份微基准无法从
仓库复现**。为此补做了专门的受控实验：把**重构前的 L07 源码**（`b9d54fe`，
pm_defs 事实表版）用 `git archive` 抽到 `src/bench_pre/L07_sum_type/`，与当前
L07 编进**同一个二进制**（`pmabbench --impls l07pre,l07`），同源同进程对撞，
每规模扣掉"同枚举、无 match"的对照。

覆盖了文档缺失的深嵌套负载（形态取自 `tests.rs` 的
`test_deep_pattern_fuel_budget_regression`：GADT Vec 上逐层 `cons` 嵌套，
σ 链长 = 深度 d），三个形态 × 3 次进程交错、rounds=5 取 min：

| 形态 | 规模 | l07pre(ms) | l07(ms) | post/pre |
|---|---|---|---|---|
| flat（臂数，无 σ） | 5 / 9 / 17 臂 | 0.033 / 0.072 / 0.232 | 0.037 / 0.082 / 0.254 | 1.12 / 1.14 / 1.09 |
| wild（列数/通配，无 σ 链） | 7 臂 | 0.076 | 0.093 | **1.22** |
| deep（σ 链长 = d） | d=16 | 0.386 | 0.455 | **1.18** |
| | d=32 | 1.166 | 1.394 | **1.20** |
| | d=64 | 4.107 | 4.848 | **1.18** |
| | d=128 | 16.377 | 20.146 | **1.23** |

**三条结论**：

1. **回归是真的，且是常数因子**。deep 一行在 d 从 16 到 128（16 倍）之间
   比值稳定在 1.18–1.23，没有随规模漂移——即显式替换没有改变复杂度，只在
   读路径上加了常数开销。
2. **开销只落在模式匹配编译上，共享内核没有回归**。对照组（同枚举、无 match）
   pre/post 逐位相同（如 flat 的 ctrl：0.346 vs 0.346 ms）；而 §2 表里
   L07 的非 match 重负载（church 0.96×、strchain 0.96×、global 1.01×、
   natadd 1.05×）也都持平或更快。所以 `force` 新增的 `VSub` 入口臂本身不贵，
   贵的是模式编译器那些"解前构建、解后消费"的消费点——`wrap_sub` 包裹、
   `Subst::lookup_hit` 的**条件包裹浅扫**（`mentions_level`）、`subst_cxt`、
   `SpecSolve` 穿参。形态越深越密，消费点越多：flat +11%、wild/deep +18~22%。
3. **与设计文档的 ~9% 不矛盾，是口径差**。文档 deep40/deep80 是**整程序**
   口径（含 `def big` 那棵 d 深值 + `println` 的 nf），而 match 编译只占其中
   约三成；19% × 约 0.3–0.4 ≈ 6–8%，与文档的 8.5–8.9% 同量级。本文的
   19% 是"模式匹配编译本身"的回归幅度，两者可以并存。

**由此订正两处文档**：

- `explicit-subst-refactor-status.md` §2 的"孪生版 bench：L07 多数负载持平或
  更快（church 1.0-1.1×、**match 0.66×、enum 0.53×**）"**不可复现**。实测
  （交错 3 轮 × rounds 9，k=10..13 一致）L07 孪生 `match` 是 **1.20–1.26×**、
  `enum` 是 **1.06×**，方向与幅度都对不上；其中 match 的 1.2× 反与同文档
  下一句"L08 最差 match +17%"一致（两层的 match 负载同源）。
- `d5-performance.md` P2-4 的建议（补深嵌套/σ 链负载）**至今未落地**——
  本文的 `pmabbench --sweep deep` 可以直接当那个负载用。

## 4. 与文档 §4 存档基线对照

重构后实测 / §4 存档：basic 几何均值 **1.012×**、fast **1.002×**
（n=42）。逐格最大偏差出现在 L09 match/enum（0.51× / 0.49×，即 §3.1 的

## 5. L10 `enum` 单元格：失败形态变化与归因订正

**现象**：主矩阵中该单元格 pre 与 post 都拿不到数字，但失败方式不同。

- pre（重构前二进制）：`thread '<unknown>' has overflowed its stack`；
- post（重构后）：`panicked at l10bench.rs:286: fast check-only 未通过 k=9`。

**定位实验**（临时把 `src/L10_typeclass/` 回退到 `efa47b9`、给
`l10bench.rs` 加 eprintln 探针、构建、运行，随后 `git checkout HEAD` 还原
源码并重建；探针输出存 `target/bench_ab/probe_*.txt`）：

| 构建 | 输出 |
|---|---|
| 重构前 + 探针 | `[probe] twin bench_check_nf 开始` 后**再无输出**，128 MB 栈溢出、1 GB/3 GB 栈下 240 s 挂死 |
| 重构后 + 探针 | `twin bench_check_nf 完成 nodes=0` → `twin bench_check = false` → 断言失败（0 s 内） |

**结论**：

1. 发散发生在**孪生版** `Tycker::bench_check_nf`（bump_spine_iter），
   参考版那一行**从未被执行到**——`bench-matrix §4` 的"参考版栈溢出/超时"
   是**误归因**（当时无法区分：断言在参考版调用之前，任何一侧先崩都会
   表现为进程级崩溃）。
2. 这**不是**重构引入的回归：孪生在该 GADT 源上重构前就是发散的
   （无界递归），重构后变成**有界拒绝**。定性上是从"崩溃"变成"干净的
   失败"，不是从"通过"变成"失败"。
3. 同一份 `enum_src`（`L09/L10/L11/L12` 四层 md5 相同）在 L09 孪生上通过、
   在 L10/L11/L12 孪生上失败（L11/L12 的失败是 §4 已登记的既有项）——
   属孪生侧一族既有限制，不是本轮重构引入。

```bash

```

`FINAL_REPORT.txt`、`probe_*.txt`）。
