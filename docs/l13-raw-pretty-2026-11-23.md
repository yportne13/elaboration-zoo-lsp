# L13 观察面补齐：源码注解渲染（2026-11-23）

> 承接 `docs/l07-final-scope-2026-11-23.md`。L13 已有完整的 `LspSurface` 契约（`hover_table` /
> `inlay_hint_table` / `completion_table` / `lsp_collect` / `accumulated_errors` / `failed_decls`），
> 本轮只补它缺的两项里的第一项：**源码注解渲染**。

## 1. 为什么不做"用 L07/L08 重写 L13"

| 层 | 非测试文件 | 非测试行数 |
|---|---|---|
| L07 | 32 | 17,540 |
| L08 | 31 | 17,284 |
| **L13** | 35 | **39,827**（2.3×） |

L13 独占（L07/L08 完全没有）：Package/Import 模块系统、`module`（505 处）、`class`（155 处）、
derive（196）、macro（580）、HDL prelude（859）、prelude 内建库（584）、TraitDecl/ImplDecl、
`Val::Nat`、`Call`/`OpCall`。parser 规模 L13 ≈ 312 KB vs L07 ≈ 34 KB（9×）。

**结论：不重写**。L13 的观察面本来就比 L07 全（L07 的 `surface.rs` 是从 L13 契约移植的），
缺的只有 `raw_pretty` 与 `shape`，补它成本 ≈ 1 天，重写成本 ≈ 数月且丢掉产品价值。

## 2. 本轮改动：`raw_pretty.rs`

新增 `src/L13_namespace/raw_pretty.rs`（~230 行）：把 def 的签名（`params` + `ret_type`，都是 `Raw`）
打成源码形态的类型串，接入 `elaboration.rs` 的 `vtyp_pretty` 生成点。

**关键收益不只是显示保真，还有复杂度：**

旧路径 `vtyp_pretty = pretty_tm(…, nf(…, typ_tm))` —— `nf` 会 `quote`，而 `quote` 对 `Val::Nat(k)`
要走 `quote_nat`，**展开成 k 层 `SumCase` 链**（`for _ in 0..k` 裸分配循环，`mod.rs:3908-3934`）。
仓库里为此加过 `NAT_CHAIN_LIMIT = 2^22` 护栏：2026-10-07 实测 `nat_mul 100000 100000` 把进程提交量
顶到 **121.8 GB**，Windows 事件 2004 记录，主机非正常重启（3 小时内 3 次）。

源码注解渲染**完全绕开** `nf`/`quote`/`quote_nat`：只遍历 `Raw` 拼字符串，零求值、零分配链。

## 3. L13 特有 `Raw` 形态的适配

| L13 与 L07 的差异 | 处理 |
|---|---|
| `U(u32, Span<()>)` | 打 `U`（层级 0）或 `U(n)` |
| `Nat(Span<u64>)` | 打源码十进制字面量（**不建链**） |
| `Sum(名, 参数, 构造子, u32, bool)`（5 字段） | 打 `enum`/`trait` 前缀 + 参数 + 层级 |
| `SumCase { is_trait, … }` | 打 `trait.` 前缀 |
| `Obj(Box<Raw>, Option<Span>)` | 字段名可选 |
| `Raw::Tm(Rc<Tm>, Rc<Val>)`（pre-checked 内部节点） | `has_source_type` 扫到就**回落值渲染**（用户源码里不出现） |

## 7. 第 2 步：登记串复用（`push_hover_decl`）

L13 的全局名使用处 hover 原来是**每个使用点都 `quote` + `pretty` 一次**（`push_hover`，
`elaboration.rs:2842`）。而 decl 表里早就存着 def-site 的渲染串（`e.6 = typ_pretty`），
`lib.rs:811` 的 LSP 消费路径本来就是优先用它。

新增 `push_hover_decl(cxt, t_span, key)`：命中 decl 表且登记串非空时**直接复用**，
否则回落 `push_hover`。接入 6 个全局名站点：

| 站点 | 位置 |
|---|---|
| 裸名解析 | `elaboration.rs:2923` |
| import alias 解析 | `:2934` |
| 后缀消歧唯一命中 | `:2986` |
| 限定路径 `a.b.c` | `:3072` |
| import alias + 限定段 | `:3085` |
| namespace prefix | `:3094` |

收益双重：**免一次 quote+pretty 全管线**，且**绕开 `quote_nat`**（`quote` 对 `Val::Nat(k)` 要建
k 层 `SumCase` 链，登记串是纯文本）。

### 复杂度证据测试

`big_nat_literal_in_annotation_does_not_expand`：`def Box(n: Nat): Type 0 = Nat` +
`def big(n: Nat): Box 100000 = n`，断言 `typ_pretty` **含 `100000` 且长度 < 60**。

## 10. 第 3 步：形状认回（`shape.rs`，方案 3）

新增 `src/L13_namespace/shape.rs`（L07/L08 的平移，~120 行）+ `Infer::render_by_shape`：

1. def 登记处记录其 **match 形状**（`Val::Match` 的 pattern 骨架 + 来源 + `type_level`）；
2. `push_hover` 先试形状认回，命中就打 `head 实参`（`g n`）而不是 `match n { … }`；
3. 优先级：**类型级 FromValue > 值级 FromValue > 类型级 FromType > 值级 FromType**。

### 10.1 两个 L13 特有的坑（都修了）

**坑 1：`Val::Call` 包住了内联的 def 体。** L13 的 `eval` 把内联的 def 体包成
`Val::Call(name, args, body)`（保留名字供显示），所以 `def T(n: Nat): Type 0 = match n { … }`
的**值**不是一个裸露的 `Val::Match`。`peel` 若不剥这层，值来源的形状登记全部落空
（实测：只登记到 `h` 一个，`T` 和 `g` 都没登记）。修法是 `peel` 里加 `Val::Call(_, _, body) => t = force(body)`。

**坑 2：`PatternDetail::Any` 携带 binder 名，且每个实例是 fresh 名。** 直接 `PartialEq` 比较
会让同一类型函数在不同实例上认不回来（实测 `h` 认成 `h n` 而不是 `T n`）。修法是加一个
**结构比较** `pats_eq`：忽略 binder 名与 span，只比构造子名与嵌套形状。

（L07/L08 没有这两处，因为它们的 `Val` 没有 `Call` 包装、`PatternDetail::Any` 不带名字。）
