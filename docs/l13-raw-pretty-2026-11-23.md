## 1. 为什么不做"用 L07/L08 重写 L13"

| 层 | 非测试文件 | 非测试行数 |
|---|---|---|
| L07 | 32 | 17,540 |
| L08 | 31 | 17,284 |
| **L13** | 35 | **39,827**（2.3×） |

L13 独占（L07/L08 完全没有）：Package/Import 模块系统、`module`（505 处）、`class`（155 处）、
derive（196）、macro（580）、HDL prelude（859）、prelude 内建库（584）、TraitDecl/ImplDecl、
`Val::Nat`、`Call`/`OpCall`。parser 规模 L13 ≈ 312 KB vs L07 ≈ 34 KB（9×）。

**结论：不重写**。L13 的观察面本来就比 L07 全（L07 的 `surface.rs` 是从 L13 契约移植的），
缺的只有 `raw_pretty` 与 `shape`，补它成本 ≈ 1 天，重写成本 ≈ 数月且丢掉产品价值。

## 2. 本轮改动：`raw_pretty.rs`

新增 `src/L13_namespace/raw_pretty.rs`（~230 行）：把 def 的签名（`params` + `ret_type`，都是 `Raw`）
打成源码形态的类型串，接入 `elaboration.rs` 的 `vtyp_pretty` 生成点。

**关键收益不只是显示保真，还有复杂度：**

旧路径 `vtyp_pretty = pretty_tm(…, nf(…, typ_tm))` —— `nf` 会 `quote`，而 `quote` 对 `Val::Nat(k)`
要走 `quote_nat`，**展开成 k 层 `SumCase` 链**（`for _ in 0..k` 裸分配循环，`mod.rs:3908-3934`）。
仓库里为此加过 `NAT_CHAIN_LIMIT = 2^22` 护栏：2026-10-07 实测 `nat_mul 100000 100000` 把进程提交量
顶到 **121.8 GB**，Windows 事件 2004 记录，主机非正常重启（3 小时内 3 次）。

源码注解渲染**完全绕开** `nf`/`quote`/`quote_nat`：只遍历 `Raw` 拼字符串，零求值、零分配链。

## 3. L13 特有 `Raw` 形态的适配

| L13 与 L07 的差异 | 处理 |
|---|---|
| `U(u32, Span<()>)` | 打 `U`（层级 0）或 `U(n)` |
| `Nat(Span<u64>)` | 打源码十进制字面量（**不建链**） |
| `Sum(名, 参数, 构造子, u32, bool)`（5 字段） | 打 `enum`/`trait` 前缀 + 参数 + 层级 |
| `SumCase { is_trait, … }` | 打 `trait.` 前缀 |
| `Obj(Box<Raw>, Option<Span>)` | 字段名可选 |
| `Raw::Tm(Rc<Tm>, Rc<Val>)`（pre-checked 内部节点） | `has_source_type` 扫到就**回落值渲染**（用户源码里不出现） |

## 4. 效果与验证

`def T(n: Nat): Type 0` / `def g(n: Nat): T n`：

| | 旧（值渲染） | **新（源码渲染）** |
|---|---|---|
| `g` 的 `typ_pretty` | `(n: Nat) → (match n { case zero => Boolean; case succ(m) => Nat })` | **`(n : Nat) → T n`** |
