> 进程、`--max-k 11`（`enum`/`implicit`/`prune`/`traitchain`/`gadt`/`moduletree`
> 取 k=9；L13 的 `prelude-*`/`examples-hdl` 与 k 无关）、`--rounds 3`

与 09-18 存档相比，**中间经历了一整批代码改动**：09-19 的「评审修复轮移植」
一口气改了 L07–L13 全部七层（`fb89bb0`/`a7d6bb5`/`88242bc`/`aafa5ed`/

提交（`6bacd12`/`b3b1700`）。所以**未改动的对照层只剩 L02–L06**，其余层本轮的
比值是「代码改动 + 窗口漂移」的合成。

### 本轮最值得看的三件事

1. **L12 match 参考版回退 6.56×**（0.218 → 1.431 ms）：`c53cbf3` 引入的
   `src/L12_canonical/pattern_match.rs:273` 一行**无条件** `eprintln!`
   （`DBG nc path=… field_sum=… pats=…`）留在嵌套覆盖检查的热路径上。实证有三：
   ① 每次 `--only basic` 运行往 stderr 打 **132 行 / 17.7 KB**；② 同一二进制
   `--only fast_ss` 打 0 行（该行只在参考侧路径上）；③ 把 stderr 引流到空设备
   重测，k=11 从 1.431 → 1.004 ms，即**这一行的 stderr 写入占 ~0.43 ms**（实参的
   `Debug`/`to_string` 构造仍在剩下的时间里）。余下 ~0.79 ms 是同一提交加入的
   嵌套覆盖探测（`NestedCheck`/`probe_accessible`）——孪生侧同样移植了该语义，
   却只从 0.176 → 0.195 ms，故参考侧这条路径值得单独再查。
   **这是本轮唯一一处显著超出窗口噪声带（±10%）的回退**，且删掉一行即可先
   验证其中 0.43 ms。
2. **L09/L13 的孪生匹配编译器大幅提速**：L09 match 孪生 0.966 → 0.055 ms
   （0.057×）、`enum` 1.619 → 0.126 ms（0.078×）；L13 match 孪生
   0.673 → 0.172 ms（0.256×）、`struct` 20.559 → 13.187 ms、真实 prelude 负载
   `prelude-core` 16.171 → 8.261 ms、`examples-hdl` 16.103 → 8.203 ms（均 ~0.51×）。
3. **`L05 chain` 参考版从 09-18 那轮的丢格里回来了**：09-18 那轮该格参考版

## 4. 表注

- 列义：`basic` = 参考版；`fast_ss` = 孪生稳态（排除建表）；`fast` = 孪生一次性；
  `fast_run` = 孪生**全流程**（仅 L11/L12 有，是这两层的可比孪生列）；
  `basic/孪生` 列对 L11/L12 用 `fast_run` 算，其余层用 `fast_ss`。
- 「—」= 不可测（**既有**，与本轮改动无关）：`L05/L06 prune` 参考版超时；
  `L10 enum` 孪生发散；`L11/L12 enum` 孪生 check+nf 失败；`L12 traitchain`
  孪生 parity 失败（perf-debt P5）。本轮 stderr 实证复核：这四类失败仍是原样的
  parity 缺口（`unsolved match`），非新引入。
- `L05 prune` 两侧都超时，孪生列来自缺口补测（`target/fill_gaps4.py`，
  fast_ss 8.090 / fast 8.331 ms，对上轮 8.156 / 8.346 为 0.99×）。
- 超时对口径的影响：`l05/chain` 参考版的 `--only basic` 调用落在 180 s 上限附近
  （本轮 147 s 通过，09-18 那轮超时；09-12/09-17 存量里 k=11 记 33.1 / 30.5 s），
  故该格属于**边缘可测**——k=11 的 29096 ms 是两次调用取 min 的结果，重跑可能
  再度超时。

# 附录：本轮矩阵之后的优化轮（2026-09-20 下午）

> 承 §0 的"本轮最值得看的三件事"，把**参考版侧的 O(D²) 成本**按「同负载横向
> 离群 ≥5×」筛出来（`target/find_slow.py`）逐簇搬其他层已验证的手法。
> 口径与上表一致（`--only basic`、k=11 / K9 取 k=9、`--rounds 3` 取 min），

## A. 离群清单与根因（诊断结论）

| 负载 | 慢层 | basic (ms) | 相对同负载最快层 | 根因（同一类：**每声明一次 O(D) 的表操作**） |
|---|---|---|---|---|
| chain | L05 | 29096 | 93.9× | `Cxt::Clone` 是 O(D) 深拷（`Locals` Box 脊 + 按值载荷、`src_names` 按值），而 `SrcPos` 每声明克隆 6-8 次 `Cxt` ⇒ 每声明 O(6-8·D) 次堆分配 |
| struct | L13 | 7490 | 55.8× | ① 先 `clone` 再 `Rc::make_mut` ⇒ 恒见计数 2、每声明 2 次整表克隆（条目含堆 `String`）；② `scan_def_replay` 递归不查 memo ⇒ 每声明一次 O(链长) DFS。**两条必须同修** |
| implicit | L05 | 4575 | 180× | 同上基座 + 每声明一次 `fresh_meta` 整 telescope 重物化 |
| strchain | L13 | 4537 | 37.0× | 同 `struct` ①② |
| global | L06 | 4368 | 32.6× | `define` 每声明深拷整条 `Locals` 链 + `src_names` 全表 |
| struct | L09 | 4269 | 31.8× | 同 `chain` 一族（L09/L10 的 `Cxt` 表示与 L05 同形） |
| strchain | L09 | 2669 | 21.7× | 同上 |
| implicit | L06 | 2281 | 89.8× | 同上（L06 无 `SrcPos`，故比 L05 轻 2×） |
| strchain | L06 | 1215 | 9.9× | 同上 |
| struct/strchain | L10 | 981 / 917 | 7.3× / 7.5× | 同上（L10 载荷已 `Rc`，比 L09 轻 3×） |

对照层做对的地方：L03/L04 的 `Cxt` 全是持久 `List`（`prepend` O(1)），
名字表就是链上的 `List`，付 O(scope) 次**指针步**而非 O(scope) 次**堆分配**；
L07/L08 的 decl 表是 `HashMap<SmolStr, Rc<DeclEntry>>`（每条目 ~7 ns vs
L13 的 ~893 ns）。

**政策**：`docs/perf-debt-2026-09-12.md` 的「参考版按项目政策只记录不修」
名单里明确含 `L05 src_names` 与 P4（L13 `scan_def_replay`）；本轮由 owner
要求破例搬运，并额外发现两项**从未登记**的成本（`Locals` 链深拷 + `SrcPos`
放大器；L13 的"先 clone 再 make_mut"，`docs/perf-l08l13-followup-2026-09-17.md`
§0 当年判的是**载荷**已达标，漏了这个模式）。

## D. 同轮修掉的正确性问题（测试补齐时发现）

1. **遮蔽臂被误报错**（L09–L13）：`pattern_match.rs` 的臂循环对"通配臂之后的臂"
   推 `Warning::Unreachable`，而这几层把非空 warnings 直接变 `Err` ⇒ 同一份源
   在 **L07/L08 通过**（`src/L07_sum_type/README.md:264` 规格：「通配臂之后的臂
   跳过……**不报错**」+ 两层各有回归钉 `test_catch_all_mixed`）、在 L09–L13 被拒。
   该警告是决策树时代的残留（老算法里"树从未到达的臂"是另一回事，见
   `docs/l09l13-match-compiler-analysis-2026-09-17.md` §2；改成逐臂下钻后只剩
   这一种情形，而它恰是规格要求不报的）。已按规格对齐（五层参考版 + 孪生），
   并各加一条钉子 `test_pm_shadowed_arm_after_catch_all_accepted`。
   L13 的**结构性不可达**（`Vec zero` 上的 `cons`，`ctor_accessible` 过滤）保留
   ——那处与 L07 的"分支不可达"同判，是有记录的口径。
2. **L12 参考版热路径残留调试打印**：`pattern_match.rs` 嵌套覆盖检查里一行
   **无条件** `eprintln!("DBG nc …")`（`c53cbf3` 引入），每次 basic 运行打
   132 行 / 17.7 KB，`match` 负载 1.431 → 0.196 ms（7.3×，其中 stderr 写入
   本身实测占 ~0.43 ms）。已删；孪生侧无此行（`--only fast_ss` 打 0 行）。
