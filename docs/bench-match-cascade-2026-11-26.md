# 多分支多层次 match 基准（2026-11-26）

## 1. 语料与工具

`src/bin/matchbench_src.rs` + `src/bin/matchbench.rs`（bin 名 `matchbench`，`required-features = ["twins"]`）。

`match_cascade_src(depth, copies, width)` 的三个轴**都作用在 match 结构上**：

| 轴 | 含义 |
|---|---|
| `depth` | 嵌套层数（第 0 臂里再开一个 match） |
| `width` | **每个 match 的臂数**（被匹配 `enum Tag` 的构造子数） |
| `copies` | 级联条数（线性放大，不改形态） |

只让第 0 臂向下钻，于是 match 块数 = `depth`、总臂数 = `depth × width`，两轴可独立调节。

```text
cargo build --release --bin matchbench --features twins
target_b13/release/matchbench.exe --width-sweep --depth 4 --copies 16 --max-width 128 --reps 7
target_b13/release/matchbench.exe --sweep --copies 16 --reps 5
```

## 4. 关键否定性实验：memo 不是差异来源

### 4.1 关掉 L13 的 memo（`ctor_accessible` 的 `accessible` 缓存）

| width | L13 有 memo | L13 无 memo | 收益 |
|---:|---:|---:|---:|
| 1 | 0.890 | 0.899 | 1.0% |
| 8 | 2.399 | 2.398 | −0.0% |
| 32 | 9.397 | 9.096 | −3.3% |
| 64 | 24.463 | 25.399 | 3.7% |
| 128 | 97.629 | 103.357 | 5.5% |

**memo 只在 width=128 上贡献 5.5%，中等宽度完全无收益。**

### 4.2 给 L07 装上同款 memo

按 L13 的形状在 L07 的覆盖循环里加 `Vec<Option<bool>>` memo：

| width | L07 基线 | L07 加 memo |
|---:|---:|---:|
| 1 | 0.604 | 0.626 |
| 32 | 22.445 | 22.823 |
| 128 | 304.309 | 312.579 |

**L07 加 memo 后反而略慢。** 原因：语料是全覆盖的，`fully_covered` 短路了整轮探测——
`probe_accessible` 根本没被调用，memo 只是白建一个 `Vec`。

### 4.3 `covers` 调用次数完全相同

给两章的 `covers` 加原子计数器，跑同一批宽度档：

| width | L07 covers | L13 covers |
|---:|---:|---:|
| 1 | 64 | 64 |
| 8 | 3 200 | 3 200 |
| 32 | 45 696 | 45 696 |
| 128 | **707 200** | **707 200** |

**逐字节相同。** 但 L07 304 ms vs L13 98 ms——差别不在调用次数，在每次调用的**内部成本**：

| 章 | `covers` 的比较方式 | `ctor_names` 元素 |
|---|---|---|
| L07 | `c.iter().any(|c| c == &name.data)` —— `String == &String` | `Vec<String>`（堆分配） |
| L13 | `c.as_str() == name.data.as_str()` —— `&str == &str` | `Vec<SmolStr>`（内联/共享） |

707 200 次 × 每次一次 `String` 堆比较 vs `SmolStr`（通常 22 字节内联、等长直接 memcmp），
这是宽 match 上的主差异。

## 5. 结论

1. **L13 在宽 match 上快 2–3×**（width 128：98 ms vs 304 ms），增长阶更低（1.32 vs 1.67）。
2. **memo 不是原因**：关掉 L13 memo 只慢 5.5%（width=128），给 L07 装 memo 反而略慢。
3. **真正原因是字符串表示**：`covers` 调用次数两章完全相同（707 200），但 L07 用 `String` 比较、
   L13 用 `SmolStr`。这是 L08 之后引入的表示差异，不是 match 逻辑差异。
4. **L13 只在极小负载慢**（width ≤ 4：1.1–1.5×），来自固定开销（引擎初始化、prelude 前置）。

### 对 B3' 的意义

这条数据链否掉了「L07 升级 memo 能追上 L13」的想法：memo 在本语料上根本不触发，
`fully_covered` 已经短路了探测。**要追上 L13 的宽度性能，该改的是 `String → SmolStr`，
而那是 L08 就做的表示升级，不是 L07 的 match 逻辑问题。**

同时也再次说明：match 负载上不存在「改 σ 能显著提速」的空间——L13 的宽度优势与 σ 无关。

## 9. 剩余差距的分阶段归因（2026-11-26 晚）

第 8.6 节留下的 0.23 斜率差，这一节把它拆到具体代码路径。方法是给七章的
`pattern_match::compile` 插**独占耗时探针**（子阶段耗时用一条线程本地栈扣掉，
各阶段之和 ≈ 墙钟，实测覆盖 95%），再由 `matchbench --prof` 输出。

### 9.1 探针与口径

```text
RESULT,<ch>,<depth>,<copies>,<width>,<bytes>,<ms>,<ok>
PROFILE,<ch>,...,FORCE=.. EVAL=.. COVER_NS=.. WALK_NS=.. SUBCXT_NS=.. REANCHOR_NS=..
                  RE_FORCE_NS=.. RE_QUOTE_NS=.. RE_EVAL_NS=.. BODY_NS=..
```

| 阶段 | 覆盖范围 |
|---|---|
| `COVER_NS` | `fully_covered` 的 `covers` 扫描 + 缺构造子探测 |
| `ARMS_NS` | 臂循环自身（快照/回滚/判 `is_catch_all`），不含子阶段 |
| `WALK_NS` | `walk`（模式走查 + 特化方程） |
| `SUBCXT_NS` | `subst_cxt`（把 σ 施加到臂上下文） |
| `REANCHOR_NS` | 期望类型重锚：`force` + `quote` + `eval` |
| `RE_EVAL_NS` | 重锚内部的 `eval`（已从 `REANCHOR_NS` 独占扣除） |
| `BODY_NS` | 分支体 `check` |
| `NEST_NS` | 嵌套位置覆盖检查 |

探针总闸：L07–L12 用 `prof::enable()`，L13 用 `FUNC_PROF.enabled`。关着时
只是一次 `AtomicBool` 读，零行为变化。

### 9.2 单次运行的完整账（depth=4, copies=16, width=128, reps=1，ms）

| 阶段（独占） | L07 | L13 | 差（L07−L13） |
|---|---:|---:|---:|
| **总计** | **177.7** | **114.7** | **+63.0** |
| 覆盖检查 `COVER_NS` | 63.3 | 59.8 | +3.5 |
| 走查 `WALK_NS` | 27.8 | 5.3 | +22.5 |
| `subst_cxt` | 11.5 | 12.3 | −0.8 |
| **期望类型重锚（含子阶段）** | **38.4** | **3.2** | **+35.2** |
| 　`force` | 0.5 | ↓ | |
| 　`quote` | 8.2 | ↓ | |
| 　`eval` | 28.1 | ↓ | **+28.1** |
| 分支体 `BODY_NS` | 17.2 | 15.1 | +2.1 |
| 臂循环 `ARMS_NS` | 2.7 | 5.7 | −3.0 |
| `frcs` 重建 `Sum`/`SumCase` | 3.0 | 0 | +3.0 |
| 嵌套覆盖 `NEST_NS` | 0.01 | 0.005 | +0.005 |
| 未归因残差 | 8.5 | — | — |

> 注：探针用「子阶段扣减」口径——`REANCHOR_NS` 的计数值只含它自己的开销，
> 三个子阶段（`force`/`quote`/`eval`）各自单列；因此**「含子阶段」行 = 父 + 三子**
> （1.6 + 0.5 + 8.2 + 28.1 = 38.4 ms）。同理 `WALK_NS` 与重锚是**兄弟**不是父子
> （`g_walk` 在走查返回后立即释放），两者不相减。各行可直接相加：
> 合计 169.2 ms / 177.7 ms = **95.2%** 被归因，残差 8.5 ms 落在
> `compile` 之外的引擎公共开销。

### 9.3 结论：差距几乎全在「期望类型重锚」这一条路径

**覆盖检查两边一样**（63.3 vs 59.8 ms）。这否掉了第 4.3 节的老结论——
那时光看 `covers` 调用次数相同就推断「差别在每次调用的内部成本」，
但升级 SmolStr 之后两边连内部成本也基本对齐了（192 万次 `covers`，
差 3.5 ms = 1.8 ns/次）。

**真正的差距是 63 ms 里的 22.5 ms 走查 + 28.1 ms 重锚 eval。** 具体形态：

| | L07 | L13 |
|---|---|---|
| 臂上下文载体 | `Cxt` + env 槽 | `Cxt` + env 槽（**同一形态**） |
| 期望类型重锚 | `force(wrap_sub σ expected)` → `quote` → `eval` | 只 `force`（flex 之外才 quote→eval） |
| `Val::Sum.cases` | `Rc<Vec<VSpan>>`，`VSpan = Rc<Span<SmolStr>>` | `Rc<Vec<Span<SmolStr>>>` |

两条机制叠加，都落在同一条读点上：

1. **L07 的 `Val::Sum` 构造子名单是「每个名字一个 `Rc`」**（`VSpan`），
   L13 是内联 `Span<SmolStr>`。一次 `eval` 重建 `Val::Sum` 要分配
   `1 + cases.len() + 4*params.len()` 个 `Rc`；width=128 时每次 eval 光
   构造子名单就是 128 次分配。实测 `VSPAN_ALLOC = 1 059 120`（每次 run）。
   （`Tm::Sum` 的 `cases` 也是 `Vec<Span<SmolStr>>`——项层没有 `VSpan`，
   所以项层不分配，值层才分配。）
2. **L07 每臂都无条件做 quote→eval 重锚**，L13 的 `ret_type` 已经在
   `Compiler::new` 时以值形态持有（`self.ret_type`），重锚退化成一次
   `force` + 极少数 flex 分支。
   注意 L07 的重锚注释（`pattern_match.rs:238-244`）明确说这不是可选的：
   「值层面只有重锚后…unify 的结构快路径（val_eq）才能命中，否则双方逐层
   展开不收敛」——所以修法 ② 不能只是「删掉重锚」，而要像 L13 那样让
   `ret_type` 从一开始就是正确锚定的值。

把这两条分开量化（width=128，reps=1，ms）：

| 项目 | L07 | L13 |
|---|---:|---:|
| `quote` 调用次数 | 16 416 | 14 768 |
| `eval` 调用次数 | 9 120 | 21 347 |
| **`eval` 在重锚里的耗时** | **28.1** | ~0 |
| `quote` 在重锚里的耗时 | 8.2 | ~0 |
| `frcs` 重建 `Val::Sum`/`SumCase` | 2.95 | 0 |
| `sum_cases()` 展开 | 0.006 | 0 |

L07 的 `eval` 次数反而**比 L13 少**（9 120 vs 21 347），但每次更贵——
因为它的 `Val::Sum` 重建要付 `VSpan` 分配，而且重锚路径每臂都跑。

### 9.4 斜率差的来源

宽度从 8 涨到 128 时（单次 run，ms）：

| width | L07 重锚内 `eval` | L07 覆盖检查 | L07 总计 | L13 总计 |
|---:|---:|---:|---:|---:|
| 8 | 0.247 | 0.044 | 3.39 | 2.41 |
| 32 | 2.28 | 1.10 | 14.69 | 13.14 |
| 64 | 7.63 | 8.64 | 46.06 | 31.85 |
| 128 | 28.1 | 63.3 | 190.3 | 111.9 |

**两段都跟着宽度超线性涨，但重锚内 `eval` 涨得更陡**：0.247 → 28.1 是
**114×**，而总时间只涨 56×、L13 涨 46×。归一化到「相对 width=8 的倍数」：

| | width 8→128 倍数 |
|---|---:|
| L07 重锚内 `eval` | **114×** |
| L07 覆盖检查 | 1438×（≈ width²，见下） |
| L07 总计 | 56× |
| L13 总计 | 46× |

重锚内 `eval` 的 114× 明显高于 16×（宽度线性）——因为 `eval` 每层都要重建
`Val::Sum`，构造子名单长度 = width，**单次 eval 是 O(width)**；而每个臂都做
一次重锚、每层 match 有 width 个臂、depth 层 → 总量约 O(width² · depth)。
这就是斜率从 1.34 抬到 1.59 的那部分。

（覆盖检查的 1438× ≈ width² 来自 `covers` 的「每构造子 × 每臂」两重循环，
但 L07 与 L13 在这一段**几乎一样**（63.3 vs 59.8 ms），它抬的是绝对值，
不抬两章的相对差。）

### 9.5 三条可验证的修法（按预期收益排序）

| 修法 | 预期收益 | 风险 |
|---|---|---|
| ①`Val::Sum.cases` / `params` / `SumCase` 改内联（去 `VSpan`），对齐 L13 | **最大**：砍掉每次 `eval`/`frcs` 重建时的逐名字 `Rc` 分配（width=128 时每次 128 个） | 动 L07–L12 的值层表示：`VSpan` 上挂着 `Deref`/`PartialEq`/`Debug` 三套 impl，且被 `unify`/`rename`/`quote`/`pretty` 共享，改起来是七章同步的大改 |
| ②`ret_type` 在 `Compiler` 上持值形态（学 L13 `self.ret_type`），去掉每臂 quote→eval 往返 | 大：直接消掉 28.1 ms `eval` + 8.2 ms `quote`（合计 36 ms / 63 ms 差距的 57%） | 中高：L07 注释明确论证过重锚是必要的（否则 `val_eq` 快路径不命中、逐层展开不收敛）。要做成 L13 那样，得先把期望类型在 `compile` 入口就重锚好，属于语义改动而非纯优化 |
| ③`eval` 的 `Sum` 臂先查 `mentions_level`，无 σ 引用时复用原 `Rc` | 中：拦掉不涉及本 σ 的重建 | 低 |

先验估计：②（若能落地）把 63 ms 差距砍掉 36 ms，width=128 从 178 → ~142 ms；
再叠 ① 应能到 ~125 ms 量级，仍略高于 L13 的 115 ms（覆盖检查那 3.5 ms +
`subst_cxt`/`BODY` 的残差）。二者的斜率贡献也不同：②是 O(width²·depth)，
①是常数因子——**要压斜率，必须做 ②**。

### 9.6 探针的零开销校验

探针必须默认零成本，否则测出来的账就是它自己造的。同一台机器、同一档
（depth=4, copies=16, width=128, reps=5，ms）：

| | L07 | L08 | L09 | L10 | L11 | L12 | L13 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 插桩前（`git stash` 干净树） | 178.8 | 173.3 | 174.9 | 169.0 | 167.5 | 167.6 | 102.4 |
| 插桩后、探针关闭 | 175.8 | 170.4 | 170.5 | 171.2 | 170.7 | 171.7 | 102.9 |

两行之差在连杆抖动带内（±2–3%），**探针关闭时确实是零成本**：每个探针
只是一次 `AtomicBool` 读（`phases::on()`），守卫结构在关闭路径上直接返回
`G { t: None }`，`Drop` 里第一个 `let Some(t) = self.t else { return }` 就退出。

另有一个**消融开关** `--no-memo`（`L13::FORCE_MEMO_DISABLED`），用来回答
「剩余差距是不是 force memo 造成的」：关掉 L13 的 memo 后 width=128 是
98.7 ms，开着是 98.1 ms——**0.6%，方向相反且在噪声内**。memo 不是原因
（与第 4 节的老结论一致，这里换了一种更直接的口径复核）。
