### [P1] `prune_vflex` 折叠应用序倒置（参考版）——L05 已修的移植缺陷未落到 L09–L13 各拷贝，且与快版分叉（已修）
- 位置：`src/L13_namespace/unification.rs:350-356`（修复前）
- 证据（三方对照，方向唯一）：
  1. **L05/L06 已把此项记为旧移植 bug 并修好**：`src/L05_pruning/mod.rs:32-37` 模块头
     ——"与旧移植的两处偏差修正（原码留有 `//TODO:revPruning` / `//TODO:need rev()?`，均已核对上游后修正）：… `pruneVFlex` 的结果折叠对齐上游 `foldr`：**最外层实参先应用**（旧移植 `iter().fold` 从内层起，**应用序倒置**）"；
     `src/L06_string/unification.rs:234-238` 的注释更直白："修正旧移植 `iter().fold` 从内层起导致的倒序——**sp 头 = 最内层**，直接 fold 会把内层包在最外"，
     实现均为 `slots.reverse()` 后折叠（`L05_pruning/mod.rs:780-790`、`L06_string/unification.rs:237-244`；L07/L08/`bench_head`/`bench_pre` 同）。
  2. **同一文件内的 `rename_sp` 取向相反**：`unification.rs:360-369` 对**同一** `Spine` 做尾递归
     （`rename_sp(t, tail)` → `App(inner, head)`），即"List 头 = 最内层、最外层先应用"；
     `prune_ty` 的注释也自述"Pruning `List` 头是最内层"（`unification.rs:215-218`）。
  3. **快版是正确序**：`bump_spine_iter/rename.rs:684-724`（`collect_args` 内先序 → `args.iter().rev()` 得外先 `slots` →
     `for (st,i) in slots { t = App(t,u,i) }`，注释"上游 foldr = 最外层实参先应用"）。
- 机制/影响：`sp.iter()` 是 head-first = **最内层先折叠**，产出 `App(App(?m', a_inner), a_outer)` = `?m' a_inner a_outer`，
  与语义及快版相反。该 `Tm` 随后被 `solve` 的非可逆 spine 路径 `eval`（`unification.rs:550/571`）用来**构造 meta 的解**，
  也经 `prune_ty_go` 进入类型：≥2 元实参的 flex 会得到**实参互换的解** ⇒ 静默错解或下游 `can't unify`；
  1 元 spine 时 `rev` 是恒等 ⇒ 与快版现存 parity 全绿并不矛盾（语料基本命中不了 ≥2 元）。
- 处置：**已修**（最小 diff，对齐 L05 与快版）：收集 `slots` → `reverse()` → 折叠（`List::Iter` 非 `DoubleEndedIterator`，故用 L05 同款收集反序写法），删掉 `//TODO:need rev()?`，补 4 行依据注释。
  **风险与回退**：该 hunk 改变参考引擎行为（仅 ≥2 元 spine 可观测），若 Lead 的 `cargo check/test` 出现基础版断言红，
  请回退此 hunk 并转交 orchestrator 决策（不可与"改测试断言"混同处理）。
- needs-verify：端到端触发用例未实测（无 cargo）；建议 Lead 用 `?m x y` 形态的隐式多参数 meta 源做一次基础版/twin 对照。
- **跨切片**：同一缺陷仍在 4 份参考版拷贝里：`L09_mltt/unification.rs:245`、`L10_typeclass/unification.rs:245`、
  `L11_macro/unification.rs:255`、`L12_canonical/unification.rs:258`（均为 `sp.iter().fold(...)` + `//TODO:need rev()?`）。
  这些文件本轮不可编辑 → 见 §4。

### [P1] `compact_state` 换 arena 时未失效"地址键 TLS 缓存"；`prime_resident` 收尾压实前无清点 → 潜在悬垂 `V`/假命中（已修）
- 位置：`src/L13_namespace/bump_spine_iter/compact.rs:611`（`drop(old)`）、`entry.rs:1018`（prima 收尾 `compact_state`，A3 文件，仅读）、
  `entry.rs:1091`（`compact_resident` 的补清点）
- 证据：
  - `compact_state` 只清 `Machine` 自有 scratch（`eval_work`/`quote_*`/`unify_*`/`vals`/`icits`/`constraints` + `quote_memo`，`compact.rs:620-631`），
    **不碰** force.rs 的五张"当轮 bump 地址为键"的 TLS 表：`FORCE_MEMO`（键/值都是旧 `V`）、`FORCE_PRIM_MEMO`、`TWIN_DECLB_CACHE`
    （`Rc<Decls<'static>>`）、`QUOTE_NAT_TM`（`&'static Tm`）、`STUCK_DECL_INTERN`（`force.rs:214-265`），
    而 `STUCK_DECL_INTERN` 是**按名字**命中的（`prim.rs:455-470`）——命中即返回旧 arena 的 `V`，无需地址复用运气。
  - 唯一清空口 `force_memo_clear()`（`force.rs:410-417`）被文档化为"每个 `bump.reset()` 轮入口的唯一汇聚点"（`force.rs:406-409`），
    而换 arena **不是** `bump.reset()`。调用点纪律不对称：prime 的 per-decl/文件边界在压实**前**清（`entry.rs:932/970`）、
    `compact_resident` 在压实**后**清（`entry.rs:1091`，注释 `entry.rs:1085-1090` 明确承认"after the arena swap both are dangling"），
    而 **`entry.rs:1018` 收尾压实两不靠**：其前最后一次清在 970（循环内文件边界），其后 `register_vconn_builtin`（989，`observe=true` 下的
    `quote`+`decl_reg`+`render_typ_pretty`，`machine.rs:930-948`）与 `insert_prelude_aliases` 仍可再填表。
- 机制/影响：若 970→1018 之间确有条目写入，则该条目在 `drop(old)` 后成为悬垂 `V`：`FORCE_MEMO` 假命中会返回野值、
  `STUCK_DECL_INTERN` 命中必野读（`v_xcell_of` 解引用释放块）⇒ UAF/静默错值，且常驻整个会话（清点只在下一次压实/轮界）。
- 处置：**已修**（最小 diff，`compact.rs` 内 1 行 + 注释）：在 `drop(old)` 之前加 `super::force::force_memo_clear();`
  （五张表全是纯缓存，清空语义中性——与 `entry.rs:1096-1098` 的"pure caches, dropping them is semantically neutral"同款论证）；
  不变量就地成立后，prime/compact_resident 的前置/后置清点变成冗余但无害。
- needs-verify：**当前 prelude 下 970→1018 是否真的填过表未能判定**（`register_vconn_builtin` 的 `eval` 只 push decl 值、
  `quote` 对 Pi/Sum 走叶臂不落 memo；再往前的 `insert_prelude_aliases` 是纯 map 操作）。即：修复的收益是**消除不变量缺口**，
  "当前是否已构成活跃 UAF"需运行时/Miri 才能定档——按 §6.7 只做加固不做语义改写。

### [P2] HashMap 迭代序泄漏到用户可见输出（补全顺序 / 歧义方法诊断）

## 5. 设计决定讨论（不属 bug，只记录）

1. **`Synth::synth` 在 L13 是"半死代码"**：全树唯一调用点是 `class_tests.rs:710`；参考版实战路径走 `can_satisfy` + `solve_trait`，
   快版走 `solve_trait_ref`。三者共用 `Synth::val_match` 故行为一致，但 `synth`（Prolog 式搜索树 + `panic!("Cannot resume with empty subgoals.")`
   `typeclass.rs:554` + `class_instances.get(name).unwrap()` `:588`）只被单测覆盖。若将来有人把它接回主路径，`:554` 的 panic 与 `:588` 的 unwrap
   都需要先加固（前者是"空 subgoals 续跑"不可能态，后者是未登记 trait 名）。**本轮不动**（不改主路径行为）。
2. **快版 `solve_trait_ref` 的"桶空早退" vs 参考版"回落全扫"**（`bump_spine_iter/typeclass.rs:282-298` vs `unification.rs:751-755`）：
   结论**等价**，但依赖 `head_index` 完备性这一非局部不变量。已核对完备性链条：`impl_trait_for` 对每个带非 out 参数的实例索引首个非 out 参数的头
   （`typeclass.rs:170-187`），注册顺序上 `new_trait`+`set_trait_out_params` 先于 `ImplDecl` 臂（`machine.rs:3906-3926`），且 ImplDecl 臂在
   `tstate.out_param` 缺失时**直接 Err**（`machine.rs:4144-4152`）⇒ 不存在"实例已登记但无索引"的可达状态；头键函数两侧同构
   （参考版 `head_key` = Decl/Sum 名，快版 `head_key_v` = 同 + Decl 头链 `HK_DECL`）。故"两桶皆空 ⇒ 候选必空"成立。**建议在 `:282` 的注释里补
   "依赖 ImplDecl 的 out_param 前置 Err 保证"**（当前注释已提到，但没点出这层因果）——本轮不改注释。
3. **`is_appliable` 的 tag-2 无条件 `true`**（`unify.rs:185-194`）看似比参考版宽松（参考版对 Sum/Nat/Lit/Pi/U 一律 false），
