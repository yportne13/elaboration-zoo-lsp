## 5. 设计决定讨论（不属 bug，只记录）

### 5.1 `typort check` 是否应该带退出码——立项材料（本轮按裁决不改）

- 位置（现状，事实）：`run_check`（`src/bin/cli.rs:675-745`）只用 `CliClient` 打印诊断，
  `main` 随后 `Ok(())`；**没有任何错误计数路径** ⇒ 有 ERROR 也 exit 0。对照：
  `run_build`/`run_test` 用 `Err` 表达失败（`tests/config_tests.rs:216` 断言 `!status.success()`）、
  `typort doc --deny-warnings`/`--min-coverage` 也返回 `Err`（`src/doc/mod.rs:150-160`）。
- **不本轮改的理由（Lead 裁决，我同意）**：退出码是**对外契约**，改它是破坏性行为变更
  （BRIEF §6.3 要求"证明是 bug"）；`tools/measure_*.sh` 把 `typort check` 的 `exit=$?` 当
  "是否崩溃"的信号打印（`measure_one.sh:12`、`measure_range.sh:12-15`），改后会把它们的读数语义弄反；
  用户脚本可能已有 `|| true` 依赖。
- **将来立项的补丁方向（已推演，未实施）**：
  1. `CliClient` 增 `DashMap<String, usize>`（**每 URI 记 max(ERROR 数)**）——
     必须取 max 而不是累加：两阶段发布会把同一批 ERROR 发两次（`src/lib.rs:1758-1777`），
     累加会让任何一次错误翻倍/假失败；
  2. `run_check` 末尾若总和 > 0 返回 `Err(format!("{n} error(s) in {m} file(s)"))` →
     `main` 的 `?` 链变成非零退出码（与 build/test 同款）；
  3. 同步改 `tools/measure_*.sh` 的读数含义、以及本报告 §4.3 的两处共享文档；
  4. 给 `tests/config_tests.rs` 补一条"坏文件 ⇒ 非零退出、好文件 ⇒ 0"的进程级断言
     （目前 `check` 的退出码**没有任何测试**）。
- 记录在案的反对意见：`check` 的定位是"给人看的报告"（help 里现在已这么写），
  带退出码后 `check` 与 `build` 的边界变模糊；若立项，建议用**新子命令或 `--deny-errors` flag**
  表达门禁语义，而不是静默改 `check` 的默认行为。

### 5.2 值输出面闸的代价（继承 R1 §5.5，仍成立）

`error-state-with-println` 让"含 println 的文件在错误态下双跑"。F2b 之后这个代价更值得保留：
它挡住的是**错的结果**（比错的诊断更糟），而 F2b 证明错误集本身也可能不完整——两道门各自覆盖一半，
在孪生侧修好之前都不该拆。撤闸的前置条件（两者同时满足）：(a) 孪生侧 stub 回滚修好；
(b) 语料 + v0/v1 形态的错误集对拍全绿。

### 5.3 错误态观察面（hover/completion/inlay）仍无对拍（R1 needs-verify-4 未变）

F2b 进一步支持这条：孪生错误态的恢复路径与参考版不同（失败的 decl 仍留在会话里 ⇒ 可观察），
而其观察表（`twin_tables`，`src/lib.rs:1486` 写入）就在这条路径上。补法很小（在 A3 的错误语料
循环里加 `resolved_hover_entry`/completion 的 twin↔reference 逐条比较），但归 A3 处置。
