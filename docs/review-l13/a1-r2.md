### [撤回 → needs-verify]（R1 的 P1）`enum` case 字段宇宙扫描脱离参数作用域
- R1 位置不变：`src/L13_namespace/elaboration.rs:1399-1405`。
- 撤回理由（Lead 实测）：
  1. R1 片段 `def Box [A : Type 0] : U5 = Type 5` 里 `U5 = Type 5` 就是 Box 的**声明类型**，
     body `Type 5` 的类型是 `Type 6` ⇒ 声明失败 ⇒ `Box`/`Poly` 全部 "not in scope"，
     `Poly[Nat]` 从未被检查。**R1 该片段属示例代码不成立**，我已在 `a1-r1.md` 的
     对应条目标注更正。
  2. Lead 修成可编译版本 `def Box [A : Type 0] : Type 6 = T5` + `enum Poly [A : Type 0] { mk(x: Box A) }`
     仍卡在 enum 声明：`can't unify expected: (x: ?50492 A) → ?50493 A x, find: Type 6`。
     该报错**不是** elaboration 缺陷，而是**调用语法**：`Box` 的唯一参数是隐式 binder
     （`[A : Type 0]`），`Box A` 会被 `insert_t`（`elaboration.rs:255-260`）先填一个新隐式 meta，
     使 `tty` 变成 `Type 6`（不是 Π），随后走 `infer_expr` 的 App 兜底臂
     （`elaboration.rs:2748-2772`）：造一个新 Π（域/余域都是 fresh meta、绑定名 `x`）
     与 `tty` 合一 → 正是那条 "expected: (x: ?… A) → ?… A x, find: Type 6"。
     本仓已有同款记载：`tests/l13_fast_parity.rs:631-638` 写"`println (f (cons …))`
     报 `can't unify expected: (x: ?N) → ?M x` 的根因（对 Nat 值做函数调用，
     elaboration 侧本无缺陷）"。⇒ **Lead 的语法写法需要 `Box[A]` 而不是 `Box A`**。
- 修正后的候选触发程序（隐式参数用方括号；`MyVec[A] l` 在 `class_tests.rs:617` 已是同款合法写法）：
  ```typort
  def T5 : Type 6 = Type 5
  def Box [A : Type 0] : Type 6 = T5
  enum Poly [A : Type 0] { mk(x: Box[A]) }
  def leak : Type 0 = Poly[Nat]
  ```
  静态预测：`Poly` 声明成功；`leak` **被接受**（漏算复现，`Poly : Type 0`）。
  正确行为应与 Lead 的对照组 `enum Poly2 { mk(x: T5) }` 同判：`Poly2 : Type 6` ⇒
  `leak2 : Type 0 = Poly2` 被拒（`expected Type 0, find Type 6`）。
  **待 Lead 一次运行判定**：通过 ⇒ 升回 P1（并与 `L12_canonical/elaboration.rs:539-545` 同批修）；
  不通过 ⇒ 本条彻底关闭（记为该实验不可判定）。
- 与可达性无关、已由代码定死的部分（两部分都不依赖运行）：
  1. case 字段扫描（`:1399-1405`）执行时 `cxt` **没有**绑定枚举参数——参数只在
     `new_cases`（`:1417-1432`）与 `typ`（`:1440-1442`）的 Π 折叠里才进入作用域；
  2. 引用参数名的字段类型会让 `check_universe` 返回 Err（`Var("A")` → "error name not in scope"，
     `:2479`），而该 Err 被 `if let Ok((_, lvl)) = …` **静默吞掉** ⇒ 贡献 0；
  3. 同形的参数域漏算已在 F1 修掉（`legacy_tests.rs:5338-5369` 的 pin），字段域这一格没有对应 pin。

### [P3]（R1 条目的 R2 收口）`BindingName.mk` 确定性 —— 证明"不是把一种不确定性换成另一种"
- 位置：`elaboration.rs:215-224` 与 `:2560-2569`（R1 已改为 `min_by(字典序)`）。
- **确定性证明**（与运行无关）：
  1. 候选集 `S = { k ∈ keys(decl) : k.ends_with(".BindingName.mk") }` 只依赖 decl 表的**键集合**
     ——键集合是程序与声明序的确定性函数，与 `HashMap` 的遍历序无关；
  2. `str::cmp` 是全序；`HashMap` 的键互不相同 ⇒ 任意两个不同候选的 `cmp` 都不为 `Equal`
     ⇒ `min_by` 的最小元**唯一** ⇒ 与遍历序无关；
  3. `"BindingName.mk"` 精确键优先分支在改动**前后**都排在最前（`:212-213` / `:2557-2558`），
     所以 `|S| ≤ 1` 或存在精确键时，输出与改动前**逐字相同**；
  4. 只有 `|S| ≥ 2 且无精确键` 时取值从"随进程随机"变为"字典序最小"——这是把无定义行为钉成
     确定值，不可能"换成另一种不确定性"（`min_by` 的输入集合与比较函数都是确定的）。
- 残留 needs-verify：`|S| ≥ 2 且无精确键` 的**可达性**未证（需要一个没有非限定
  `BindingName.mk`、却有两份限定 `*.BindingName.mk` 的程序）。该分支此前也从未被任何确定性
  测试钉住（旧行为随机 ⇒ 若有测试覆盖它早就是 flaky）。⇒ 我把 R1 的 P2 降为 **P3 + needs-verify**：
  不确定性本身已被消除，剩下的是"这条分支实际能不能被走到"。
- 快版同点位是**另一套确定性**规则（`bump_spine_iter/machine.rs:919-923`：精确名优先，否则取
  **登记序**首个），两侧都确定但 |S| ≥ 2 时取值可能不同 —— 是否逐字对齐留给 A3/Lead 定（见 §4）。

## 5. 设计决定讨论（不属 bug，只记录）

- **锁纪律（R2 复验结论）**：参考版现在与快版同款——"读旧值（短守卫）→ 无锁求值 → 写回（短守卫）"。
  单线程语义下与原"原子持锁"等价（`Infer` 是 `Rc` 非 `Send`，`mutable_map` 只跨 clone 共享），
  但**不再假设**回调期间状态冻结：回调里改同名键现在是"后写胜"，与快版一致。
  `get_global` 改共享读锁后，唯一还取写锁的读写 prim 是 `create_global`/`change_mutable*` 的
  回填段（都不在锁内求值），锁语义收敛为"短临界区"。
- **`Box A` vs `Box[A]` 的报错质量（P3 观察，未改）**：对"唯一参数是隐式 binder 的函数"
  显式应用实参时，用户看到的是 `can't unify expected: (x: ?N) → ?M x, find: Type 6`
  （`elaboration.rs:2748-2772` 的兜底臂直接透传 `unify_catch` 的文案）。
  更可诊断的说法应是 "`Box` 没有显式参数 / 期望函数，得到 Type 6"。
  改文案会动诊断字节，按 BRIEF §6.3 需要独立证据与门禁授权，本轮只记录。
  该形态本身不是缺陷（`tests/l13_fast_parity.rs:631-638` 同款记载）。
- **我的 R1 误判复盘（供团队参考）**：P0（挂起）我给了完整触发程序且被实测证实；
  P1 我给的是"片段级"推测——**根因是没有先把片段跑通就写进报告**。R2 起我把这类
  "机制成立但触发未跑通"的东西一律降到 needs-verify，并在报告里注明"待运行判定"。
