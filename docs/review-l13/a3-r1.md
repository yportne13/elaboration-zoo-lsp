## 2. 发现列表

### [P0] 快版 `Machine::unify` 整机重借 —— Stacked Borrows 别名 UB（L13 独立复核**成立**）

- **位置（L13 实际坐标）**
  - 句柄来源 + 触发失效的解构：`src/L13_namespace/bump_spine_iter/machine.rs:1310`
    （`let mach_ptr: *mut Machine = self;`）、`:1311-1324`（`let Machine { spine, vals, icits, defs, metas,
    mutable, ren, conv, constraints, unify_work, unify_stack, .. } = self;`）、`:1356`（`mach_ptr` 传入
    `unify_iter`）。
  - 失效后的使用点（跨切片，A2 的文件）：`unify.rs:384`（`flex_flex_bump`，定义于 `:337`）、
    `unify.rs:1395`（`solve_flex_side_bump`，定义于 `:1366`）：
    `let tr = unsafe { (&mut *mach_ptr).solve_multi_trait_ref(bump, cxt, m, false) };`
- **机制（按 Miri `stacked_borrows` 实现逐条核对，不是纸面推理）**——Miri 源码
  [`stacked_borrows/mod.rs`](https://raw.githubusercontent.com/rust-lang/miri/master/src/borrow_tracker/stacked_borrows/mod.rs)：
  1. `mach_ptr = self`（`&mut Machine → *mut Machine`）是 `RetagMode::Raw`：`NewPermission::Uniform {
     perm: SharedReadWrite, access: None }`，`Stack::grant` 走 `access == None` 分支 ⇒
     `find_granting(Write, self_tag)` 后插到 `find_first_write_incompatible(self_idx)`；`self` 的参数 tag 是
     `Unique`（`pointee.is_unpin()` ⇒ `perm: Unique, access: Some(Write)`）⇒ **raw tag 恰好插在 self tag 正上方**。
  2. 字段解构 `let Machine { spine, .. } = self;` 会产生 `&mut (*self).spine` 等**独立 retag**（每个字段一个
     `Unique`，`access: Some(Write)`，parent = `self` 的 tag）。`Stack::access(Write, self_tag)` →
     `find_first_write_incompatible(self_idx)`：`self` 是 `Unique` ⇒ "On a write, everything above us is
     incompatible" ⇒ `self_idx + 1` ⇒ **弹出正上方的 raw tag**（在本字段的字节范围内）。
     弹出项无 protector，故这一步本身不报错，只是把 `mach_ptr` 变成死 tag。
  3. 各字段字节栈独立 ⇒ 字段 `&mut` 之间互不影响（与借用检查器允许不相交字段借用一致）；
     但 raw tag 覆盖**整个 `Machine`**，所以在**每个**被解构字段的字节范围内都被弹掉。
  4. `&mut *mach_ptr` 的 retag 范围 = `size_of::<Machine>()`（整机），其 `access(Write, raw_tag)` 必须在
     **每一段字节栈**里 `find_granting` 到 raw tag；被解构字段的字节段找不到 ⇒ `dcx.access_error` ⇒ **UB**。
     （关键：`mach_ptr` 是**具体 tag**，不是整数往返出来的 Wildcard；不适用"匹配 unknown 部分"的近似分支。）
- **可达性**：任何走到 `flex`（未解 meta）求解 → trait 合成的路径。本仓测试已把该路径钉住：
  `tests/twin_engine_tests.rs:674-695`（`twin_solves_implicits_around_nested_unify`，注释明确写
  "that is what forces trait synthesis (and hence the nested `unify`) mid-comparison"），
  以及 `examples/theorem_proving.typort` / `examples/adder_proof.typort`。
  触发的是**表达式求值**（`&mut *mach_ptr`），不需要内层真的解出 trait。
- **"一步之遥"脆弱点**：`unify.rs:691` `let pre_tm_len = unsafe { (*mach_ptr).trait_metas.len() };`
  之所以不 UB，是因为 `trait_metas` **不在** `machine.rs:1311-1324` 的解构列表里（该字段字节栈上 raw tag 还在）。
  任何人把 `trait_metas` 加进该解构列表，这一行的读就会立刻变成 UB。
- **最小复现思路（无 Miri 环境下的可执行方案）**
  1. 纯 Rust 最小片段（无需本仓）：
     ```rust
     struct S { a: Vec<u8>, b: Vec<u8> }
     fn f(s: &mut S) {
         let p = s as *mut S;                  // SharedReadWrite，插在 s 的 Unique 正上方
         let S { a, b } = s;                   // 每个字段 retag 的 write-access 弹出 p
         unsafe { (*p).a.push(1); }            // UB：p 在 a 的字节栈里已不存在
         a.push(2); b.push(3);
     }
     ```
     `cargo +nightly miri run`（**不要**加 `-Zmiri-strict-provenance`，理由见 §5.3）应报
     "attempting a write access using `<tag>` … does not exist in the borrow stack"。
  2. 本仓真实入口：`cargo miri test --test twin_engine_tests twin_solves_implicits_around_nested_unify`
     或 `MIRIFLAGS=-Zmiri-permissive-provenance cargo miri test --lib` 的 L13 段。
- **处置：仅报告 + needs-verify（BRIEF §6.7 不得盲改）**。修复方向（供立项，不在本轮实施）：
  `solve_multi_trait_ref`/`solve_trait_ref` 改为接收**不相交字段的自由函数**（`spine/defs/metas/mutable/…
  逐个传参），或把"M 台求解态"拆成不与其余字段同处一个 `&mut Machine` 的子结构。**注意**：
  把 `let mach_ptr = self` 挪到解构之后再取 raw 指针**不能**解决——只是把弹出方向反过来
  （此时 `&mut *mach_ptr` 的 write-access 会弹掉字段 `&mut`，随后 `unify_iter` 的
  `stack`/`spine`/`work` 使用仍旧 UB）。

### [P1] 合一失败后该 def 名仍可解析（`fake_bind` 就地写调用方 Cxt + 错误恢复不回滚）——Lead F2 根因

- **位置（参考版对照，A1/A7 文件）**：`elaboration.rs:1063-1066` `infer_after_prefix` 先
  `let mut cxt = cxt.clone();` 再调用 `infer_after_prefix_mut` ⇒ `fake_bind`（`cxt.rs:1228-1234`，同样是

  **永远不会触发**；② `println(add two two)` 类型良好，`force` 在该 Decl 头链上停住（`force.rs:671+`），
  pretty 渲染出 `add 2 2`。
- **为什么参考版的同类就地 COW 不出事**：参考版 `infer_in_place`（`elaboration.rs:1045-1054`）的调用者
  **全部首错即停**——`mod.rs:3709` 用 `?`、`mod.rs:4537-4540` 直接 `return false`；只有孪生
  `observe_user` 是"错误不早退 + 保留上一个 cxt"。两条纪律交叉才产生污染。
  `cxt.rs:1219` 的注释显示参考版这份就地 COW 是**从孪生移植过去**的，移植时保留了参考版自己的隔离入口。
- **判定：缺陷（非有意设计）**。孪生注释只论证了成功路径（`machine.rs:798-802`："decl_reg 随后以真值静默
  覆盖同名条目"），错误路径的交互未被考虑；参考版行为（not-in-scope + 无 println 输出）是用户可见契约。

  1. `observe_user` 里 per-decl `clone_cxt` 快照 + 失败回滚：会让 `decls` 的 Rc 计数恒 ≥2 ⇒ 每次
     `fake_bind`/`decl_reg_in` 的 `make_mut` 退化为整表深拷贝——正是 `machine.rs:798-801` 记录并在
     2026-09-12 修掉的 O(D²)。**不可用。**

     `DeclEntry(SmolStr, Option<DeclEntry<'static>>)` + `observe_user` 的 per-decl 帧（成功并入父帧、
     失败回滚）即可；但这是 ≥40 行的热路径改动，且一旦写错会**污染声明表本身**（比当前"少一条诊断"更糟），

  3. 只删 stub 的 `Rc::get_mut` 补丁在 `fake`（`clone_cxt` 的共享者）仍存活时必返回 `None` ⇒

### 5.3 对 `FINAL.md` §3.1 建议的 CI 命令的修正（重要，影响立项）

⇒ 建议：**(a)** 用默认（permissive）provenance 跑 Miri 以检出 §2.1；**(b)** 把 packed-word 的
int→ptr 作为"已知 provenance 空洞"正式记录（它仍有价值：地址非法/悬垂仍会被 Miri 抓到——
