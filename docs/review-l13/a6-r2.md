### [P3] 文件开头的 UTF-8 BOM 被词法层当成 `ErrToken`：每个 BOM 文档一条伪解析错误（原 needs-verify ① → **确认并已修**）

- 位置：`src/L13_namespace/parser/lex.rs:297`（`err_token`）、`:304-310`（前导空白，本轮改动）
- 证据（完整 token 轨迹，无需运行）：
  1. `pmatch(|c| c.is_whitespace())`（`:304` 原式）用的是 Unicode `White_Space` 属性；
     U+FEFF **不在**该属性表内（PropList White_Space = 0009..000D/0020/0085/00A0/1680/2000..200A/2028/2029/202F/205F/3000），
     所以 BOM 不被前导空白吃掉；
  2. token 循环里 `string`/`macro_ident`/`brace`/`op`/`num`/`ident`/`endline` 全部不匹配 U+FEFF
     （`op` 的字符区间是纯 ASCII；`ident` 的 `is_alphabetic()` 对 Cf 类字符为 false）；
  3. 落到 `err_token = pmatch(|c| !c.is_ascii_whitespace())`（`:297`）⇒ 产出 `ErrToken`，
     顶层 `p_decl` 失败 → `recover_with(skip_until_decl)` 记录一条错误并同步到下一个声明。
  4. 触发面：`src/bin/cli.rs:705` 的 `fs::read_to_string` **不剥 BOM**（只校验 UTF-8）⇒ CLI 路径必然触发；
     LSP 路径取决于客户端是否把 BOM 放进 `didOpen.text`（全仓 grep `FEFF|BOM` 无任何处理、无测试）。
- 机制/影响：每个以 BOM 保存的 `.typort` 都会在编辑器里多一条红色诊断（"unexpected token"），
  CLI 输出多一条错误；解析结果本身不丢声明（`skip_until_decl` 能同步）。属**伪诊断**（P3），不是数据破坏。
- 处置：**已修（1 行，最小 diff）**：前导空白匹配器扩为 `c.is_whitespace() || c == '\u{feff}'`。
  只作用于文档**开头**（token 循环内的 `ws()` 不含 BOM）⇒ 文件中间的 U+FEFF 仍是 `ErrToken`，行为不变；
  唯一的既有差异面是"以 BOM 开头的输入"，全仓无此类语料/测试，故零回归面。
  钉子：`tests/parser_error_tests.rs`（`token_errors::leading_bom_is_skipped`）——断言
  (i) 首个声明 `f` 仍被解析、(ii) 不出现含 "unexpected token" 的错误（故意不断言"零错误"以外的东西，避免脆断言）。

#### ② 深层嵌套 `$(` 的匹配器递归无上限 → **仍无法判定（需实测）**

- 位置：`parser/mod.rs:2277`（`p_macro_group_matcher`）↔ `:2399`（`p_macro_matcher_sequence`）↔
  `:2329`（`p_macro_matcher_single`）；同族还有 `macros.rs:309-332`（`MacroTranscriber::Group::replace` 递归）。
- 依据（为什么无法静态定案）：每层递归的**源码成本**是确定的（≥4 字节：`$(` … `)*`），
  但每层**栈成本**（若干闭包/迭代器帧的字节数）只有实测才知道；8MB 栈下若按 500B/层估算需 ~1.6 万层
  （≈64KB 单行源码），按 4KB/层估算需 ~2000 层（≈8KB 源码）——两种结论的严重度完全不同。
- 给 Lead 的**安全探针设计**（不会以 SIGSEGV 收场）：
  ```rust
  // 生成 src = "$(".repeat(n) + ")*".repeat(n) 的宏定义体（放在 macro_rules m { () => { … } } 的转写器里）
  // 在 stack_size = 8MB 的线程里跑 parser(src, 0)，n 取 500 / 2000 / 8000 三档；
  // 任一档返回 Some（或 depth 限制错误）即说明"合法输入不可能触顶"（用户要写 MB 级单行才可能）。
  // n 档失败时不要把栈叠满：只记录"该档未通过"。
  ```
- 建议：若 n=2000（≈8KB 源码）即溢出，则给 `p_macro_group_matcher` 也挂 `MacroDepthGuard`
  （与命名片段同款，改动 ~6 行）；否则记为"理论存在、实用不可达"，仅文档留痕。

      ⇒ **整体不生成 `TypeName.create` 工厂**（`build_field_create_expr` 的不识别分支是 `Raw::Hole`，

  设计决定，不在我轮内单点改）：(i) pass 1 对 `Decl::Derive{decl: Decl::Class}` 先做

## 5. 设计决定讨论（不属 bug，只记录）

1. **BOM 放在词法层而不是 `preprocess`**：`preprocess` 的契约是"输出与输入**等字节长**"（`mod.rs:4470`），
   用它剥 BOM 只能"3 空格替换 3 字节"——那会改变文本内容（虽然对 BOM 无害），但会与
   `L06` 那套"注释外一律原样"的语义混在一起；放在 `lex` 的前导空白里既不改字节、也不影响
   `preprocess` 的黄金校验。选它的代价是：`parser_test`/`parser_with_macros` 的所有入口共享该行为，
   而 `format` 侧（自己 `scan_raw`）不受影响——两侧对"什么可以忽略"的口径本来就不完全一致（见 §4.2.4）。
2. **命名片段与展开重解析共用同一深度计数**（R1 §5.3 保留）：两者语义不同但都属"宏嵌套"，
   实测上限 256 对合法程序是数量级余量；若日后出现"合法程序触顶"，应拆成两个计数而不是抬高上限。
