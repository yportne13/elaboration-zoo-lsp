### [P1] 正常 `shutdown` 后 LSP 进程不退出：`io_threads.join()` 永久挂起 —— 已修

- 位置：`src/lib.rs:4067-4068`（F2 闸之前为 4028-4029，`350b35a` 上为 4008），同一缺陷另一处在
  `src/lib.rs:4020-4032`（init 失败分支，`drop(backend)` 在 `:4026`）。
- 证据链（全部可静态复核）：
  1. `src/lsp_stdio.rs:157` `let (writer_sender, writer_receiver) = unbounded::<Message>();`，
     唯一的发送端由 `stdio()`（`:128-131`）放进 `lsp_server::Connection { sender, .. }`；
     写入线程是 `writer_receiver.into_iter().try_for_each(...)`（`:162`）——
     `Receiver` 迭代器**只在"通道空且所有发送端已 drop"时**返回 `None`。
  2. 该 `Connection` 被 `Client`（`src/client.rs:111-113`）持有，而 `Client` 被
     `Arc<Backend<Client>>` 持有：`src/lib.rs:4018` 的 `backend` 在 `run_lsp_server` 作用域内**一直存活**，
     直到函数结束才 drop。
  3. `src/lib.rs:4068` 的 `io_threads.join()`（`src/lsp_stdio.rs:110-121`：先 join reader、再 join writer）
     因此卡在 writer 上：`backend` 未释放 ⇒ 发送端未 drop ⇒ 迭代器阻塞。
  4. 上游 `lsp-server` 没有这个问题，因为它的示例把 `Connection` **按值**交给 `main_loop`
     （见 `~/…/lsp-server-0.7.9/src/lib.rs:40` 与 `stdio.rs:13-55`：`Connection` drop 时发送端随手释放）。
- 机制/影响：**用户每次正常关闭编辑器（shutdown+exit）都留下一个不退出、不响应、还持有常驻孪生
  `~430MB` 的僵尸语言服务器进程**；`src/lib.rs:4071` 的 `eprintln!("shutting down server")` 属死代码
  （永远打不出来），客户端只能强杀。init 失败但通道已断的路径（`:4020-4032`）同构：reader 已结束、
  writer 仍被 `backend` 钉住 ⇒ 同样挂起。
- 处置：**已修**。在上述两处调用 `io_threads.join()` 之前 `drop(backend);`（释放唯一发送端），
  并加注释说明为什么必须在这个顺序上。行为影响：正常 shutdown 从"永久挂起"变为"退出 0"；
  非 shutdown 断连路径不变（仍 `result?` 传播 Err → 退出 1）。
- needs-verify（Lead）：本机无 LSP 进程级测试覆盖该收尾（§4.2），建议 `typort lsp` 手工
  打通 shutdown+exit 观察进程是否自行退出。

### [P1] `main_loop` panic 被吞掉后仍 `Ok(())`：真崩溃 exit 0，与 `09c78e9` 的口径相反 —— 已修

- 位置：`src/lib.rs:4039-4060`（F2 闸之前 4000-4021，`350b35a` 上 3992-4007）。
- 证据：改动前
  ```rust
  match main_result {
      Ok(result) => { result?; }
      Err(panic_err) => { eprintln!("main loop panicked: {}", msg); }   // 吞掉，继续往下
  }
  io_threads.join()?;
  eprintln!("shutting down server");
  Ok(())                                     // ← panic 也走这里：exit code 0
  ```
  而 `09c78e9` 的提交说明与 `src/lib.rs:3819-3823` 的注释明确写"宿主无法区分正常关闭与崩溃"，
  并为此把"无 shutdown 断连"改成返回 `Err`。⇒ 同一提交的**另一条路径（真正的 crash）退出码仍是 0**，
  信号方向被弄反：EOF 断连（无害）exit 1，panic（真崩溃）exit 0。
- 机制/影响：`catch_unwind` 之后还继续走 `io_threads.join()`：`main_loop` 已死、无人消费消息，
  reader 仍在往无界通道里堆消息（内存无上限增长），writer 又被 `backend` 钉住 ⇒ 崩溃表现为**挂起**
  而非退出（本项与 P1-1 叠加）；即便 exit，宿主看到的也是成功码。
  触发面：任何 `main_loop` 内可达 panic（例如持锁区 panic 导致 `cxt`/`twin_prelude` 中毒后下一次
  `.lock().unwrap()`，见 §2 P3-3 与 needs-verify-3）。
- 处置：**已修**。panic 分支改为先打印、随后直接 `return Err(format!("main loop panicked: {msg}").into())`
  （`src/lib.rs:4058`），不再 join（注释说明：join 只会把崩溃表现成挂起）。
  行为影响：真崩溃从 exit 0 变为 exit 1（符合 `09c78e9` 的口径与 LSP 规范精神），
  且不再留僵尸进程。

### [P1] 信任闸放行"孪生版产出参考版没有的 println 值"（Lead 实测 F2，已修）

- 位置：信任闸判据 `src/lib.rs:1551-1579`，新增值输出面闸 `:1580-1617`（判据在 `:1610`）。
- 证据（**实测方 = Lead**，`docs/review-l13/LEAD-probes.md` §F2；我逐条复核了代码路径）：
  - 输入：非递归 `def add` 却体内自引用 + `def two` + `println(add two two)`；
  - `Engine::Reference`：errs = [`can't unify …`, `error name not in scope: add`]，**infos = []**；
  - `Engine::Twin`：errs = [`can't unify …`, **同一条再来一遍**]（漏了 not-in-scope），
    **infos = [`add 2 2`]**，且**没有回落**（日志无 `twin fallback:`）。
- 机制（代码级）：
  1. 孪生的错误全部命中 `classify` 的 `can't unify` 前缀（`:1552-1554`）⇒ `untrusted == None`
     ⇒ 直接进入发布路径；信任闸**只看 error 的类别**，`printlns`（`:1501-1515` 采集）从不参与判据。
  2. 参考版在 decl 失败后把该名字移出作用域（失败 decl 不导出，见 `elaborate_reference` 的
     `has_error` 分支），于是 `add` 在后面是 not-in-scope 且无法求值；孪生把失败的 `add`
     当不透明 rigid 留在会话里 ⇒ 求值成功并 pretty 出 `add 2 2`。
  3. 结果：**INFO 面板告诉用户"算出来了"**，而参考版认定那个名字根本不在作用域——
     这不是"错的诊断"，是**错的结果**，比错的诊断更糟（BRIEF 的 P1 口径）。
- 处置：**已修**（最小 diff，`src/lib.rs:1610-1617`）：
  ```rust
  if !errors.is_empty() && !printlns.is_empty() {   // 信任类错误 + 值输出 ⇒ 交回参考版
      self.twin_tables.remove(&uri_str);
      self.note_twin_fallback(&uri_str, "error-state-with-println", …);
      return false;

  ```
  理由与边界（已写进代码注释）：参考版是权威输出，回落只会变慢、不会变错；
  判据只取证据支持的那一半——**孪生自报错误 + 又产出了 println 值**；
  `parse_errs` **不计入**（两引擎同一 parser、逐字节相同，算进去会让打字期半成品文件大规模回落，
  正是信任闸本来要消除的双跑）。
- 代价与残留（诚实记录）：
  - 代价：**含 `println` 的文件在错误态下重新变成双跑**（错误态无 println 的常见打字路径不受影响）。
    这是"宁可慢也不要错"的方向选择；若日后要收回，必须先把孪生的错误恢复路径修到与参考版一致（§4.2）。

### [P2] CLI 诊断渲染按 `char` 计数而非 UTF-16：非 BMP 字符后诊断错位/整条丢失 —— 已修

- 位置：`src/client.rs:21-45`（`position_to_byte_offset`，`render_diagnostics_stderr` 唯一调用点 `:62-63`）。
- 证据：旧实现 `char_count += 1`（每个 `char` 记 1）判断 `char_count == position.character`；
  而服务端所有诊断 range 的列号来自 `src/lib.rs:3856-3871` 的 `offset_to_position`——
  按 `ch.len_utf16()` 计数（`initialize` 未声明 `offset_encoding`，LSP 默认即 UTF-16）。
  两者对 **BMP 及以下完全一致**，但只要同一行出现过非 BMP 字符（emoji、CJK 扩展 B 等，
  1 `char` = 2 UTF-16 单元）就开始偏：
  - 列号偏 1 起 ⇒ `typort check` 的 codespan 下划线**指到错误的 token**；
  - 若列号等于"行内容 char 数 + 多出的 UTF-16 单元数"这一形态，循环走完仍不相等 ⇒
    函数返回 `None` ⇒ `render_diagnostics_stderr` 的 `filter_map`（`:53`）**静默丢掉这条诊断**。
- 触发用例（静态可推）：`def y: Nat = succ 🎉bad`（emoji 在同一行、诊断 span 在 emoji 之后/到行尾）
  ⇒ CLI 输出与 LSP 弹窗对同一份诊断的定位不一致，极端形态下 CLI 完全不报。
  与 `tests/test_rope_offset.rs` 自己钉的口径（该文件全文按 UTF-16 语义写断言）也矛盾。
- 处置：**已修**（最小 diff）：`position_to_byte_offset` 改按 `ch.len_utf16()` 累计并改名
  `char_count → utf16_count`，补文档说明"必须与 `Backend::offset_to_position` 同口径"。
  ASCII/BMP 行为逐字节不变（`len_utf16() == 1`），非 BMP 行为变正确。

## 5. 设计决定讨论（不属 bug，只记录）

1. **"错的诊断比慢的诊断更糟"的机制覆盖**：F2 之后，值输出面（INFO）有了独立闸
   （错误态 + 有 println ⇒ 回落，§2 [P1-3]），但另两半仍缺机制：
   "孪生报出信任类错误但错误集本身是错的"（needs-verify-1，F2 已证实机制、缺无 println 的实例）
   与"孪生漏报"（HDL 自检闸撤除后）都只剩语料级测试兜底。
   `docs/l13-perf-replace-2026-09-27.md` 的 R0（引擎对拍报告）正是补这几半的正解 ——
   建议把它作为撤任何闸的前置条件，而不是靠扩语料。
   本轮的 INFO 闸是**保守近似**：它不判断"哪个值更对"，只在无法自证时把权威还给参考版。
2. **`catch_unwind` 与"崩溃可见化"的取舍**：本轮的修法是"panic → Err（exit 1）且不 join"。
   另一个可选设计是保留 `catch_unwind` 但立刻 `std::process::abort()`（让宿主/OS 直接看到非正常终止）
   —— 与 VS Code 扩展的 `State.Stopped` 计数兼容，也不会有"挂起"形态。本轮选 Err 是为了与
   `09c78e9` 的既有口径（`Box<dyn Error>` 链 → 非零退出码）保持一致，且能被 CLI 打印成人话。
3. **粘性降级的通用风险**（`twin_gate_distrusted`）：长驻进程里的"粘性早退"本质上是
   把运行期观测结晶成永久状态，而唯一的解除点是文件关闭。若将来重新启用任何同类闸，
   建议把"粘性"限制为"直到下一次成功的探测为止"（带一次重探机会），而不是"直到关闭"。
4. **`Engine` 选择函数的可测性**：`lsp_default`/`from_env` 读环境变量、不可注入，
   于是最关键的引擎选择逻辑天然难测。若要长期维护双引擎，建议把"环境变量 → Engine"的决策
   抽成 `fn engine_for(mode: Option<&str>, default: Engine) -> Engine` 纯函数，让 env 读取只留一行
   （属重构建议，不在本轮改动内）。
5. **值输出面闸的取舍（记录，便于下一轮复议）**：`errors` 非空 + `printlns` 非空 ⇒ 回落，
   意味着"含 println 的文件在错误态下双跑"。选它的理由是**不回落的代价不可见且更坏**
   （F2：用户看到一个参考版根本不承认的值）；不选"更窄的形状匹配"（例如只在该值串里出现
   本文件 decl 名时回落）是因为那要靠 pretty 串做子串匹配，误判面与漏判面都不可控。
   若 A3 把孪生恢复路径修到与参考版一致（§4.2），本闸应整体撤除并加一条
   "错误+println 的 twin↔reference INFO 对拍"作为替代门禁。
