### [P0] 参考版 `change_mutable` / `change_mutable_default` 持写锁调用回调 → 用户可触发自死锁（挂起）
- 位置：`src/L13_namespace/cxt.rs:718-739`（`change_mutable`，已修为 `:728-734`）、
  `:846-864`（`change_mutable_default`，已修为 `:852-860`）。
- 证据（修复前）：
  ```rust
  if let Ok(mut x) = infer.mutable_map.write() {          // 写守卫 x 一直存活
      if let Some(x) = x.get_mut(&a.data) {               // 内层同名遮蔽
          *x = infer.v_app(decl, &args[1], x.clone(), Icit::Expl)  // ← 持锁求值回调
      }
  };
  ```
  1. `mutable_map` 是 `Rc<std::sync::RwLock<HashMap<String, Rc<Val>>>>`（`mod.rs` 字段声明，
     现 `:1367`），`std::sync::RwLock` **不递归**：同线程在写守卫存活时再取同一把锁 = 死锁。
  2. 回调是**急切求值**的：`v_app(Val::Lam(..))` → `closure_apply` → `self.eval(...)`
     （现 `mod.rs:2831`、`:2826`），eval 机器 `Frame::ApplyAfter` 对非 λ 头直接
     `self.v_app(...)`（现 `mod.rs:3247` 起的臂），而 `Val::Decl` 带 prim 时立即执行 prim
     （`v_app` 的 `Val::Decl` 臂，现 `mod.rs:2831+`）。
  3. 于是回调体里**直接出现**的 `get_global`（修复前一并取**写**锁，`cxt.rs:745` 旧码）、
     `change_mutable(_default)`、`create_global` 都会在同一线程重入同一把锁。
  4. 触发程序（先 `create_global`/播种，否则 `change_mutable` 走不到 `v_app`）：
     ```typort
     class probeReent {
         let _ = change_mutable_default("ModuleTree", x => x, ModuleTree.mk(0, nil))
         let _ = change_mutable("ModuleTree", x => get_global("ModuleTree"))
         let _res: ModuleTree = get_global("ModuleTree")
     }
     println (moduleTreeVL(probeReent.create._res))
     ```
     形状与已绿的 `class_tests.rs:381-428` 同构（该类先 `change_mutable_default` 播种再
     `change_mutable` 链）。修复前该程序在同一线程二次拿写锁 → 挂起。
- 机制/影响：`change_mutable*` 是 `Cxt::new`（`cxt.rs:1013-1054`）注册给**用户程序**的 builtin，
  因此属"用户程序可触发的挂起"（P0）。同时它是**参考版 vs 快版的纪律分叉**：快版
  `PrimId::ChangeMutable`（`bump_spine_iter/prim.rs:591-611`）与 `ChangeMutableDefault`（`:635-654`）
  都先 `let old = mutable.borrow()...;`（临时守卫，语句末即释放）、**无守卫**跑 `vapp1`、
  最后单独 `borrow_mut()` 回填——正是参考版缺的那一步。
- 处置：**已修（最小 diff，语义等价）**：取旧值 → 释放锁 → `v_app` → 重新取锁回填；
  缺键不写、锁中毒静默 no-op 的既有行为保留（旧码 `if let Ok(...)` 同样吞中毒）。
  顺带把 `get_global`（`:753`）由 `write()` 改为 `read()`：与快版 `PrimId::GetGlobal`
  （`prim.rs:619` 的 `mutable.borrow()`）及本文件 `get_global_default`（`:769`）同口径，
  只读 prim 不再争排他锁（HDL 每个 module/frame 都调它），行为不变（两者中毒时同样 panic）。
- **未验证**：我不能运行编译/测试；§4 给出 Lead 的验证方案（必须带超时）。

### [P2] `Locals::update_by_cxt` 把精化绑定的"定义值"写成 `U(0)` 占位（与 L11 分叉）
- 位置：`src/L13_namespace/syntax.rs:53-67`（占位在 `:62`：`infer.quote(decl, lvl, &Val::U(0).into())`；
  `:61` 留着注释掉的 `//infer.quote(decl, lvl, v),`）。
- 证据：GADT 精化把 `Locals::Bind` 升级成 `Locals::Define` 时，该 Define 的第三字段（定义值 Tm）
  被写成 `Type 0`。唯一语义消费者是 `close_ty`（`syntax.rs:76-78`：`Define → Tm::Let(x, a, t, b)`），
  它被 `fresh_meta` 用来闭包化 meta 类型并**立即 eval**（`mod.rs` 的 `fn fresh_meta`，现
  `:2478`；内层 `eval(decl, &List::new(), &close_ty(&cxt.locals, quote(a)))` 在 `:2489`）——
  `Tm::Let` 会把第三字段当值代入，于是精化变量在 meta 类型里被替换成 `Type 0`。
  对照：`L11_macro/syntax.rs:51-60` 写的是 `infer.quote(decl, lvl, v)`（真值）；
  `L12_canonical/syntax.rs:53-67` 与 L13 同为 `U(0)`；快版无对应机制（其 refresh 直接产出值与
  env，`bump_spine_iter/machine.rs:2711-2729`），故若可观测则是**参考版独有的静默降级**（parity 裂缝）。
- 机制/影响：在"先 GADT 精化、后建 meta 且 meta 类型提到被精化变量"的程序里，meta 类型携带
  `Type 0` 而非精化值 → 可能假拒（`can't unify for unsolved meta` / 结构冲突）。属静默错误结果类，
  但**可达性未证**，故不急升 P1。
- 处置：**仅报告 / needs-verify**。不盲改原因：`U(0)` 是 `40a0243`（"better canonical, but still
  possible to panic"）刻意替换 `quote(v)` 的结果——`quote(v)` 在 v 越界时会走 `lvl2ix` 的
  `panic!("level ... is out of scope")`（`mod.rs` 的 `fn lvl2ix`，现 `:1126`）。换回去可能重新
  引入 panic，必须整仓测试背书 + 与 L12 同批。
