## P1 参考版 L07-L09：`SumCase.datas` 按值持有 → 依赖 match 自递归链 O(n²)

- **症状**：natadd（`add x y = match x { case succ(n) => succ (add n y) }`，
  `p{i} = add p{i-1} p{i-1}`）参考版 k=9/10/11 = 0.22/0.93/4.74 s
  （×4.2/翻倍 = O(n²)），k=12 = 25 s / **24.8 GB RSS**；孪生全章线性
  （0.9 ms @k=11）。
- **根因**：`Val::SumCase.datas: Vec<(Span<String>, Val, Icit)>`
  （L07-L09，`src/L07_sum_type/mod.rs:163` 一族）——match 提取字段 `n`
  即深拷贝剩余 succ 链，第 j 步拷 O(n−j) → 单次 add O(n²)。同源对照：
  L10 起字段是 `Rc<Val>`（`src/L10_typeclass/mod.rs:142`），提取 = 引用
  计数 +1，实测线性 2.11 ms。这是 L02 readme 教训 1（共享性一级效应）
  在构造子值上的重演：L02 修了 `VApp`，L10 的 Rc 迁移顺手治好了
  SumCase，L07-L09 掉队。
- **修法**：L07/L08/L09 参考版 `Val::SumCase`（及 `Sum` 的参数槽）迁
  `Rc<Val>`——语义保持重构，跨三章值世界（eval/match/quote/pretty 的
  所有权路径）。
- **验证**：三章 `cargo test --lib` + fast_parity 全绿；natadd basic
  k=13 应到 ms 级且 ×2/翻倍；church/strchain/struct/match 无回归。

## P2 孪生 L09/L10：`bind_name` 每 binder 整表克隆（universe 残留平方项）

- **症状**：同一 universe 源（1029-4096 defs），L09/L10 孪生 65 ms
  @k=11（16 µs/decl，×4/翻倍），L11/L12 孪生 1.8 ms（0.45 µs/decl），
  L13 孪生 3.45 ms——**同源同参差 19-35×**。
- **根因**：L09/L10 孪生 `bind_name` 每 Π binder `(*cxt.names).clone()`
  深克隆 by_name+by_lvl 双 HashMap（L09 移植时丢掉 L08
  `name_map + name_trail` O(1) 机制的回归；define/fake_bind 已在
  2026-09-12 的 COW 轮修掉，bind_name 因父视图遮蔽风险未机械套
  make_mut，见 opt-name-table-cow 文档残留项 1）。
- **修法**：恢复 L03-L08 的 `name_map + name_trail` 持久结构（L03
  readme「名字解析 O(1)」节 + commits 6efa7dc/ccf943d/985390b/a483331
  为蓝本）。注意 L09+ 的 meta 快照语义与 L08 不同（refresh 走
  update_cxt），trail 回滚边界要按 L09 的 decl 边界重推。
- **验证**：L09/L10 universe 孪生 k=11 应到 ~2 ms 档；universe 双实现
  parity 逐 k 不变；church/natadd/match 无回归。

## P3 共享：pretty 打印深链 O(n²)（L11+ 全流程口径被输出绑定）

- **症状**：church（L11/L12 逗号复活版，生成器带 `println p{k}`）两版
  全流程 k=12→13 = 35→143 ms（×4.1/翻倍），倍率 1.0×——基本版与孪生版
  数字几乎重合（147.9 vs 142.2 ms @k=13），而孪生 bare 口径（check+quote
  无输出）只要 1.58 ms。约 140 ms 全在 pretty。
- **根因**：`pretty_tm` 对嵌套链逐节点 `format!` 拼接，深度 d 处的字符串
  上下文 O(d)，全链 O(n²) 字节。两版 print 路径同构（都经
  export → pretty_tm），故互相抵消成 1.0×。L02-L10 的 church 计时不含
  输出路径（生成器无 println），所以此前没暴露。
- **修法**（两选一）：a) L01 `bump_spine_rpn` 同款思路——quote 直出字节
  流免中间树；b) pretty 改增量 builder（`String::with_capacity` + 逐节点
  push，避免 format! 的重复扩容）。b 改动面小，先量 b。
- **验证**：L11 church full-flow k=13 应从 ~143 ms 降到 ~5 ms 档；输出
  逐字节不变（golden 锚）。

## P4 L13 bench 路径：孪生逐 decl 观察面 O(D²)（未定位到行）

  同源同参的 L11 孪生 2.81 ms。universe 反例（L13 孪生 3.45 ms/1029
  defs，近线性）说明引擎核心不平方——是 bench 路径形态

- **根因**：未逐行定位（候选：issues 累积/扫描、prim 版本追踪、defs
  平坦区相关）。bench 形态固有成本，非引擎回归。
- **修法**：先定位（`L13BENCH_DIAG` 式分相计时打点），再决定是排水
  批量化还是观察面延后。
- **验证**：strchain 孪生 k=11 回到 ~5 ms 档；prelude-hdl 无回归。
