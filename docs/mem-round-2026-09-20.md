# 内存轮（2026-09-20）：孪生 prime 峰值、缓存容量常驻、LSP 关闭不释放

> 本轮口径：**峰值工作集（Peak Working Set）**为第一指标——它是用户唯一能感知的
> "内存占用"（任务管理器/系统 OOM 看到的数）；`typort stats` 的 dhat 口径另列。
> 所有生产态读数取 `--release`（mimalloc）构建；`mem-profile`（dhat）构建的绝对值
> 不可与生产态直接比较，只用于分配归因。

## 0. 结论

1. **LSP 默认引擎（孪生）的峰值是参考引擎的 ~4.7×**：同一份 `check`，参考 199.8MB、
   孪生 926–976MB。孪生是为速度选的（文档记的 2.2× 是**稳态**），但**峰值**差得更多，
   而峰值决定"编辑器会不会被 OOM 杀掉"。
2. 峰值的主因不是"残留数据"，而是 **bump arena 的分配量**：arena 只增不减，
   `Bump::allocated_bytes()` ≈ chunk 链总和 ≈ RSS。关压实实测 cap 2054MB / 峰值 1939MB；
   开压实（每文件边界）后 cap ≤115MB 但峰值仍 926–976MB——**单文件、乃至单 decl
   内部的 churn 拦不住**。
3. 另有 ~250MB 属**分配器滞留**（已释放未归还）：`MIMALLOC_PURGE_DELAY=0` 使 CLI
   孪生峰值 940→691MB（−26%），代价运行时长 5.3→6.3s。
4. LSP 侧 `didClose` **原本不释放**（`document_map`/`document_id` 从不删；
   `file_symbols` 缺键时直接 `return`，跳过 `remove_file` 的全部清理）——长会话无界增长。
5. 跨章节的同族缺陷已按血统矩阵回灌（见 §4）。

## 2. 根因（带证据）

1. **arena 无回收**：`TYPORT_TWIN_NO_COMPACT=1` 对照实测 `cap=2054MB`、峰值 1939MB；
   开压实 962MB。即压实确实救了一半，但粒度太粗。
2. **单 decl 内 churn 是峰值主因**：新增逐 decl 探针（`TYPORT_TWIN_MEM`）实测最大
   单 decl **+122MB**（decl i=671），另有 +119/+84/+81/+77MB。文件边界与 decl 边界
   都拦不住一个 decl 内部的分配。
3. **分配器滞留**：`MIMALLOC_PURGE_DELAY=0` → 940→691MB（−26%），+1s；且
   `NO_COMPACT + PURGE_DELAY=0` = 1933MB（vs 默认 1939MB）证明那 2GB 不是滞留而是
   真实 arena 占用。
4. **压实自身需要第二块 arena**（旧 + 新同时活），dhat t-gmax 快照里最大的活块就是
   chunk 链（613/306/153/77MB 各 1 块，合计 ~1.3GB）。
5. **LSP 生命周期**：`did_close` 不删 `document_map`/`document_id`；`document_id` 的 id 由
   `document_id.len()` 分配，所以"删了再开"会撞 id——这两个缺陷互为因果，必须一起修。

  把常量降到 `1<<17` 即可（代价是每个 epoch 一次重哈希）。

## 5. 未做项与理由

- **单 decl 内 churn**（峰值主因，最大 +122MB/decl）：要改求值与规范化的分配模式
  （例如中间结构复用），属算法级改动，不是机械修复。
- **用户段（每 kick）中途压实**：`Resident` 检查点与 journal 都持有 arena 句柄，
  中途压实会悬垂；需要"双根压实"（同时搬迁检查点与当前状态），改动面大。
- **`RESIDENT_BUMP_LIMIT`（512MB）调小**：它只在 kick **之间**检查，不约束单 kick 峰值，
  调小只增加压实频率与输入延迟。
- **`Locals`/`MetaEntry` 的"按值内联"**：L07/L08 的 `Locals` 按值持 `Ty`/`Tm`、L08/L09 的
  `MetaEntry::Solved` 内联 `Val`（184B/条）看着"费内存"，但改成 `Rc` 是
  **内联换成"指针 + 堆块"**（184B → 24B 表项 + 2×104B 堆块），**内存总量反而变大**，
  只是克隆变便宜——属时间优化，不计入本轮。
- **`rc::Rc`（无 weak 头）迁移**：项目已评估（时间 +11%），内存侧只省 `List`/`Rc<Vec>`
  的 8B 头（`Val`/`Tm` 的 80+16=96 与 80+8=88 落在同一 mimalloc 尺寸类，**收益≈0**），
  且需线程模型配套，未做。
- **`-C link-arg=/STACK:67108864`**：64MB 线程栈预留是虚拟内存，未计入工作集，未动。

## 6. 后续可做（按收益排序）

1. **单 decl churn**：先给 `nf`/`eval` 的中间结构做"每 decl 分配量 Top-N"画像
   （`TYPORT_TWIN_MEM` 探针已能给到 decl 粒度，可再加 decl 内阶段打印），再决定是复用
   缓冲还是改算法。
2. **`MIMALLOC_PURGE_DELAY=0` 作为可选档位**：读数是 −26% 峰值 / +1s（CLI 5.3→6.3s）。
   LSP 是交互进程，建议只在内存受限环境用环境变量开启，不做默认。
3. **双根压实**（用户段中途压实）：把 `Resident` 与 journal 一并搬迁，可把 LSP
   "单次按键峰值 ~930MB"压到 arena 阈值量级。
4. **LSP 按需 prime**：`Engine::lsp_default` 选孪生的前提是它的稳态 ~429MB 可接受；
   若目标是低内存，`TYPORT_LSP_ENGINE=reference` 的峰值只有 1/5（199.8MB），
   代价是按键延迟。

## 7. 性能回归检查（bench A/B，2026-09-20）

### 7.1 方法

- **两侧二进制**：同工具链同机，`git stash push -- src/` → `cargo build --release --bins`
  → 存 `target/mem/bench_before/`；`git stash pop` → 再构建 → `target/mem/bench_after/`
  （13 个 bench + typort，逐文件 md5 均不同）。
- **口径**对齐 `docs/bench-matrix-2026-09-20.md`：隔离进程、k=11（enum/implicit/prune/
  traitchain/moduletree 取 k=9）、rounds=3（traitchain 1 轮）、每格取 min、单 run 上限
  180s（L13 prelude 类 300s）。两轮**顺序相反**（before→after / after→before），每侧取
  两轮 min。运行器：`target/mem/bench_ab.py`（L06–L12 格式）、`bench_ab13.py`（L13 围栏
  格式）、`analyze_ab.py` / `analyze_ab13.py`。
- **控制层**：L04/L05 源码本轮未改动，14 格比值中位 **0.996**、范围 0.933–1.020
  ⇒ 噪声带 ≈±2%（`l05 prune fast_ss` 是既有的临床不稳格，basic 口径该格 28–29s）。

### 7.2 结果（两轮合并取 min）

| 组 | 格数 | 中位 | 最好 | 最差 | 判读 |
|---|---|---|---|---|---|
| 控制层 L04/L05 | 14 | 0.996 | 0.933 | 1.020 | 噪声带 |
| 参考版列 basic（L06–L12） | 36 | **0.987** | 0.712 | 1.071 | 无系统性变化 |
| 孪生列 fast_ss/fast_run（L06–L12） | 52 | **0.999** | 0.779 | 1.065 | 无系统性变化 |
| L13（10 负载 × 2 实现） | 20 | **1.003** | 0.959 | 1.026 | 全部落在 ±3% 内 |

- **单格大幅摆动不能用源码解释**：参考列 `l11 struct` 0.780、`l09 church` 0.712 与
  `l11 strchain` 1.071 这几格，其源码本轮**没改**（L11/L09 只动了孪生文件）；但所有 bench
  二进制都链接改动过的 lib（`elaboration_zoo_lsp`），二进制布局/内联随之变化。LTO 下单格
  ±10–20% 的摆动是布局效应，**判读看分组中位**（与 09-20 矩阵把 L07 church 0.647× 记为
  窗口漂移同源）。
- L13 的 `prelude-core` / `prelude-hdl` / `examples-hdl` 孪生列分别为 0.997 / 0.989 /
  0.991 —— **prime 的真实成本不在这些格里**（它们测的是已 prime 后的逐文件段），要看
  下面的端到端口径。

### 7.3 唯一有因果的成本：prime 阈值压实（端到端 CLI，7 次，min/中位）

| 口径 | HEAD | 本轮@384MB（出厂） | 本轮@192MB |
|---|---|---|---|
| `check`（孪生引擎） | 4.98 / 5.02s | 5.04 / 5.11s（**+1.3% / +1.6%**） | 5.26s（+5.4%） |
| `check`（参考引擎） | 3.11 / 3.14s | 3.12 / 3.14s（+0.3% / 0%） | — |
| 峰值（默认设置 / 强制归还） | 961.5 / 858.7MB | 938.7 / 773.0MB | 920.1 / 690.2MB |

**归因实验**（孪生 `check`，`TYPORT_TWIN_NO_COMPACT=1` 关压实对照，min of 5）：

| 变体 | 时间 |
|---|---|
| HEAD | 5.03s |
| 本轮 | 5.20s |
| HEAD + 关压实 | 4.79s |
| 本轮 + 关压实 | 4.78s |

即：**缓存回收本身零成本**（4.78 vs 4.79），全部差值出在压实频率——HEAD 的"每文件边界"
压实已花 0.24s，本轮的阈值触发再加 ~0.17s（192MB）/~0.07s（384MB）。

**出厂取 384MB**：+1.3% 启动时间换 −10% 活 arena 峰值（并保证单文件不会把 chunk 链顶到
1GB 量级）；内存受限部署把 `PRIME_COMPACT_BYTES` 调到 `192 << 20` 即得 −19.7% / +5.4%。
